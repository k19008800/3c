## 1. 业务定位与目标

### 1.1 兑换码的核心价值

兑换码不仅是"输入一串字符获得免费额度"的简单工具，它是 3cloud 实现 **用户增长 → 活跃 → 付费转化 → 裂变传播** 的营销引擎核心组件。

| 目标 | 说明 |
|------|------|
| 🧲 **拉新获客** | 新用户注册即送、活动推广获客 |
| 🔄 **促活留存** | 老用户回归激励、连续签到奖励 |
| 💰 **付费转化** | 限时折扣码、充值满赠券、套餐体验码 |
| 🚀 **渠道拓展** | 代理商/渠道商自主发码拉客，按效果分成 |
| 🗣️ **社交裂变** | 邀请好友各得额度、分享即得体验码 |

### 1.2 三端定位

```
客户端 (User)         代理端 (Agent)         系统后台 (Admin)
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  消费侧       │    │  发放侧       │    │  管理侧       │
│              │    │              │    │              │
│  • 输入兑换   │    │  • 生成兑换码 │    │  • 规则配置   │
│  • 查记录     │    │  • 管理库存   │    │  • 活动管理   │
│  • 邀请得码   │    │  • 效果统计   │    │  • 审核风控   │
│  • 接收通知   │    │  • 导出数据   │    │  • 全局看板   │
└──────────────┘    └──────────────┘    └──────────────┘
```

## 2. 业务流程全景

### 2.1 兑换码完整生命周期

```
┌────────────────────────────────────────────────────────────────────────┐
│                        兑换码生命周期                                    │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│  ① 创建 ──→ ② 分发 ──→ ③ 用户领取 ──→ ④ 使用消耗 ──→ ⑤ 过期/作废      │
│  (admin/    (渠道/活动/   (输入兑换码)   (token 划入   (到期自动失效)     │
│   agent     链接/卡券)                 用户余额)                        │
│   生成)                                                               │
│                                                                        │
│  ←──── 可追踪、可审计、可统计 ────→                                     │
└────────────────────────────────────────────────────────────────────────┘
```

### 2.2 核心业务规则

| 规则类型 | 说明 |
|---------|------|
| **面额类型** | 固定 Token 额度 / 百分比折扣 / 套餐兑换 / 模型权限解锁 |
| **适用对象** | 全部用户 / 新注册用户 / 指定用户组 / 指定代理商下级 |
| **使用限制** | 每人限用 1 次 / 同一 IP 限用 N 次 / 需最低消费门槛 |
| **有效期** | 固定截止日期 / 领取后 N 天内有效 / 永久有效 |
| **叠加规则** | 可与余额叠加 / 不可与其他优惠叠加 / 自动取最优 |
| **状态流转** | 待发放 → 已激活 → 已使用 → 已过期 / 已作废 / 已回收 |

### 2.3 典型营销场景

```
场景 A：新用户注册福利
  新用户注册 → 系统自动发放体验兑换码 → 用户激活 → 获得 1 万 Token 体验额度
  → 体验期内用完 → 弹出首充优惠窗口 → 付费转化

场景 B：渠道推广活动
  代理商 → 后台生成 1000 个 5 万 Token 兑换码 → 印在宣传物料/社群分发
  → 用户扫码/输入兑换 → 成为代理商下级用户 → 代理商获得佣金

场景 C：节日限时活动
  Admin → 创建"双11大促"活动 → 生成限量 5000 张 8 折折扣码
  → 倒计时 72 小时 → 先到先得 → 活动结束后未使用的自动失效

场景 D：用户裂变
  用户 → 分享邀请链接 → 好友注册并使用兑换码 → 双方各得 2 万 Token
  → 邀请排行榜 → 前 10 名额外奖励
```

### 3.3 交互流程

```
用户进入兑换页面
  ↓
输入兑换码 → 点击兑换
  ↓
前端校验：格式、是否已兑换过
  ↓
调 API → POST /user/codes/redeem
  ↓
后端处理：
  ① 校验兑换码是否存在、有效、未超量
  ② 校验用户资格（新用户专享？黑名单？）
  ③ 生成兑换操作日志
  ④ 划入 Token 余额（写入 balance_logs）
  ⑤ 更新兑换码使用计数
  ↓
返回结果 → 弹窗反馈
  ↓
用户可跳转至余额页面或继续使用
```

### 3.4 通知触达

| 触发时机 | 通知方式 | 内容 |
|---------|---------|------|
| 兑换成功 | 站内通知 + 可选邮件/短信 | "兑换码 3C***XK7P 已成功到账，+50,000 Token" |
| 兑换码即将过期 | 站内通知（到期前 3 天） | "您有一个兑换码将于 3 天后过期，内含 20,000 Token" |
| 收到赠送兑换码 | 站内通知 | "您的好友 xxx 向您赠送了一个兑换码，价值 10,000 Token" |

### 4.3 代理端核心业务规则

| 规则 | 说明 |
|------|------|
| **配额消耗** | 代理商生成兑换码时，从代理商账户冻结等值 Token 额度 |
| **使用后结算** | 用户使用兑换码后，实际从代理商账户扣除对应 Token |
| **未使用退款** | 兑换码过期后，冻结额度自动解冻回到代理商账户 |
| **成本价 vs 面值** | 代理商按成本价消耗，用户获得面值 Token，差价由平台承担（作为营销成本）|
| **下级用户归属** | 通过代理商兑换码注册的用户自动归入该代理商下级 |

| 列 | 业务含义 | Admin 可采取的动作 |
|----|---------|------------------|
| 发放量 | 该代理累计生成的兑换码总 Token | 判断是否超过合理范围 |
| 使用量 | 实际被用户兑换消耗的 Token | 使用率过低 = 营销效率差 |
| 冻结额度 | 已生成但未使用的 Token（含未过期+未使用的部分） | 长期冻结考虑回收政策 |
| 带动充值 | 被兑换用户后续的充值金额 | 判断该渠道的 C端转化质量 |
| 使用率 | 使用量÷发放量 | **核心 KPI**，<30% 需要预警 |

**管理动作：**
- 行内**查看详情** → 钻取到该代理的完整兑换明细
- **调整配额上限** → 对优质代理提高发放额度，对低效代理收紧
- **临时冻结** → 发现异常时一键暂停该代理的全部兑换码
- **标记风险等级** → 正常/观察/限制/冻结

┌──────────────────────────────────────────────────────────┐

│  │ ¥52,800  │ │ ¥38,200  │ │ ¥14,600  │ │ ¥86,200  │   │

│                                                           │
│  ┌──┬────────┬────────┬────────┬────────┬────────┬─────┐ │
│  │# │代理商  │消耗Token│消耗成本│带动营收│补贴占比 │ROI  │ │
│  ├──┼────────┼────────┼────────┼────────┼────────┼─────┤ │
│  │1 │渠道商A │ 120万  │¥12,000 │¥38,200 │¥2,400  │318% │ │
│  │2 │渠道商B │ 65万   │¥6,500  │¥22,500 │¥3,500  │346% │ │

| 财务术语 | 计算公式 | 说明 |
|---------|---------|------|
| 平台总成本 | Σ(代理消耗成本 + 平台补贴) | 平台为兑换码付出的总成本 |
| 代理消耗成本 | Σ(兑换码 Token × 成本单价) | 代理生成的码实际消耗部分 |
| 平台补贴 | Σ(面值 Token × 面值单价 - 消耗成本) | 面值超出成本价的部分 |
| 带动营收 | 被兑换用户后续充值总额 | 衡量兑换码的最终商业价值 |
| ROI | (带动营收 - 总成本) / 总成本 | 核心效率指标 |
| 补贴占比 | 平台补贴 ÷ 总成本 | 补贴过高说明代理在"薅平台" |

## 6. 双角色发码的财务与成本核算体系

> 本章聚焦 Admin 和 Agent 两个角色都发放兑换码时，**财务流如何分层设计**，确保资金链路清晰、成本归属准确、对账可追溯。

### 6.1 双角色发码的财务定位差异

```
特征              Admin 发码                   Agent 发码
─────────────────────────────────────────────────────────────────
成本承担方         平台 (营销费用)              代理商 (从账户扣)        
财务性质           运营支出                     预付费消耗 / 渠道成本
资金流             平台出钱 → 用户得 Token      代理冻资 → 用户得 Token

Agent 视角      —                           成本价消耗，面值补贴
平台视角          ¥X 营销投入                 ¥Y 成本损耗 + ¥Z 平台补贴
```

### 6.2 财务流全景图

#### 场景 A：Admin 发放兑换码

```
┌─────────────────────────────────────────────────────────┐
│  Admin 发码财务流                                        │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ① Admin 批量生成 50,000 Token × 1000 张                │
│     ├─ 平台账户：无资金变动（marketing_expense 暂记）     │
│     └─ 兑换码表：记录 created_by_type='admin'            │
│                                                         │
│  ② 用户兑换（假设成本单价 ¥0.10/千Token）                │
│     ├─ 用户余额：+50,000 Token                          │
│     ├─ balance_logs：type='redemption', source='admin'  │
│     ├─ 平台负债：+50,000 Token（用户预存款）              │

│                                                         │
│  ③ 用户消费使用 Token                                    │
│     ├─ 用户余额：-N Token                               │
│     ├─ 平台收入：按 API 调用实际产生收入                   │

│                                                         │

│     ├─ 平台成本：无（实际未发生）                          │

#### 场景 B：Agent 发放兑换码

```
┌─────────────────────────────────────────────────────────┐
│  Agent 发码财务流                                        │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ① Agent 预充值（或已有账户余额）                         │
│     ├─ Agent 支付 ¥1,000 → 余额 ¥1,000                  │

│                                                         │
│  ③ 用户兑换                                              │
│     ├─ Agent 冻结 → 扣除（¥5 → 实际消耗）                 │
│     ├─ Agent 可用余额：不变                               │
│     ├─ 用户余额：+50,000 Token                           │
│     ├─ balance_logs：记录 agent_id + agent_cost          │

│     ├─ Agent 冻结解冻：¥5 × 未使用数                      │
│     ├─ Agent 可用余额恢复                                 │
│     └─ 财务：无实际消耗                                  │
│                                                         │

### 6.7 财务核算的完整闭环

```
┌──────────────────────────────────────────────────────────────┐
│                   兑换码财务核算闭环                           │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  ① 发码阶段                                                  │
│     ├─ Admin 发码 → 计入营销预算（marketing_expense 预提）    │
│     └─ Agent 发码 → Agent 余额冻结（agent_balance_frozen）   │
│                                                              │
│  ② 使用阶段                                                  │
│     ├─ Admin 码消费 → 确认营销费用（实际发生的部分）          │
│     ├─ Agent 码消费 → 确认渠道成本（从冻结→实际扣除）        │
│     └─ 用户 Token 到账 → 确认平台负债（预收账款增加）         │
│                                                              │
│  ③ 消费阶段                                                  │
│     ├─ 用户实际 API 调用 → 确认主营业务收入                  │
│     └─ 归因分析 → 该兑换码用户后续产生的收入回溯              │
│                                                              │
│  ④ 结算阶段                                                  │
│     ├─ Agent 对账：期初余额 + 充值 - 消耗 - 冻结 + 解冻      │
│     ├─ 结算单生成 → Agent 确认/异议 → Admin 复核 → 锁定     │
│     └─ 发票流转 → 资金交割                                   │
│                                                              │
│  ⑤ 分析阶段                                                  │
│     ├─ ROI 分析（活动级 / 代理级 / 批次级）                  │
│     ├─ 预算执行率追踪                                        │
│     └─ 渠道质量评估 → 指导下周期资源分配                      │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 6.8 关键边界与风险

| 边界/风险 | 说明 | 对策 |
|-----------|------|------|
| **Agent 账户余额不足** | Agent 余额不够发码冻结 | 生成时实时校验，不足则拒绝 + 提示充值 |
| **面值 &gt; 成本价倒挂** | Agent 用成本价发面值券，平台补贴过高 | 设置补贴率上限告警（如 >90% 预警）| 
| **兑换码套利风险** | Agent 自注册账号兑换自己的码 | 风控告警机制（同一设备/IP 多账号兑换）|
| **多 Agent 串通** | 多个 Agent 联合刷量 | 按批次使用率 + IP 聚合分析 |
| **结算争议** | Agent 不认可结算单 | 异议流程：逐笔核对 → 追溯单码明细 → Admin 复核 |
| **预算超支** | Admin 发码超出营销预算 | 预算上限控制 + 超支审批流 |

### 7.3 兑换码编码规则

```
3C-A1B2C3D4E5F6
│  └─ 12 位随机字符（base32，排除易混淆字符）
└─ 前缀标识
```

- **字符集**：2-9、A-Z（排除 0/O、1/I/L、2/Z）= 30 字符空间
- **熵值**：30¹² ≈ 5.3×10¹⁷，完全不可枚举
- **前缀规则**：`3C-` 固定 + 可选活动标识（如 `SD`=双11 → `3C-SD-A1B2C3D4E5F6`）
- **校验位**：可选最后 1 位为校验位（Luhn mod 30）

## 10. 风控与安全（增强版）

### 10.1 兑换安全

| 措施 | 说明 |
|------|------|
| **防枚举攻击** | 同一 IP 连续错误 5 次 → 验证码锁定 30 分钟 |
| **防批量兑换** | 同一兑换码 1 分钟内超过阈值触发熔断 |
| **防重复兑换** | 幂等 ID 机制（请求唯一 ID + 服务端去重）|
| **码值不可猜** | crypto.randomBytes 生成 + base32 编码，完全不可预测 |
| **传输加密** | 兑换码全程 HTTPS，服务端存 Hash（前端可见明文）|
| **风控熔断** | 异常流量达到阈值 → 自动关闭兑换入口 N 分钟 |

### 10.2 业务风控规则

#### 用户级风控

| 规则 | 阈值 | 处置 |
|------|------|------|
| 同 IP 高频兑换 | >30 次/小时 | 告警 + IP 封禁 10 分钟 |
| 同设备多账号 | >3 账号/设备 | 标记 + 新账号兑换需短信验证 |
| 新注册秒兑大量码 | 注册 5 分钟内 >3 个 | 人工审核 + 降低单码面额 |
| 异地登录兑换 | 与历史 IP 不符 | 二次验证 |
| 黑产 IP | 已知代理/IDC/虚拟号码库 | 静默拦截 + 证据链记录 |

#### 代理级风控

| 规则 | 阈值 | 处置 |
|------|------|------|
| 单日生成量激增 | 日环比 ≥300% | 通知审核 + 临时降额 |
| 批次使用率极低 | 生成 7 天后 <10% | 渠道质量告警 |
| 多 Agent 同面额 | 3+ 代理同时相同面额 | 标记反串通 |
| 疑似自兑 | 同一设备兑换多个 Agent 码 | 冻结生成权限 |
| 补贴率过高 | 面值-成本补贴 >90% | 预警 + 限制生成 |

#### Admin 级风控

| 规则 | 阈值 | 处置 |
|------|------|------|
| 营销预算超支 | 超过预算 120% | 阻止继续生成 + 审批流 |
| 活动使用率低 | 活动过半 <20% | 建议调整策略 |
| 恶意 Admin 操作 | 批量作废/调价频率 | 审计二级复核 |

### 10.3 Agent 风险等级动态管理

```
┌────────────┐    ┌────────────┐    ┌────────────┐
│ 🟢 正常    │ →  │ 🟡 观察    │ →  │ 🔴 限制    │
│ 使用率≥70% │    │ 使用率30-70│    │ 使用率<30% │
│ 高配额     │    │ 维持现状   │    │ 降额+审查  │
└────────────┘    └────────────┘    └────────────┘
      ↑                                    │
      └────────────────────────────────────┘
               整改后评估
```

### 10.4 审计要求

- 所有创建/修改/作废操作记录审计日志
- 兑换记录**永久保存**（不可删除）
- 风控操作详细记录（触发规则 + 上下文快照）
- Admin 强制操作需短信/邮件二次确认
- 对账操作锁定后不可修改，仅可追加备注

## 11. 业务闭环验证（增强版）

### 11.1 双角色正向流程

```
┌─ Admin 发码流 ─────────────────────────────────┐
│  ① Admin 批量生成 → 预算预提                   │
│  ② 用户兑换 → 营销费用确认                    │
│  ③ 用户消费 → 主营业务收入                    │
│  ④ ROI 追踪 → 标记活动效果                    │
└───────────────────────────────────────────────┘

┌─ Agent 发码流 ─────────────────────────────────┐
│  ① Agent 预充值 → 账户余额                    │
│  ② 生成码 → 等额冻结                          │
│  ③ 用户兑换 → 冻结→扣除                      │
│  ④ 平台补贴 = 面值 - 成本价                   │
│  ⑤ 过期码 → 冻结解冻                          │
└───────────────────────────────────────────────┘
```

### 11.2 闭环检查清单

| 环节 | Admin 发码验证 | Agent 发码验证 |
|------|---------------|---------------|
| ✅ **创建** | 面额>0、有效期合理、预算充足 | 面额>0、有效期合理、**冻结余额充足** |
| ✅ **兑换** | 码状态、有效期、防重复、幂等 | 同左 + 校验 frozen 状态 |
| ✅ **入账** | Token 到账、balance_logs 记录 | 同左 + agent_balance_ledger 记录 |
| ✅ **成本** | marketing_expense 准确 | agent_cost + platform_subsidy 分开记录 |
| ✅ **结算** | — | 冻结解冻正确、对账单一致 |
| ✅ **统计** | ROI、预算执行率 | ROI、使用率、补贴率 |
| ✅ **审计** | 全程可追溯 | 全程可追溯 |
| ✅ **风控** | 异常拦截 | 代理级+用户级双重风控 |

### 11.3 异常场景与处置

| 异常 | 影响 | 处置方式 |
|------|------|---------|
| 兑换码有效期已过 | 用户无法使用 | 明确提示过期日期，引导查看其他活动 |
| 兑换码使用次数耗尽 | 用户无法使用 | 提示已领完，建议关注后续活动 |
| 用户已兑换过 | 重复提交 | 提示已兑换，展示兑换记录和到账时间 |
| 代理余额不足 | 无法生成 | 提示充值，提供快捷充值入口 + 金额推荐 |
| 黑产拦截 | 黑产无法兑换 | 静默拒绝（不提示原因，不让黑产获知规则） |
| 网络错误/超时 | 状态不确定 | 幂等 ID 保证，前端可安全重试 |
| 对账不一致 | 财务差异 | 逐笔追溯 → 比对两方 → Admin 复核落差原因 |
| 风控误杀 | 正常用户无法兑换 | 申诉入口 → 客服工单 → 人工审核解封 |
| 预算超支 | 无法继续生成 | 超支审批流 → Super Admin 确认 |

### 11.4 扩散场景

#### 兑换码转赠（可选）

用户 A 获得一个面值 50,000 的兑换码 → 转赠给用户 B：

```
流程：A 发起转赠 → A 的兑换码状态变为 transferred
     → B 收到通知 → B 确认领取 → 码绑定到 B
     → 过期未领 → 退回给 A
```

#### 第三方外部集成（可选）

```
外部系统 → POST /api/v1/external/codes/generate (需 API Key)
          → 返回兑换码列表
          → 自定义回调 URL：用户兑换后通过 webhook 通知外部系统
```

#### 定时自动发码（可选）

```
系统任务 → 每天 00:00 检查 scheduled_codes 表
          → 到点的自动激活/发送
          → 生日福利/节日活动/注册满 N 天奖励
```

### 12.4 关键决策点

| 阶段 | 决策点 | 影响 |
|------|--------|------|
| Phase 0 结束时 | 兑换码格式是否定稿？前缀规则是否够用？| 改动前缀影响存量码 |
| Phase 1 结束时 | Agent 冻结机制是实时扣还是预扣？| 影响代理资金周转体验 |
| Phase 2 结束时 | 成本单价的定价策略（固定/浮动/阶梯）| 影响 finance_cost_records 计算逻辑 |
| Phase 3 结束时 | 结算周期（按月/按周/按批次触发）| 影响结算模块架构 |
| Phase 4 开始前 | 是否开放给第三方平台集成？| 决定是否需要 API Key 管理 |

### 12.5 风险和缓冲

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| Agent 冻结余额机制与现有余额系统冲突 | 中 | 高 | Phase 1 先做简单的预扣，Phase 2 再优化为冻结模式 |
| 兑换码被批量扫描 | 高 | 中 | Phase 0 就加入 IP 频率限制 |
| 对账逻辑复杂导致结算滞后 | 中 | 中 | 先上线手工确认版对账，再自动化 |
| 前端页面大量增加影响加载性能 | 低 | 中 | 兑换码模块按需加载（lazy）|
