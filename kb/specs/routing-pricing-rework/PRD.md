# 路由调度与定价体系改造 — 产品需求文档

> **项目**：3cloud (3C) AI Token 聚合平台  
> **版本**：v1.0  
> **状态**：初稿  
> **日期**：2026-07-29  
> **编写**：产品团队

---

## 1. 项目背景与目标

### 1.1 背景

3cloud 平台已对接 40+ 模型供应商、130+ 模型，日均处理大量 API 请求。现有路由调度和定价体系的局限逐渐暴露：

- 路由只按基础售价排序，未考虑供应商实时负载、延迟波动、错误率
- 模型可见性只有"启用/禁用"二值，缺少"仅路由可用但不公开"的中间态
- Key 分组折扣虽已实现，但路由决策时未纳入实际结算价计算
- 并发上限硬编码，无法根据实时表现动态调整
- 连接缺乏复用，每次请求新建 TCP 连接，延迟开销大

### 1.2 目标

| 目标 | 指标 |
|------|------|
| 降低用户调用延迟 | 平均延迟降低 ≥15% |
| 提升路由决策质量 | 错误率 ≥5% 的供应商自动降低权重 |
| 实现动态并发管理 | 并发上限根据负载自动调整 |
| 模型可见性精细化 | 三级控制：公开/内部/禁用 |
| 基于实际结算价排序 | 路由选择纳入 Key 折扣，选择真实最低价 |

## 3. 用户角色与场景

### 3.1 角色定义

| 角色 | 平台权限 | 核心关注 |
|------|---------|---------|
| 普通用户 | 用户端 | 调用稳定性、延迟、价格透明 |
| 代理商 | 代理端 | 客户体验、佣金最大化 |
| 运营管理员 | 管理后台 | 供应商管理、定价配置、成本控制 |
| 系统管理员 | 管理后台 | 全局策略配置、模型可见性控制、系统调优 |
| 供应商 | 供应商端 | 查看调用统计、Key 管理 |

### 3.2 用户场景

**场景 A：模型下架但路由仍可用**
> 某模型因上游价格波动计划下架，但已购买包月的用户仍需服务。  
> 管理员将该模型 visibility 设为 `internal`，用户端不再展示，但路由引擎可将其作为降级备选。

**场景 B：高峰期自动分流**
> 某供应商高峰期延迟飙升 2 倍、错误率升至 8%。  
> 负载均衡器自动计算综合分，将该供应商 40% 流量分流到其他供应商，同时下调并发上限。

**场景 C：Key 折扣纳入路由决策**
> 供应商 A 基础售价 ¥0.010/千Token，供应商 B 基础售价 ¥0.012/千Token。  
> 但用户持有的 Key B 有 8 折折扣，实际 ¥0.0096/千Token，路由应选 B。

**场景 D：大批量 Key 上架审核**
> 供应商自助上传 50 个 Key，状态默认 `pending_review`。  
> 管理员在资源池列表批量通过，系统自动完成连通性测试。

## 4. 模块一：多厂商资源调度（6 项）

### 4.1 负载感知分流系统

**现状**：路由选择只依赖基础售价排序和熔断器（四级状态），无中间状态分流。  

**目标**：基于实时性能指标（并发饱和度、延迟比、错误率）计算综合分，按分数段执行分流。

**需求**：

| 需求编号 | 需求描述 | 优先级 |
|---------|---------|--------|
| RS-1 | 每 30 秒从 call_logs 统计各供应商最近 5 分钟/1 小时的延迟、错误率 | P0 |
| RS-2 | 计算综合分 = 并发饱和度×40% + 延迟比×35% + 错误率×25% | P0 |
| RS-3 | 根据综合分映射分流比例：≤0.3 不分流，0.3-0.5 分流 0%-10%，0.5-0.7 分流 10%-30%，0.7-0.9 分流 30%-60%，>0.9 分流 60% | P0 |
| RS-4 | 高分流（>50%）的供应商候选自动移除，轻度分流降低权重 | P0 |
| RS-5 | 分流策略仅作用于 lowest_price 和 adaptive 路由模式 | P0 |

**规则说明**：

```
综合分 < 0.3: 正常路由，不分流
综合分 0.3~0.5: 按比例降低权重（最多降 10%）
综合分 0.5~0.7: 分流 10%-30% 流量
综合分 0.7~0.9: 分流 30%-60% 流量
综合分 > 0.9: 分流 60% 流量，接近熔断
```

### 4.2 动态并发上限管理

**现状**：`forward.ts` 中并发上限硬编码为 `VENDOR_CONCURRENT_DEFAULT`（50），手动调整需改代码重启。  

**目标**：根据供应商实时表现自动调整并发上限，范围 10-200。

**需求**：

| 需求编号 | 需求描述 | 优先级 |
|---------|---------|--------|
| RS-6 | 初始并发上限从 system_configs 读取 vendor_concurrent_default（默认 50） | P0 |
| RS-7 | 每 5 分钟评估一次，按延迟比和错误率调整上限 | P1 |
| RS-8 | 良好状态（延迟比<1.2 且错误率<1%）上限 ×1.1（上限 200） | P1 |
| RS-9 | 负载高（延迟比>1.5 或错误率>5%）上限 ×0.8（下限 10） | P1 |
| RS-10 | 错误率 >10% 联动熔断器，记录 vendorModel 失败 | P1 |

### 4.3 连接池复用

**现状**：每次请求使用 Fastify 自带 HTTP 客户端，无连接池复用，每次新建 TCP 连接。  

**目标**：对每个供应商 Endpoint 维持 HTTP Keep-Alive 连接池。

**需求**：

| 需求编号 | 需求描述 | 优先级 |
|---------|---------|--------|
| RS-11 | 使用 undici Pool 或 http.Agent 维护每个供应商 Endpoint 的连接池 | P1 |
| RS-12 | 连接池大小 = min(maxConcurrent, 20)，支持连接复用 | P1 |
| RS-13 | 空闲 30 秒后自动关闭连接 | P2 |
| RS-14 | 连接池状态可监控（活跃/空闲连接数） | P2 |

### 4.4 请求队列等待

**现状**：并发超限直接返回 429 Too Many Requests。  

**目标**：短等待排队替代直接 429。

**需求**：

| 需求编号 | 需求描述 | 优先级 |
|---------|---------|--------|
| RS-15 | 并发超限时，请求进入等待队列（最多 500ms） | P2 |
| RS-16 | 等待期间有可用令牌则出队继续，超时则返回 429 | P2 |
| RS-17 | 等待队列上限 100 个请求，超限直接拒绝 | P2 |

## 5. 模块二：定价策略（5 项）

### 5.1 实际结算价路由排序

**现状**：lowest_price 策略按 `vendor_models.sell_price_input` 排序，Key 折扣（keySellPriceInput）在路由选择后才解析。  

**目标**：路由选择时预先解析所有候选 Key 分组，按实际结算价排序。

**需求**：

| 需求编号 | 需求描述 | 优先级 |
|---------|---------|--------|
| PR-1 | 路由选择前预先解析所有候选厂商的 Key 分组 | P0 |
| PR-2 | 实际结算价 = Key 折扣价（如有）或 vendorModel 基价 | P0 |
| PR-3 | 按 effectivePriceInput ASC 重新排序候选 | P0 |
| PR-4 | 预解析 Key 分组不更新统计（避免重复计数） | P0 |

### 5.2 vendor_models 定价策略配置

**现状**：vendor_models 只有固定的卖价和买价字段，缺乏定价策略标识。  

**目标**：每个 vendorModel 可配置定价策略，灵活对接不同供应商的计价方式。

**需求**：

| 需求编号 | 需求描述 | 优先级 |
|---------|---------|--------|
| PR-5 | vendor_models 新增 pricing_strategy 字段：cost_plus / fixed / auto / blocked | P1 |
| PR-6 | cost_plus = 按买价+固定加价率计算卖价 | P1 |
| PR-7 | fixed = 固定卖价（现有模式） | P1 |
| PR-8 | auto = 智能定价建议（根据市场价格自动匹配） | P2 |
| PR-9 | blocked = 该型号不上架（即使 status=true） | P1 |

### 5.3 配置变更历史

**现状**：定价配置修改无审计记录。  

**目标**：所有定价相关配置变更写入 `priceChangeHistory` 表（已有表结构）。

**需求**：

| 需求编号 | 需求描述 | 优先级 |
|---------|---------|--------|
| PR-10 | 卖价/买价/定价策略变更自动记录到 priceChangeHistory | P1 |
| PR-11 | 变更记录包含：操作人、变更字段、旧值、新值、时间 | P1 |

## 6. 模块三：Key 分组管理（4 项）

### 6.1 智能 Key 选择

**现状**：Key 选择策略（round_robin / weighted / failover / priority）只考虑静态权重和轮询。  

**目标**：引入多维评分，动态选择最优 Key。

**需求**：

| 需求编号 | 需求描述 | 优先级 |
|---------|---------|--------|
| KG-1 | 新策略 `intelligent`：综合评分 = weight + (1-error_rate) + (1-saturation) + (1-latency_rank) | P1 |
| KG-2 | error_rate / saturation / latency_rank 从负载均衡器的实时统计获取 | P1 |
| KG-3 | 系统配置中有可管理的开关，可启用/禁用此新策略 | P2 |

### 6.2 资源池批量管理

**现状**：新增 Key 需逐个配置，无批量操作。  

**目标**：支持供应商自助批量上传 + 管理员批量审核/上架。

**需求**：

| 需求编号 | 需求描述 | 优先级 |
|---------|---------|--------|
| KG-4 | 供应商端：批量上传 Key（CSV/手动输入），导入后状态 = pending_review | P1 |
| KG-5 | 管理员端：资源池列表支持批量筛选（状态、供应商、Key 分组） | P1 |
| KG-6 | 批量上架：选中多个 Key → 批量审核通过 → 自动连通性测试 | P1 |
| KG-7 | 连通性测试失败时标记异常，提供失败原因 | P1 |

## 7. 模块四：模型可见性控制（4 项）

### 7.1 三级可见性

**现状**：`models.status` 只有 true/false 二值。  

**目标**：改为三级枚举：public / internal / disabled。

**需求**：

| 需求编号 | 需求描述 | 优先级 |
|---------|---------|--------|
| MV-1 | models 表 status(boolean) → visibility(public/internal/disabled) | P0 |
| MV-2 | public：用户可见可用，路由正常选择 | P0 |
| MV-3 | internal：用户不可见不可用，路由引擎可作为降级备选 | P0 |
| MV-4 | disabled：完全不可用，路由引擎跳过 | P0 |
| MV-5 | 迁移脚本：status=true → public, status=false → disabled | P0 |

### 7.2 可见性在路由中的表现

| 调用方 | public | internal | disabled |
|--------|--------|----------|----------|
| 用户 API（/v1/chat） | ✅ 可选 | ❌ 不可选 | ❌ 不可选 |
| 路由引擎（降级备选） | ✅ 可用 | ✅ 可用 | ❌ 不可用 |
| 模型列表 API | ✅ 展示 | ❌ 不展示 | ❌ 不展示 |
| 管理后台 | ✅ 展示 | ✅ 展示 | ✅ 展示 |

### 7.3 管理后台 UI

**需求**：

| 需求编号 | 需求描述 | 优先级 |

## 8. 财务模块影响分析

### 8.1 影响总览

| PRD 模块 | 影响程度 | 说明 |
|---------|---------|------|
| 模型可见性 | 无影响 | 不涉及价格/计费/结算 |
| 负载感知分流 | 无影响 | 仅影响路由决策，不改变计价逻辑 |
| 实际结算价排序 | 间接影响 | 路由选择参考 Key 折扣价做决策，但**实际计费价格不变**（计费仍用选定 vendorModel 的 sell_price） |
| 定价策略配置 | 直接影响 | pricing_strategy 影响卖价计算方式；priceChangeHistory 需要明确写入时机和字段映射 |
| 连接池/动态上限/队列 | 无影响 | 纯性能优化，不触达财务层 |
| 智能 Key 选择 | 间接影响 | 改变调用分布，影响利润统计的数据源分布 |
| 资源池批量管理 | 无影响 | 纯管理流程 |

### 8.2 定价策略变更 → priceChangeHistory 写入规范

`priceChangeHistory` 表已有，PRD 需明确写入时机和字段映射：

```
触发时机：
  1. 管理员手动修改 vendor_models.sell_price_input/output
  2. 管理员修改 vendor_models.sell_cost_input/output（买价）
  3. 管理员修改 vendor_models.pricing_strategy
  4. 全局定价乘数变更（system_configs.pricing_multiplier）
  5. Key-Model 交叉价变更（vendor_key_group_model_prices）

字段映射：
  operatorId   → 当前登录管理员 user_id
  changeType   → 'price_change' | 'cost_change' | 'strategy_change' | 'multiplier_change' | 'key_price_change'
  targetType   → 'vendor_model' | 'system_config' | 'key_group_item'
  targetId     → 对应表的主键 ID
  beforeValue  → 变更前的数值（JSON 字符串，含字段名和旧值）
  afterValue   → 变更后的数值（JSON 字符串）
  reason       → 管理员填写的变更原因（可选）
```

### 8.3 利润统计兼容性

`finance_profit_records` 表按 `vendorModelId` 汇总利润，不受路由排序变化影响，因为：

- 路由排序改变的是**哪个候选排在前面**，不改变**最终选定 vendorModel** 的计费价格
- 选定后计费仍走现有 billing 流程，`call_logs` 记录的价格不变
- 利润统计的数据源（`call_logs`）不受影响

### 8.4 计费一致性保障

- **实际结算价仅用于路由排序**，不直接作为计费依据
- 路由选定的 vendorModel 后，计费流程不变（仍使用 `vendorModels.sell_price_input/output`）
- Key 折扣价（`keySellPriceInput`）在 billing 层已有独立处理逻辑，路由层排序不影响最终账单

### 8.5 财务审计补充

- `priceChangeHistory` 变更记录需在管理后台「审计日志」中有对应条目
- 定价策略变更（特别是 auto→fixed/cost_plus 切换）需要二次确认弹窗
- 全局定价乘数变更后，建议触发一次利润重算提示

### C. Key 分组智能策略评分公式

```
score = weight_normalized * 0.3
      + (1 - error_rate) * 0.3
      + (1 - saturation) * 0.2
      + (1 - latency_rank_normalized) * 0.2
```

- weight_normalized = weight / max_weight_in_group
- latency_rank = 该 Key 使用的 vendorModel 的延迟排名
- saturation = 并发饱和度
