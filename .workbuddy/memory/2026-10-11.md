### 排查经验（值得记住）
1. **数字对不上先查时区**。SQL 算出 8724.53 而接口返回 7423.89，差 1300 元，
   根因是 `timestamp without time zone` + Drizzle UTC 序列化。**不报错、只是数字错**。
2. **同库两种时间语义并存**：`consumption_records` 是 `without time zone`，
   而 `alerts`/`monitoring_rules`/`conversation_context_records` 是 `with time zone`。不可套用同一构造函数。
3. **测试失败先分清「代码回归」与「环境数据依赖」**。告警中心掉到 21/23 时，
   通过 `git status`（告警模块未改动）+ 查引擎数据源窗口内 0 条留痕 + 手动造数后 28/28，
   三步确认是环境依赖而非回归。
4. **测试脚本路由要带 `/app` 前缀**（console 挂载点）。写成 `/admin/xxx` 会 404 到 SPA 兜底页，
   表现像「前端没渲染新元素」，实为路径错误——曾据此误判为 HMR 问题。
5. **`Number('') === 0` 而非 NaN**，解构默认值 `= 1970` 只对 undefined 生效，脏输入会得到「公元 0 年」。

## 3cloud — 生产演示数据 100 万条

提交 `2735ced`，已推送至 `origin/main`。

### 过程
1. **修正 `seed-demo-users.sql` 字段错误**（尚未执行，无影响）：`users.name` 是 NOT NULL
   但脚本未提供；`balance` 字段在 `users` 表**不存在**，余额在 `customer_balances`。
   生产实况核对后重写。顺带确认 `api_keys.key_prefix` 只有 varchar(12)。
2. **发现生产 `consumption_records` 是 RANGE 分区表**（本地以为不是）：只有 5 个分区
   （2026_10~2027_01 + default），180 天窗口会有 6/10 数据落进 default。
   → 新建 `prepare-partitions.sql` 补 6 个月度分区；default 里既有基础数据
   `req_demo_12`(2026-08-01) 需先暂存再建分区（PostgreSQL 会校验 default 有无落在新范围的行）。
3. 用户数从 20提到 **60**：100 万 / 20 = 人均 5 万条，但「用户用量 Top N」只有 20 行仍偏少。
   60 人 ≈ 人均 1.7 万条、落180 天窗口，日均 90 条/人，榜单形态可信。
4. 分 4 批 × 25 万插入，单批 6~7 秒，全程内存充裕。

### 生产验证（全部通过）
- **100 万条 / 60 用户 / 7 个月（2026-04~10）均匀分布**（每月 8~17 万条）
- **缺归属 0 条、未归因成本 ¥0** — 不掩盖本地那个 99% 无归属的真实缺陷
- 全部落在正确月度分区，**default 分区兜底 0 条**
- 库体积 18MB → 350MB，内存可用 688MB（造数前 791MB），无压力
- 对账端点 `supplier_id=1&period=2026-09` → `status:"matched"`、`diff=0`
- `/list` 端点 16.7 万条/月汇总 **169ms**，接口合计 1924.7782 vs SQL 1924.7783
  （差 0.0001 是 numeric 逐行累加尾差）
- ERROR 日志无新增（仅 9/7 两条历史 Redis NOAUTH）

### 3 个「不报错但结果错」的坑（已写进脚本注释）
1. **分批 offset 切分必须无重叠覆盖 `[0,total)`**。写成 0/10000/260000/510000/760000
   会溢出成 101 万条——不报错，只是数字不对。正确切分应为 0/250000/500000/750000。
2. **幂等保护不能查全表**，只查本批区间，否则第 2 批被上一批存量误拦，分批根本跑不下去。
   另外 psql 变量在 `$$` 引号内替换行为版本不一致，用 `\gset` + `\if` 避开。
3. **时间轴必须夹逼到当下**。`(random()*interval '1 day')` 抖动让末尾约 1% 溢出到未来
   （实测 10,608 条），"本月至今"趋势图会失真。已加 `LEAST(..., 今天 23:59:59)`。

### 顺带修正
生产 API 路径是 `/api/v1/...`（不是 `/api/...`），登录响应字段是 `accessToken`
（不是 `token`）——之前 404/401 误判源于此，端点本身没问题。
