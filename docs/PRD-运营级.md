## 一、平台定位与商业运营模型

### 1.1 平台定义

3cloud 是一个 **AI API 中间层平台**。本质是：从多家上游模型供应商批量采购 API 能力，通过智能路由和精细计费系统，转售给下游开发者和企业用户，同时提供多级分销（代理商体系）、全链路监控告警、安全风控和运营管理工具。

### 1.2 商业模型

| 角色 | 行为 | 收入/价值 | 对平台的贡献 |
|------|------|----------|-------------|
| **平台** | 从供应商采购 → 加价/抽佣转售 | 赚取采购价与售价之间的差价 + 代理商佣金抽成 | — |
| **供应商** | 提供模型 API 能力 | 通过平台触达更多终端用户 | 提供核心算力产品 |
| **一级代理** | 发展名下用户和子代理 | 赚取用户消费的佣金分成 | 带来用户流量和消费 |
| **子代理** | 隶属于一级代理发展用户 | 赚取用户消费的佣金分成 | 扩展用户触达面 |
| **企业用户** | 集中管理团队 API 消费 | 统一计费、审计、权限管理 | 高价值稳定消费 |
| **开发者** | 使用 API Key 调用模型 | 一站式接入多模型、免去逐一签约 | 最广泛的用户基础 |

### 1.3 核心商业指标（运营 KPI）

| 指标名称 | 定义 | 采集方式 | 运营意义 | 预警阈值 |
|---------|------|---------|---------|---------|
| 日活跃用户 (DAU) | 每天发起至少 1 次 API 调用的独立用户数 | `call_logs.user_id` 去重计数 | 衡量平台日活健康度 | 连续 3 天下降 > 10% |
| 日调用量 | 全天 API 请求总数 | `call_logs` 计数 | 系统负载和营收来源 | 增长率 > 100%/周 需扩容 |
| 月流水 (MRR) | 月度用户消费总额 | `consumption_logs` 按月聚合 | 平台营收核心指标 | 月环比下降 > 15% |
| 毛利率 | (用户收入 - 供应商成本) / 用户收入 × 100% | 财务模块自动计算 | 平台盈利能力 | < 15% 需调整定价 |
| 用户留存率（7日） | 注册后第 7 天仍有调用的用户 / 注册总数 | 用户分析模块 | 产品粘性 | < 20% 需优化 Onboarding |
| 用户留存率（30日） | 注册后第 30 天仍有调用的用户 / 注册总数 | 用户分析模块 | 长期价值判断 | < 10% 需调整运营策略 |
| 代理活跃度 | 近 30 天名下用户有消费的代理 / 总代理数 | 代理模块 | 分销体系健康度 | < 50% 需代理激励 |
| Key 使用率 | 已创建 Key 中近 7 天有调用的占比 | `api_keys` 关联 `call_logs` | Key 闲置率监控 | < 40% 需提醒用户清理 |
| 供应商健康度 | 各供应商 API 可用率（最近 24 小时） | 健康检查模块 | 服务质量监控 | < 99% 触发告警 |
| 告警收敛率 | 真实告警 / 总告警数 × 100% | 告警模块 | 告警质量、避免告警疲劳 | < 60% 需调整规则阈值 |
| 自助结算率 | 代理商自助确认结算的比例 | 结算模块 | 运营人力投入 | < 70% 需优化结算流程 |
| 客单价 (ARPU) | 月总消费 / 月活跃用户数 | 财务模块 | 用户价值分层 | 连续 3 月下降需营销刺激 |

### 1.4 用户分层与运营策略

| 用户分层 | 定义 | 占比（典型） | 运营策略 |
|---------|------|------------|---------|
| **种子用户** | 当月消费 > ¥1000 | ~5% | 专属客户经理、优先技术支持、专属折扣 |
| **活跃用户** | 当月消费 ¥100-1000 | ~15% | 定期推送用量报告、活动通知 |
| **普通用户** | 当月消费 ¥10-100 | ~30% | 邮件营销、满赠活动 |
| **休眠用户** | 当月有登录但无消费 | ~25% | 推送模型更新、优惠券唤醒 |
| **流失用户** | 注册超过 30 天且近 30 天无登录 | ~25% | 召回邮件、新模型上线通知 |

### 2.1 角色与权限体系

#### 2.1.1 角色矩阵

| 角色标识 | 等级 | 定位 | 权限概览 | 人数限制 | 典型任命场景 |

| `admin` | L4 | 运营管理员 | 除财务放款/系统密钥外的全部管理权限 | 按需 | 日常运营负责人 |
| `finance` | L4 | 财务岗 | 财务数据查看、充值审核、提现初审、发票管理 | 1-5 人 | 出纳、会计 |
| `auditor` | L4 | 审计岗 | 日志只读权限、审计报表查看 | 1-3 人 | 合规审计 |
| `operator` | L4 | 运营岗 | 活动/公告/内容/邮件模板管理 | 1-5 人 | 运营专员 |
| `security` | L4 | 安全岗 | 安全事件/风控规则/实名审核/封禁管理 | 1-3 人 | 安全工程师 |
| `agent_mgr` | L4 | 代理管理岗 | 代理审核、佣金配置、结算审批 | 1-3 人 | 渠道经理 |

#### 2.1.3 多管理员协作与操作审计

**操作日志记录内容**（每条记录必须包含）：

| 字段 | 说明 | 示例值 |
|------|------|--------|
| `operator_id` | 操作人用户 ID | `u_10086` |
| `operator_name` | 操作人昵称 | `张三` |
| `operator_ip` | 操作人来源 IP | `117.78.2.66` |
| `action` | 操作类型 | `user.balance.adjust` |
| `target_type` | 操作对象类型 | `user` |
| `target_id` | 操作对象 ID | `u_10087` |
| `before_value` | 操作前值（敏感操作必填）| `{"balance": 500.00}` |
| `after_value` | 操作后值（敏感操作必填）| `{"balance": 300.00}` |
| `reason` | 操作理由 | `用户申请退款调整` |
| `result` | 操作结果 | `success` / `failed` |
| `timestamp` | 操作时间 | `2026-07-26 11:30:00` |

**敏感操作列表**（必须记录前后值 + 需二次确认）：

```
1. 用户余额调整（加/减）
2. 提现审核通过/拒绝
3. 充值订单补单
4. 用户角色变更
5. 系统配置修改
6. 供应商状态切换（在线→离线）
7. 模型价格变更
8. API Key 禁用/删除
9. 代理商佣金率修改
10. 活动预算修改
```

**敏感操作审批流**：

```
操作发起 → 自动检测是否为敏感操作
   ├── 否 → 直接执行，记录日志
   └── 是 → 二次确认弹窗（展示操作内容和"确认执行"按钮）
       ├── 确认 → 执行
       └── 取消 → 不执行
       
超阈值操作（如单次余额调整 > ¥1000）：
   → 记录日志
   → 自动发送通知给 super_admin
   → 需另一名 admin 确认后才生效
```

- 余额即将耗尽时，卡片的"立即充值"按钮放大突出

##### 区域 2：核心指标卡片

**字段规格**

| 卡片 | 主数值 | 辅助信息 | 对比维度 | 点击跳转 |
|------|-------|---------|---------|---------|
| 今日调用次数 | `COUNT(call_logs)` 当日 | 成功/失败数 | 环比昨日变化率 | `/console/logs?range=today` |
| 今日 Token 消耗 | `SUM(tokens)` 当日 | 输入/输出拆分 | 环比昨日变化率 | `/console/stats?range=today` |
| 今日消费金额 | `SUM(cost)` 当日 | 月累计消费 | 环比昨日变化率 | `/console/transactions?range=today` |
| 账户余额 | `users.balance` | 昨日余额变化 | 昨日余额 | `/console/recharge` |

**变化率展示逻辑**

```
变化率 = (今日值 - 昨日值) / 昨日值 × 100%
  ├── 正增长：↑ 绿色文字（调用量/Token/消费增长是好事）
  ├── 负增长：↓ 红色文字
  └── 昨日值为 0：展示 "—"（不计算变化率）
```

**边界条件**

- 数据加载失败时：卡片展示 `--`，卡片右下角显示"数据加载失败"灰色小字
- 无数据（新用户）：卡片展示 `0`，变化率显示 `—`
- 数值超过 9999 时：转换为 K/M 单位（如 12500 → "12.5K"）

**运营配置**

| 配置项 | 说明 |
|-------|------|
| 是否展示免费额度消耗 | `site_configs.show_free_quota` |
| 对比基准（昨日/上周同期/上月同期）| `site_configs.default_compare_period` |

##### 区域 3：额度使用进度条

**字段规格**

| 字段 | 类型 | 说明 |
|------|------|------|
| 总额度 | decimal | 用户的有效配额上限 |
| 已用量 | decimal | 当月已消耗量 |
| 使用率 | int | 已用量 / 总额度 × 100% |
| 剩余额度 | decimal | 总额度 - 已用量 |
| 预估可用天数 | int | 剩余额度 / 日均消耗量（日均消耗量 = 近 7 天总消耗 / 7）|

**进度条状态逻辑**

```
使用率 < 60%：绿色进度条，无提示
使用率 60-80%：绿色进度条，右端显示 "剩余 ¥XX"
使用率 80-95%：黄色进度条，显示 "已用 80%，剩余 ¥XX"
使用率 >= 95%：红色进度条，显示 "额度即将耗尽，立即充值 →"
使用率 = 100%：红色进度条，显示 "额度已用完，立即充值 →"（按钮闪烁）
```

**边界条件**

- 用户无额度限制（`user_quotas` 未设置）：不显示进度条组件，改为显示"无限制"标识
- 日均消耗量为 0（新注册/无调用）：预估可用天数展示 "—"
- 余额为 0 且额度已用完：进度条满红 + "账户已欠费"遮罩

**运营策略**

- 额度 > 80% 时：系统自动触发余额不足通知
- 额度 > 95% 时：在通知基础上，增加邮件通知

##### 区域 5：Token 消耗趋势图

**图表配置**

| 参数 | 默认值 | 可选值 |
|------|-------|-------|
| 时间范围 | 近 7 天 | 24h / 7d / 30d / 自定义 |

**对比基准叠加规则**

- 开启对比后，用虚线渲染对比周期的趋势
- 对比周期 = 当前时间范围 - 当前时间范围长度
- 例如：7 天对比 → 显示前 7 天的数据虚线

**数据导出**

- 图表右上角下载按钮：导出 PNG / SVG 图片
- 原始数据导出：CSV（包含每条数据和对比数据）

##### 区域 11：成本预测卡片（P1）

**预测算法**

```
预测月消费 = 已消费金额 + (日均消费 × 剩余天数)

日均消费 = 近 30 天总消费 / 30
  如果用户注册不足 30 天：日均消费 = 注册以来总消费 / 注册天数
  如果用户注册不足 7 天：不展示预测（"数据不足，暂无法预测"）

余额耗尽天数 = 当前余额 / 日均消费
  如果日均消费为 0：展示 "—"
  如果余额为 0：展示 "已耗尽"
```

**展示内容**

```
预计本月消费 ¥890.50
已消费 ¥450.20 | 剩余 15 天 | 日均 ¥30.01

余额 ¥200.00 | 预计可用 6.7 天
⚠️ 余额将在 7 天内耗尽，建议立即充值
```

**预警阈值**

| 可用天数 | 展示样式 | 附加操作 |
|---------|---------|---------|
| > 30 天 | 绿色，正常显示 | 无 |
| 15-30 天 | 蓝色，正常显示 | 无 |
| 7-14 天 | 黄色，显示"即将耗尽" | "查看充值优惠"按钮 |
| 3-6 天 | 红色，显示"余额不足" | "立即充值"按钮（放大） |
| < 3 天 | 红色闪烁，显示"余额即将耗尽" | "紧急充值"按钮（高亮） |
| 已耗尽 | 灰色遮罩，显示"余额已用完" | 仅展示"立即充值" |

## 三、代理商体系（精化摘要）

### 3.1 代理商层级与权益

| 层级 | 准入条件 | 权益 | 默认佣金率 | 审核流程 |
|------|---------|------|-----------|---------|
| 预备代理 | 注册+实名 | 可查看佣金规则，不能提现 | 无 | 自动 |
| 一级代理 | 实名+资质审核 | 全功能代理面板、自定义佣金、可提现 | 10% | agent_mgr 审核 |
| 高级代理 | 月调用 > 100 万 Token | 专属客户经理、优先支持、阶梯佣金 | 12-18% | super_admin 审批 |
| 子代理 | 由一级代理创建 | 管理名下用户 | 由上级代理配置 | 上级代理 |

### 3.2 代理佣金规则配置

**佣金计算方式**

| 方式 | 公式 | 适用场景 |
|------|------|---------|
| 固定比例 | 用户消费 × 佣金率 | 通用场景 |
| 阶梯比例 | 月消费 ¥0-1000: 5%, ¥1000-5000: 8%, >5000: 12% | 激励大代理 |
| 固定金额 | 每 Token ¥X 固定佣金 | 高利润模型 |
| 混合 | 按模型分别设置不同佣金率 | 精细运营 |

**规则配置界面**

```
┌─ 佣金规则配置 ──────────────────────────┐
```

#### 4.3.4 Key 资源池 `/admin/vendor-key-groups`（P2）

**为什么需要 Key 资源池**

平台在同一个供应商处可能有多个 API Key，例如 DeepSeek 购买了 5 个 Key。直接将所有 Key 配置为同等地位会导致：
- 无法精细控制哪个 Key 接收多少流量
- 某个 Key 异常时难以快速切换
- 不同采购价格的 Key 无法区分定价

Key 资源池解决以上问题。

**资源池分组规格**

| 字段 | 说明 |
|------|------|
| 分组名 | 如 "高优先级组" / "普通组" |
| 所属供应商 | 关联到具体供应商 |
| 权重 | 整个分组的流量权重 |
| 定价覆盖 | 可独立于全局定价 |
| 状态 | 启用/禁用 |

**分组内的 Key 管理**

```
组名：高优先级组（权重 3）
Key 列表：
  Key A (sk-xxxx1)    权重 5    状态 启用  今日调用: 1234
  Key B (sk-xxxx2)    权重 3    状态 启用  今日调用: 987
  Key C (sk-xxxx3)    权重 2    状态 熔断  今日调用: —

[添加 Key 到分组] [移除] [测试连通性]
```

**加权轮询算法**

```
请求分配到组"高优先级组"时，组内有 Key A/B/C：
权重之和 = 5 + 3 + 2 = 10
Key A 接收 5/10 的请求
Key B 接收 3/10 的请求
Key C 接收 2/10 的请求（但当前熔断，跳过）

熔断的 Key 被轮询跳过，剩余 Key 重新按比例分配
```

**连通性测试**

```
[测试全部 Key] → 逐个发送健康检查请求

结果展示：
  ✅ Key A: 成功 (45ms)
  ✅ Key B: 成功 (67ms)
  ❌ Key C: 失败 (请求超时)
  ✅ Key D: 成功 (32ms)
```

#### 5.1.2 负载均衡算法（P2）

**加权轮询实现**

```
供应商 A（权重 5），供应商 B（权重 3），供应商 C（权重 2）

轮询序列：A, A, A, A, A, B, B, B, C, C, A, A, ...
权重总和 = 10，一轮发出 10 个请求后重置

每个请求：current_index = (current_index + 1) % 权重总和
跳过熔断的供应商
```

**最少连接优先**

```
每个供应商记录当前活跃请求数
新请求 → 发往活跃请求最少的供应商
避免请求堆积到慢速供应商
```

#### 5.1.3 熔断器状态机（P2）

**三态流转**

```

                                      ↓
                                ┌──────────┐
                                │  全开     │
                                │ (Open)    │

                                     │
                     等待 T 秒后自动进入半开
```

**熔断配置参数**

| 参数 | 默认值 | 说明 |

| 失败阈值 | 5 次 | 连续失败次数达此值触发半开 |

#### 5.1.4 健康检查

**检查方式**

```
定时任务（每 30 秒）：
  向供应商的 /health 或指定端点发送请求
  检查 HTTP 状态码是否为 200
  可选：检查响应体是否符合期望格式

响应处理：
  成功 → 记录响应时间，更新健康度
  失败 → 记录失败计数，触发熔断器
```

**健康度计算**

```
最近 24 小时可用率 = 成功请求 / 总检查请求 × 100%
健康评分 = 可用率 × 70 + (1 - 平均响应时间/基准响应时间) × 30
基准响应时间 = 200ms
```

### 5.2 计费与结算精化

#### 5.2.1 价格层级与优先级

**价格层级定义**

| 层级 | 名称 | 说明 | 单价来源 |
|------|------|------|---------|
| L0 | 供应商成本价 | 上游原始价格 | `vendor_models.input/output_price` |
| L1 | 平台标准价 | L0 × (1 + 全局加价率) | `site_configs.default_markup_rate` |
| L2 | 模型覆盖价 | 特定模型的独立售价 | `models.override_price` |
| L3 | 代理折扣价 | 代理名下用户专属价格 | `agent_commission.discount_rate` |
| L4 | 分组定价 | Key 组专属价格 | `key_group_pricing.unit_price` |
| L5 | 活动价 | 活动期间临时价格 | `campaign_prices.discount_rate` |

**定价优先级规则**

```
L5 活动价 > L4 分组定价 > L3 代理折扣价 > L2 模型覆盖价 > L1 标准价

如果活动价存在 → 使用活动价
否则如果分组定价存在 → 使用分组定价
否则如果该用户属于代理 → 使用代理折扣价
否则如果模型有覆盖价 → 使用覆盖价
否则 → 使用标准价
```

---

#### 5.2.2 实时计费执行流程

```
① 用户请求到达，解析 model 字段
② 根据 Key 查询定价策略（按优先级）
③ 计算预估单价：input_price, output_price
④ 请求尚未发送，无法知道实际 Token 数
⑤ 按 request body 中的 max_tokens 估算最大费用
⑥ 检查余额能否覆盖最大费用
   ├── 充足 → 预扣 max(预估费用, ¥0.01)（防止零元订单）
   └── 不足 → 返回 402 Insufficient Balance
⑦ 发送请求到供应商
⑧ 获取供应商响应（含实际 Token 消耗）
⑨ 计算实际费用 = input_tokens × input_price + output_tokens × output_price
⑩ 执行余额调整：预扣金额 → 实际费用（多退少补）
⑪ 记录 consumption_logs + call_logs
⑫ 返回响应给用户
```

#### 5.3.1 四级限流详细规格

| 级别 | 限制维度 | 配置方式 | 默认值 | 作用范围 | 超越方式 |
|------|---------|---------|-------|---------|---------|

| L1 全局 | 全系统 TPM | `site_configs` | 60000000 | 所有请求 | 不可超越 |
| L2 用户 | 用户 QPS | `user_quotas` | 100 | 该用户 | admin 可调整 |
| L2 用户 | 用户 TPM | `user_quotas` | 600000 | 该用户 | admin 可调整 |
| L2 用户 | 用户日调用 | `user_quotas` | 不限 | 该用户 | admin 可调整 |
| L3 Key | Key QPS | `api_keys` | 50 | 该 Key | 用户可调整 |
| L3 Key | Key TPM | `api_keys` | 300000 | 该 Key | 用户可调整 |
| L3 Key | Key 日调用 | `api_keys` | 不限 | 该 Key | 用户可调整 |
| L4 模型 | 模型全局 QPS | `rate_limits` | 2000 | 该模型所有请求 | admin 可调整 |


```
  充值通知: 站内 + 邮件

  安全告警: 站内 + 邮件 + WebSocket（强制，不可关闭）
  活动通知: 站内（仅）
```

**错误码参考**（P1）

| 错误码 | HTTP 状态 | 含义 | 处理建议 |
|--------|----------|------|---------|
| `invalid_api_key` | 401 | API Key 不存在 | 检查请求头 Authorization 是否正确 |
| `key_disabled` | 403 | API Key 已被禁用 | 在控制台启用该 Key |
| `key_expired` | 403 | API Key 已过期 | 在控制台续期或创建新 Key |
| `insufficient_balance` | 402 | 余额不足 | 充值后重试 |
| `rate_limit_exceeded` | 429 | 请求频率超限 | 降低请求频率，等待 retry_after |
| `model_not_found` | 404 | 模型不存在 | 检查请求中的 model 参数 |
| `model_unavailable` | 503 | 模型暂时不可用 | 稍后重试或切换到其他模型 |
| `content_filtered` | 400 | 请求命中内容过滤 | 修改请求内容 |
| `ip_not_allowed` | 403 | IP 不在白名单 | 检查 IP 白名单设置 |
