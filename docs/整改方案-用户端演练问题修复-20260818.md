## 二、分问题整改方案

### R1【P1】资金收口：兑换码 redeem 统一 creditBalance + 存量数据修复 + 重启生效

**现状/根因**
- 运行旧代码：充值审核走裸 `UPDATE customer_balances ... RETURNING`（无行即 404）；兑换码 redeem 走同样的裸 UPDATE（`recharge.ts:257-277`），均**不自动建户**。
- 工作区 `balance.ts` 已有 `creditBalance()`（INSERT ON CONFLICT DO NOTHING 自动建户 + 审计 + 原子增额 + 资金流水，同事务），`recharge.ts` 审核路径已改用之；**但 redeem 路径未收口**（代码注释自述「本期未收口（裁决 Q6）」）。

**方案**
1. **redeem 收口**：`api/src/routes/recharge.ts` 事务内替换裸 UPDATE 段（现 257-277 行）：

```ts
// 余额入账：统一收口 creditBalance（自动建户兜底 + 资金流水，同事务）
const { balanceAfter } = await creditBalance(tx, {
  userId: uid,
  amount: row.faceValue,
  type: 'recharge',
  referenceType: 'redemption',
  referenceId: String(claimed.id),
  description: `兑换码 ${code} 充值`,
});
return { claimedId: claimed.id, balanceAfter };
```

2. **存量数据一次性修复**（幂等，新脚本 `api/tmp/fix-missing-balance-accounts.cjs` 或 SQL）：

```sql
INSERT INTO customer_balances (user_id, total_balance, available_balance, frozen_balance, currency)
SELECT u.id, 0, 0, 0, 'CNY'
FROM users u
WHERE NOT EXISTS (SELECT 1 FROM customer_balances cb WHERE cb.user_id = u.id);
-- 审计一行：action='balance.bulk_auto_create'，details={count}
```

3. **提交 + 重启**：与在途会话协调，将工作区 R1-R4 修复批次（balance/recharge/manual-topup/审计/通知/migration 0026-0028）**一次性提交**后重启 API（`node --import tsx src/index.ts`，日志 tee `api/tmp/`）。

**验收**
- [ ] 对无余额行用户：审核充值 → 自动建户 + 入账成功；兑换码兑换 → 成功；两者写 `audit_logs`（`balance.auto_create`）
- [ ] 对有余额行用户：行为不变（余额/流水正确，version+1）
- [ ] 单测：`api/src/routes/admin-recharge-audit.test.ts`、`admin-manual-topup.test.ts` 已覆盖审核收口；**新增 redeem 无余额行用例**（`recharge` 相关测试文件）

### R2【P1】网关上游 401 分类与故障转移（mock 回退兜底）

**现状/根因**
- 磁盘 `chat.ts` 已有 `mockFallback`（渠道不可用 → 占位 completion，仍记账），`routing.ts` 按 supplier/key/model 状态选渠道；但**上游非 2xx 错误没有分类**：若上游返回 401（如平台配置的上游 key 无效），当前会透传/返回上游格式错误，误导用户「你的 key 无效」，且不触发回退。
- 演练实测：余额充足时 `POST /v1/chat/completions` → `401 Authentication Fails, Your api key: ****5eb0 is invalid`（DeepSeek 上游格式，掩码 key 与用户无关）。

**方案**
1. **新增上游错误分类工具** `api/src/services/upstream/errors.ts`：

```ts
export type UpstreamFault =
  | { kind: 'auth'; status: 401 | 403 }          // 平台上游 key 无效/无权限
  | { kind: 'retryable'; status: number }        // 5xx/429/超时 → 可熔断重试
  | { kind: 'client'; status: number };          // 请求本身问题（模型不存在等）

export function classifyUpstreamError(resp: { status: number; body: string }): UpstreamFault;
```

2. **proxy step 改造**（`chat.ts` / `proxy.ts`）：上游 401/403 → 标记该 supplier key 故障（计数，供 key-selector 后续跳过），**继续 failover 下一渠道**；全部渠道失败后：
   - 存在 auth 类故障 → 返回 `502 UPSTREAM_AUTH_FAILED`「平台上游鉴权失败，请稍后重试或联系管理员」（**绝不透传上游原始 401**）；
   - 其余 → 现有熔断 + `mockFallback` 兜底（返回 mock 且记账，标注 `mock:true`）。
3. **配置校验**：启动时/健康检查核对 `supplier_keys` 非空且 `suppliers.status='active'` 的渠道存在；全空时 `/status` 置为 `degraded` 并提示运营。
4. **复测前置**：先重启 API 复现确认（若重启后 mock 回退生效则 R2 仅剩分类加固）。

**验收**
- [ ] 上游 401/403 → 用户收到 502 `UPSTREAM_AUTH_FAILED` 中文文案，**不再出现** `Authentication Fails, Your api key: ****5eb0 is invalid`
- [ ] 上游 5xx/超时 → 熔断 + failover + mockFallback（200 mock，记账，`mock:true`）
- [ ] 单测：`classifyUpstreamError` 三分支；proxy step 401/5xx/超时路径（对齐 `services/pipeline/integration.test.ts` 模式）
- [ ] 压测回归：`scripts/stress-chat.cjs 10 2` 9/9（含 mock 路径记账一致）

### R4【P2】空 JSON body 端点兼容

**现状/根因**：Fastify 5 对 `Content-Type: application/json` + 空 body 抛 `FST_ERR_CTP_EMPTY_JSON_BODY`（9 个无体端点：工单 resolve、公告/通知 read-all、2FA setup、Webhook test/regenerate-secret/delete、数据导出 cancel、登出）。

**方案**（`api/src/app.ts` 全局容错，两选一，**推荐 ① 低风险**）

① **preParsing 钩子剥离空 JSON 头**（不动默认 parser，保留 secure-json-parse 原型污染防护）：

```ts
app.addHook('preParsing', async (request) => {
  const ct = request.headers['content-type'];
  if (typeof ct === 'string' && ct.startsWith('application/json') && Number(request.headers['content-length'] ?? 0) === 0) {
    delete request.headers['content-type']; // 空 body 按无 content-type 处理 → Fastify 不再要求 JSON body
  }
});
```

② 备选：自定义 `addContentTypeParser('application/json', { parseAs: 'string' }, ...)` 空串返回 `{}`——需回归全量 JSON 路由（808 单测 + 冒烟），注意避免 `JSON.parse` 的原型污染风险。

- 同步在 `docs/api-contract.md` 标注：无体端点建议客户端传 `{}` 或省略 JSON 头。

**验收**
- [ ] 9 个端点带 JSON 头 + 无 body → 2xx（功能正常），不再 400
- [ ] 全量回归：`pnpm --filter @3cloud/api test` ≥ 基线（当前 808/808）+ `scripts/verify-fullflow-data.cjs`
- [ ] E2E：`cd e2e && pnpm test` 10/10

### R6【P3】错误响应携带 context（details）

**现状/根因**：`app.ts` 未注册 `setErrorHandler`，Fastify 默认序列化丢弃 `AppError.context`，导致兑换码/数据导出 `EXISTS` 错误不带 `requestId`（客户端无法定位进行中的申请）。

**方案**：`api/src/app.ts` 注册统一错误处理器：

```ts
app.setErrorHandler((err, _request, reply) => {
  if (err instanceof AppError) {
    return reply.status(err.statusCode).send({
      statusCode: err.statusCode,
      code: err.code,
      error: err.name,
      message: err.message,
      ...(err.context ? { details: err.context } : {}),
    });
  }
  reply.send(err); // 其余交给默认处理
});
```

- 附加字段 `details` 对现有前端**向后兼容**（新增键不影响解析）；仅 `EXISTS` 等带 context 的错误会多出 `details.requestId`。
- 全量回归（错误响应形状变化影响面：前端错误 toast 均读 `message`/`code`，不受影响；测试断言若比对精确 JSON 需同步）。

**验收**：兑换码/数据导出 EXISTS → 响应含 `details.requestId`；其余错误响应形状不变（除新增 details）。
