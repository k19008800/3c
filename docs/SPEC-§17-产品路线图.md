### 功能描述

产品迭代的版本规划和优先级排期，指导开发团队按节奏推进。

### 版本规划

| 版本 | 时间 | 范围 | 核心目标 |
|------|------|------|---------|
| v1.0 | 当前 | 已有功能 + §8-§12 新增 | 完成所有 P0 功能，达到上线标准 |
| v1.1 | v1.0 + 1 个月 | P1 功能 | 完善客服/财务/业务员支撑 |
| v1.2 | v1.1 + 1 个月 | P2 功能 | 全功能版本 |
| v2.0 | 待定 | 架构升级 | 微服务拆分、多活部署 |

### P0 优先（当前版本 v1.0）

| 优先级 | 模块 | 预估工作量 | 依赖 |
|--------|------|-----------|------|
| P0-1 | §8 运营增长 | 后端 8d + 前端 8d | 用户系统已就绪 |
| P0-2 | §9 财务模块 | 后端 12d + 前端 10d | 计费系统已就绪 |

### P1 优先（v1.1）
包括：快捷回复模板 / 在线客服 / 用户操作时间线 / 跟进提醒 / 商机报价 / 业绩看板 / 合同管理 / 缓存管理 / 任务调度 / 日志查看 / 第三方集成

### P2 优先（v1.2）
包括：销售知识库 / 团队协作 / 数据库面板 / 变更计划 / 版本管理 / 组件库规范

### 技术债清理计划
- v1.0：Drizzle ORM exists 子查询兼容 / 日志表分区迁移
- v1.1：剩余大组件拆分 / 统一错误码规范 / 完善单元测试覆盖率 > 80%
- v2.0：微服务架构评估

### [?] 页面帮助

**页面名称**：产品迭代路线图

**适用角色**：所有角色（产品/开发/测试/运营/管理）

**功能定位**：展示平台产品迭代的版本规划和优先级排期，指导开发团队按节奏推进，帮助各方了解各阶段交付内容和时间线。

**子模块说明**：
- 版本规划：v1.0（当前，P0 全量）→ v1.1（P1）→ v1.2（P2）→ v2.0（架构升级）
- P0 优先功能清单：当前版本 v1.0 必须完成的核心功能
- 历史版本变更记录：已发布版本的功能变更日志

**注意事项**：
- 路线图为规划参考，实际排期以项目进度为准
- v2.0 架构升级（微服务拆分、多活部署）时间待定
- 版本范围变更需产品负责人评审确认

**常见问题**：
Q: v1.0 什么时候上线？
A: v1.0 目标为完成所有 P0 功能达到上线标准，具体时间以项目排期为准。

Q: P1/P2 功能什么时候做？
A: v1.0 上线后约 1 个月进入 v1.1（P1），再 1 个月进入 v1.2（P2）。

Q: 我可以提需求插队吗？
A: 需求优先级调整需产品负责人评审，紧急需求可走特批流程。

## 边界条件

| # | 场景 | 触发条件 | 预期行为 |
|---|------|---------|---------|
| ROAD-001 | 版本依赖冲突 | v1.0 中的 P0 模块依赖其他模块（如 §10.3 帮助中心依赖 §10.2 知识库），但依赖模块未按时交付 | 版本发布计划自动标记相关功能为"阻塞"状态，评估降级方案（如独立功能先上线）并通知相关方 |
| ROAD-002 | 版本发布时间延迟 | 原定发布日仍有未关闭的 P0/P1 缺陷或未完成的功能 | 触发版本发布评审会议，根据缺陷严重度和完成度决定延期时长，修订后的计划自动通知所有干系人 |
| ROAD-003 | 功能依赖链中断 | §8 运营增长依赖的用户系统版本升级因兼容性问题被回滚，导致 §8 上线路由阻塞 | 功能看板自动展示依赖阻断链，PM 评估是否将 §8 拆分为可独立发布的子功能 |
| ROAD-004 | 技术债阻塞新功能开发 | 技术债清理计划（如日志表分区迁移）因数据量过大超出预估时间窗口，影响 v1.1 新功能排期 | 技术债任务自动升级为 P0 优先级，临时调整排期腾出对应开发资源 |
| ROAD-005 | 紧急 hotfix 打乱迭代节奏 | 生产环境出现严重漏洞需要立即修复，打乱当前迭代的开发计划 | hotfix 任务强制插入当前迭代，通过 backlog 自动推迟同等工作量的低优先级任务 |
