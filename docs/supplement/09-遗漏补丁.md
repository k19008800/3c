## 补丁 A：流式计费处理（合并到 01-计费引擎状态机.md §三后）

### A.1 流式请求的计费难点

流式（streaming）计费与非流式有本质区别：
- 非流式：请求前已知 prompt_tokens，响应后已知 completion_tokens → 可精确预扣
- 流式：请求前只知道 max_tokens，实际 completion_tokens 在响应中逐步产生，无法预知总量

### A.2 流式预扣规则

```sql
-- 流式预扣使用最大可能费用，确保余额足够
-- prompt_tokens 已知 → 使用已知值
-- prompt_tokens 未知 → 使用 max_input_tokens（模型配置，默认 8192）
-- completion_tokens → 使用 max_tokens（若未指定，用模型默认最大值）

estimated_cost = max(prompt_tokens) × inputPrice + max(completion_tokens) × outputPrice

-- 注意：这是"最坏情况"预扣，实际费用通常更低
-- 多退少补在流式结束时执行
```

### A.3 流式累计与结算

```
1. 响应阶段（流式累计）：
   - 每次收到 chunk，累积 prompt_tokens + completion_tokens
   - 不计费（计费在结束后统一执行）
   - 可用 WebSocket 向前端推送实时累计费用（仅展示，不影响实际扣款）

2. 结束阶段（结算）：
   - 实际费用 = 最终 prompt_tokens × inputPrice + 最终 completion_tokens × outputPrice
   - 多退少补：refund_amount = estimated_cost - actual_cost
   - 若实际费用 > 预扣 → 追扣（极其罕见，因为流式预扣默认偏大）

3. 与 billing_logs 的映射：
   - 流式请求全程对应同一条 billing_log
   - 流式完成后，billing_logs 状态从 pending → settled
```

### A.4 流式超时与断流处理

| 场景 | 检测方式 | 处理 |
|------|---------|------|
| 连接超时（10s 无任何数据包）| 连接层超时 | 回滚预扣，billing_logs → refunded |
| 流式中途断流（已收到部分 chunk 后 60s 无新 chunk）| 空闲超时定时器 | 按已收到 tokens 结算，退还未使用部分 |
| 用户主动断开连接 | WebSocket close 事件 / HTTP 连接断开 | 按已收到 tokens 结算 |
| 流式响应超长（> 30 分钟）| 全局超时定时器 | 截断，按已收到 tokens 计费，标记日志 |
| Prefill 阶段失败（0 个 chunk 返回）| 无数据返回 | 全额退款预扣，billing_logs → refunded |
| 供应商正常完成但 tokens=0 | 流式结束 | 实际费用=0，全额退还 |

### A.5 流式计费一致性校验

```sql
-- 每日校验：检查流式请求的预扣与实际消耗
-- 流式请求的 refund_amount 通常为正（预扣>实际）
-- 如果 refund_amount < 0（追扣），即使金额小也需告警
SELECT count(*) as streaming_追扣笔数
FROM billing_logs
WHERE refund_amount < 0 AND status = 'settled'
  AND created_at::date = CURRENT_DATE - 1;
```

## 补丁 B：消费退款后的佣金处理（合并到 04-代理佣金与结算.md §六）

### B.1 退款对佣金的影响规则

```sql
-- 核心原则：佣金按最终消费计算，消费退款后佣金相应减少
-- 处理方式：不追回已发放佣金，在下次佣金中扣减

-- 精确规则：
-- 1. 退款发生后，下次佣金计算时自动扣减
-- 2. 扣减金额 = 退款金额 × 原佣金率
-- 3. 扣减记录写入 agent_commissions 表，amount 为负值，附带 refund_ref 关联
-- 4. 如果扣减后该代理当月佣金为负 → 从提现余额中扣除

-- 示例：
--   用户消费 ¥100，佣金率 10% → 佣金 ¥10（已发放）
--   该笔消费退款 ¥20（退 20%）
--   下次佣金计算时自动扣除 ¥20 × 10% = ¥2
--   当月汇总佣金 = ¥10 - ¥2 = ¥8
```

### B.2 退款佣金扣减时序

```
退款发生 → 退款订单 refund_completed
  ↓
标记相关的 billing_logs（记录 refund_relation）
  ↓
下次日终佣金计算时：
  1. 正常计算当日新佣金
  2. 同时查找关联的退款记录
  3. 生成扣减佣金条目（amount 为负，level 与原佣金相同）
  4. 扣减后的净佣金写入 agent_commissions
  5. agents.available_commission += 净佣金（可能为负则减少可用余额）
  ↓
如果扣减导致累计可用佣金 < 已提现总额 → 禁止新增提现
```

### B.3 退款佣金扣减 SQL

```sql
-- 日终佣金计算时，同时处理退款扣减
INSERT INTO agent_commissions (agent_id, user_id, billing_log_id, amount, rate, level, period_date, status)
SELECT 
  ac.agent_id,
  ro.user_id,
  ro.id AS refund_order_id,      -- 关联退款订单
  -ro.amount * ac.rate AS amount, -- 扣减金额（负数）
  ac.rate,
  ac.level,
  ro.created_at::date AS period_date,
  'settled'
FROM refund_orders ro
JOIN billing_logs bl ON bl.id = ro.billing_log_id
JOIN agent_commissions ac ON ac.billing_log_id = bl.id AND ac.status != 'cancelled'
WHERE ro.created_at::date = CURRENT_DATE - 1
  AND ro.status = 'refund_completed'
  AND ro.refund_type = 'consumption_refund'
  AND NOT EXISTS (
    SELECT 1 FROM agent_commissions ac2 
    WHERE ac2.billing_log_id = ro.id AND ac2.amount < 0
  );
```

## 补丁 C：多层次熔断规则（合并到 05-路由熔断恢复梯度.md §五）

### C.1 熔断粒度

```
熔断分三个层次，从大到小：

┌─────────────────────────────────┐
│  ① 供应商级熔断（全局）          │
│    整个供应商 OPEN → 所有请求切换到其他供应商 │
│    触发条件：该供应商所有 Key 都失败         │
├─────────────────────────────────┤
│  ② Key 级熔断                   │
│    单个 API Key 耗尽/异常 → 切换到同供应商其他 Key │
│    触发条件：429/quota_exceeded / 连续 429          │
├─────────────────────────────────┤
│  ③ 用户级限流（非熔断，但相关）  │
│    单个用户超限 → 429，不影响其他用户              │
│    触发条件：QPS / 日调用量 / 月调用量预算          │
└─────────────────────────────────┘
```

### C.2 Key 级熔断的独有规则

```
1. Key 熔断判定（独立于供应商熔断）：
   - 单个 Key 连续 3 次返回 429（配额耗尽）
   - 或单 Key 连续 3 次返回 5xx
   → 该 Key 标记为 quota_exhausted 或 disabled
   → 不再轮询到该 Key
   → 切换到同供应商其他 Key (round-robin)

2. Key 恢复：
   - quota_exhausted 的 Key → 等待配额重置时间（vendor_api_keys.quota_reset_at）
   - disabled 的 Key → 仅人工恢复

3. Key 级熔断与供应商级熔断的关系：
   - 如果某供应商的所有 Key 都处于熔断状态 → 触发供应商级熔断
   - 供应商级熔断结束后，所有 Key 的熔断状态保留（不自动恢复）
   - 需要各 Key 独立通过 HALF_OPEN 探测
```

### C.3 用户级限流规则

```
用户级限流不是"熔断"，但它与路由决策交互：

1. 用户级限流检测点：
   - API 调用入口（鉴权后，计费前）
   - 三个维度的限流可独立或叠加：
     a) QPS 限流：每秒最大请求数（按 API Key）
     b) 日调用量限流：每日最大 Token 数
     c) 月预算限流：每月最多消费金额

2. 限流结果：
   - 超过任一限流 → 返回 429 + retry-after header
   - 不转发到供应商，不计费
   - 用户端收到明确的 limit type（qps/daily/monthly）

3. 限流与熔断的交互：
   - 某用户被限流 → 不影响其他用户路由
   - 某供应商熔断 → 该模型所有用户受影响
   - 两者独立运作
```

### C.4 熔断统计排除规则

以下场景**不纳入**熔断统计（即不影响失败率计算）：

```
1. 用户端 4xx 错误（请求参数错误/鉴权失败/余额不足）
   → 这是用户问题，不是供应商问题
   → 不计入熔断统计

2. 用户被限流返回 429
   → 这是平台限流，不是供应商异常
   → 不计入熔断统计

3. 路由主动跳过（无可用供应商时的 503）
   → 不是供应商失败
   → 不计入熔断统计

4. 健康探测请求的结果
   → 健康探测独立统计，不混入业务请求统计
   → 健康探测有自己的成功/失败计数器
```

## 补丁 D：payment_logs 表定义（合并到 07-Schema重设计建议.md §充值域）

### D.1 支付渠道回调日志表

```typescript
// === payment_logs ===
// 支付渠道回调日志——记录所有来自支付渠道的异步回调
// 用作充值对账的原始数据源
export const paymentLogs = pgTable("payment_logs", {
  id: serial("id").primaryKey(),

  // 支付渠道订单号（渠道侧的唯一标识）
  outTradeNo: varchar("out_trade_no", { length: 100 }).notNull().unique(),
  channel: varchar("channel", { length: 20 }).notNull(),  // alipay / wechat

  // 平台订单号
  orderNo: varchar("order_no", { length: 30 }).references(() => rechargeOrders.orderNo),

  // 回调参数
  tradeStatus: varchar("trade_status", { length: 30 }).notNull(),  // TRADE_SUCCESS / TRADE_CLOSED / ...
  totalAmount: numeric("total_amount", { precision: 14, scale: 2 }).notNull(),
  receiptAmount: numeric("receipt_amount", { precision: 14, scale: 2 }),  // 实际收款（扣除手续费后）
  buyerId: varchar("buyer_id", { length: 100 }),
  gmtPayment: timestamp("gmt_payment"),

  // 验证结果
  verified: boolean("verified").default(false),   // 签名验证结果
  verifyError: varchar("verify_error", { length: 200 }),

  // 原始回调报文
  rawBody: text("raw_body"),                       // 原始 POST body
  rawHeaders: text("raw_headers"),                 // 原始 callback headers

  // 处理结果
  processed: boolean("processed").default(false),  // 是否已被处理（关联到 recharge_orders）
  processedAt: timestamp("processed_at"),
  processError: varchar("process_error", { length: 200 }),

  createdAt: timestamp("created_at").notNull().defaultNow(),
});

// 索引
// - idx_out_trade_no: (out_trade_no) UNIQUE
// - idx_channel_trade_status: (channel, trade_status)
// - idx_order_no: (order_no)
// - idx_created_at: (created_at)

// 数据保留策略：
// - 保留至少 180 天
// - 超过 180 天的记录按月归档到 cold_storage.payment_logs_archive
```

### D.2 充值对账 SQL（补充到 07-Schema重设计建议.md §充值域）

```sql
-- 每日对账：payment_logs vs recharge_orders
-- 场景 1：payment_logs 有但 recharge_orders 无（渠道回调了，平台没找到订单）
SELECT pl.* FROM payment_logs pl
LEFT JOIN recharge_orders ro ON pl.order_no = ro.order_no
WHERE pl.created_at::date = CURRENT_DATE - 1 AND ro.id IS NULL;

-- 场景 2：recharge_orders success 但无对应 payment_logs
SELECT ro.* FROM recharge_orders ro
WHERE ro.created_at::date = CURRENT_DATE - 1
  AND ro.status = 'success'
  AND NOT EXISTS (
    SELECT 1 FROM payment_logs pl WHERE pl.order_no = ro.order_no
  );

-- 场景 3：金额不一致
SELECT pl.order_no, pl.total_amount AS channel_amount, ro.amount AS order_amount
FROM payment_logs pl
JOIN recharge_orders ro ON pl.order_no = ro.order_no
WHERE pl.created_at::date = CURRENT_DATE - 1 AND pl.total_amount != ro.amount;
```
