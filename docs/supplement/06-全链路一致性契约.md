# 全链路数据一致性契约

> **定位**：3cloud 重写时各模块之间的数据一致性约束和交互契约
> **核心原则**：每个数据变动必须有来源、有追踪、可验证

## 二、模块间数据一致性契约

### 2.1 充值 → 余额（充值订单 → users.balance）

```
契约编号：C-01
数据流：recharge_orders.status=success → users.balance += amount

一致性规则：
  1. 充值订单标记 success 后 500ms 内，余额必须到账
  2. 每条 success 充值订单必须有且仅有一条对应余额变动记录（balance_logs）
  3. 余额到账使用 UPDATE 行级锁，确保不会因并发少加钱
  4. 如充值订单 success 但余额未变化（系统 Bug），日终对账脚本检测并自动修复

校验 SQL：
  SELECT r.id, r.amount, COALESCE(SUM(bl.amount), 0) AS balance_added
  FROM recharge_orders r
  LEFT JOIN balance_logs bl ON bl.recharge_order_id = r.id AND bl.type = 'recharge'
  WHERE r.status = 'success'
  GROUP BY r.id, r.amount
  HAVING r.amount != COALESCE(SUM(bl.amount), 0);
```

### 2.2 余额 → 计费（users.balance → billing_logs）

```
契约编号：C-02
数据流：billing_logs.status=settled → users.balance -= actual_cost

一致性规则：
  1. 计费扣款使用 UPDATE ... WHERE balance >= amount - overdraftLimit 行级锁
  2. 每条 settled billing_log 的 actual_cost 必须从用户余额中扣减
  3. 扣款前余额 = billed 前 balance，扣款后余额 = 扣款前 - actual_cost
  4. 预扣回滚时，回滚金额必须等于预扣金额
  
校验 SQL（按用户）：
  SELECT user_id, 
         SUM(CASE WHEN status IN ('settled','reconciled') THEN actual_cost ELSE 0 END) AS total_cost,
         SUM(CASE WHEN status = 'refunded' THEN refund_amount ELSE 0 END) AS total_refund
  FROM billing_logs
  WHERE created_at::date = CURRENT_DATE - 1
  GROUP BY user_id;
```

### 2.3 计费 → 总账（billing_logs → platform_ledger）

```
契约编号：C-03
数据流：billing_logs.status=settled/reconciled → platform_ledger(type=user_consumption)

一致性规则：
  1. 每日 T+1 归集：前一日所有 settled/reconciled 的 billed_logs 汇总写入 platform_ledger
  2. 归集是批量操作，不是逐笔（减少写放大）
  3. 笔数校验：billing_logs 笔数 == platform_ledger 归集条目
  4. 金额校验：SUM(actual_cost) == platform_ledger 汇总金额

归集 SQL（每日 00:30 执行）：
  INSERT INTO platform_ledger (type, direction, amount, balance_after, date, created_at)
  SELECT 
    'user_consumption',
    'in',
    SUM(actual_cost),
    /* balance_after 来自前一日的总账余额 + 当日汇总 */
    CURRENT_DATE - 1,
    NOW()
  FROM billing_logs
  WHERE created_at::date = CURRENT_DATE - 1
    AND status IN ('settled', 'reconciled');
```

### 2.4 计费 → 供应商结算（billing_logs → vendor_settlements）

```
契约编号：C-04
数据流：call_logs → vendor_settlements（按供应商维度汇总）

一致性规则：
  1. 供应商结算基于 call_logs（不是 billing_logs），因为供应商按调用量计费
  2. 每笔 settled billing_log 应关联一条对应的 call_log
  3. 供应商结算金额 = Σ(供应商成本价 × tokens)
  4. 平台毛利 = Σ(user_actual_cost) - Σ(vendor_cost)
  5. 毛利偏差 > ¥100 触发告警

结算计算：
  供应商成本 = call_logs.prompt_tokens × vendor_models.cost_input_price / 1000000
             + call_logs.completion_tokens × vendor_models.cost_output_price / 1000000
  
  平台收入 = billing_logs.actual_cost
  
  单笔毛利 = 平台收入 - 供应商成本
```

### 2.5 计费 → 代理佣金（billing_logs → agent_commissions）

```
契约编号：C-05
数据流：billing_logs.status=settled/reconciled + agent_user_relations → agent_commissions

一致性规则：
  1. 佣金计算基于 settled/reconciled 的 billing_logs
  2. 每日佣金计算在计费日终结算完成后执行
  3. 执行顺序：计费日终 → 总账归集 → 佣金计算 → 佣金汇总
  4. 同一笔 billing_log 不可被重复计算佣金（(agent_id, billing_log_id) UNIQUE）
  5. 佣金计算的快照费率（commission_rules）必须锁定计算当天的费率版本
```

### 2.6 提现 → 余额/总账（withdraw_orders → platform_ledger）

```
契约编号：C-06
数据流：withdraw_orders.status=paid → platform_ledger(type=agent_withdraw)

一致性规则：
  1. 提现审批通过后，冻结的佣金余额才真正扣减
  2. 提现打款成功后，写入 platform_ledger
  3. 提现失败（打款失败）→ 不写入 platform_ledger，佣金余额解冻
  4. 提现状态与总账一一对应：一笔提现对应一条总账记录
```

## 三、每日对账校验（必须全部通过才能标记日结完成）

### 3.1 对账时序

```
00:00  — 前一日数据截止
00:30  — 充值对账：payment_logs vs recharge_orders vs balance_logs
00:35  — 计费对账：billing_logs vs call_logs
00:40  — 总账归集：billing_logs / recharge_orders / withdraw_orders → platform_ledger
00:45  — 余额校验：会计恒等式校验
00:50  — 佣金校验：billing_logs vs agent_commissions
00:55  — 对账报告生成
08:00  — 对账报告推送
```

### 3.2 强制校验规则

```sql
-- 以下校验都必须通过（偏差为 0），否则阻止日结完成：

-- 1. 充值一致
SELECT COUNT(*) FROM recharge_orders 
WHERE created_at::date = CURRENT_DATE - 1 AND status = 'success'
AND id NOT IN (SELECT recharge_order_id FROM balance_logs WHERE type = 'recharge');

-- 2. 计费一致
SELECT user_id, SUM(actual_cost) AS total_cost,
       (SELECT balance FROM users WHERE id = user_id) AS current_balance
FROM billing_logs
WHERE created_at::date = CURRENT_DATE - 1 AND status = 'settled'
GROUP BY user_id;

-- 3. 总账出入平衡
SELECT 
  SUM(CASE WHEN direction = 'in' THEN amount ELSE 0 END) AS total_in,
  SUM(CASE WHEN direction = 'out' THEN amount ELSE 0 END) AS total_out,
  SUM(CASE WHEN direction = 'in' THEN amount ELSE 0 END) - 
  SUM(CASE WHEN direction = 'out' THEN amount ELSE 0 END) AS net
FROM platform_ledger
WHERE created_at::date = CURRENT_DATE - 1;

-- 4. 会计恒等式
-- （见 02-对账差异处理定量规则.md §七）
```

## 四、模块间调用契约

### 4.1 计费引擎调用契约

```
输入（路由引擎调用计费）：
  - userId: number
  - modelId: number
  - keyGroupId?: number
  - campaignId?: number
  - maxTokens: number（预估用）
  - promptTokens?: number（非流式，实际已知）
  - completionTokens?: number（非流式，实际已知）

输出：
  成功：{ ok: true, billingLogId: number, cost: number }
  余额不足：{ ok: false, error: 'BALANCE_EXHAUSTED' }
  计费异常：{ ok: false, error: 'BILLING_ERROR' }

幂等性：
  同一 call_log_id 不可重复计费
  同一 billing_log 不可重复 settled
```

### 4.2 路由引擎调用契约

```
输入（API 网关调用路由）：
  - model: string
  - apiKey: string
  - headers: object
  - body: object（原始请求体）
  - maxTokens: number

输出：
  成功：{ status: 'ok', vendorResponse: object, callLogId: number }
  鉴权失败：{ status: 'error', code: 'AUTH_FAILED', message: '...' }
  余额不足：{ status: 'error', code: 'BALANCE_EXHAUSTED' }
  限流：{ status: 'error', code: 'RATE_LIMITED', retryAfter: number }
  全部不可用：{ status: 'error', code: 'ALL_VENDORS_DOWN' }
```

### 4.3 供应商调用契约

```
每次供应商调用需记录：
  - call_logs: 请求/响应/Token/耗时/状态码完整记录
  - 供应商响应中的 usage 字段（prompt_tokens, completion_tokens）作为计费依据
  
超时设置：
  非流式请求：默认 30s（可配置，最大 120s）
  流式请求：默认 60s（连接超时 10s，响应超时 60s）

重试：
  路由引擎本身不重试（由用户端重试）
  但如果第一次选择的供应商失败，自动故障转移到下一个
```

## 五、数据一致性优先级

| 优先级 | 场景 | 约束 |
|--------|------|------|
| P0 | 用户余额变动与实际消费对应 | 必须精确到分，不可有偏差 |
| P0 | 充值到账 | 用户付款后必须到账（最多 5 分钟延迟）|
| P0 | 充值退款 | 退款金额必须等于实际支付金额 |
| P0 | 对账偏差归零 | 日终对账偏差必须 ≤ ¥10 |
| P1 | 佣金计算 | 日终结算时偏差 ≤ ¥1 |
| P1 | 供应商结算 | 月结时偏差 ≤ ¥100 |
| P2 | 余额展示 | 缓存延迟 ≤ 30 秒 |
