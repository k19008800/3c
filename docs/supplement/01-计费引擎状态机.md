## 一、billing_logs 状态机定义

### 1.1 状态定义

| 枚举值 | 含义 | 是否终态 | 可重入 |
|--------|------|---------|--------|
| `pending` | 已预扣，等待供应商响应 | 否 | 否 |
| `settled` | 已结算（预扣-追扣/退款完成） | ✅ 终态 | 否 |
| `refunded` | 已回滚（供应商失败，预扣退还） | ✅ 终态 | 否 |
| `orphaned` | 孤儿状态（预扣后服务器崩溃/超时，未收到结算或回滚） | 否 | ✅（可手动修复）|
| `reconciled` | 对账确认一致（从 settled 升级） | ✅ 终态 | 否 |

### 1.2 完整状态转换图

```
① 预扣成功
  ┌───────────┐
  │  pending  │ ◀──────── 创建（预扣成功）
  └─────┬─────┘
        │
    ┌───┴───┐
    │       │
    ▼       ▼
 ┌────┐  ┌──────┐
 │    │  │      │
 │set-│  │refun-│  ← 供应商超时/异常，回滚预扣
 │tled│  │ded   │
 │    │  │      │
 └──┬─┘  └──────┘
    │
    ▼
 ┌──────────┐
 │reconciled│  ← 对账确认（终态）
 └──────────┘

② 异常路径
  pending ──(60s 超时无响应)──→ orphaned
    │
    └──(人工修复: 补录实际费用)──→ settled
    └──(人工修复: 确认供应商失败)──→ refunded
    └──(人工修复: 确认需要放弃)──→ 标记为 lost（日志保留但不修正余额）

③ 对账路径
  settled ──(对账匹配成功)──→ reconciled
  settled ──(对账差异)──────→ 保持 settled + 写入对账差异表
```

### 1.3 每个状态转换的精确副作用

| 转换 | 触发条件 | 数据库操作 | 缓存操作 | 通知 |
|------|---------|-----------|---------|------|
| `(无)→pending` | 预扣成功 | INSERT billing_logs (status=pending)；UPDATE users SET balance = balance - estimated_cost | 无需 | 无 |
| `pending→settled` | 供应商返回有效响应 | UPDATE billing_logs SET status=settled, actual_cost, refund_amount；余额调整(多退少补) | 清除用户余额缓存 | 无 |
| `pending→refunded` | 供应商超时/异常 | UPDATE billing_logs SET status=refunded, refund_amount=estimated_cost；余额 = 余额 + estimated_cost | 清除用户余额缓存 | 无 |
| `pending→orphaned` | 60s 兜底定时器触发 | UPDATE billing_logs SET status=orphaned WHERE status=pending AND created_at < NOW()-60s | 清除用户余额缓存 | P1 告警（系统通知）|
| `settled→reconciled` | 对账匹配成功 | UPDATE billing_logs SET status=reconciled, reconciled_at=NOW() | 无 | 无 |
| `orphaned→settled`| 人工修复: 补录 | UPDATE billing_logs SET status=settled, actual_cost | 清除用户余额缓存 | 写入 operation_logs |
| `orphaned→refunded` | 人工修复: 确认失败 | UPDATE billing_logs SET status=refunded；余额 = 余额 + estimated_cost | 清除用户余额缓存 | 写入 operation_logs |

### 1.4 状态约束规则

```sql
-- 不可逆转：已 settled 不可退款（通过退款表处理，不是修改 billing_logs）
-- 不可逆转：已 reconciled 不可修改
-- orphaned 可通过人工操作转换，但需记录 operation_logs

-- 数据库约束：
-- 1. billing_logs 写入后不可 DELETE（软删除标记）
-- 2. settled/refunded/reconciled 不可 UPDATE（只读终态）
-- 3. orphaned 仅可由后台管理接口更新（需 finance_ops 权限）
```

## 二、并发扣款保护机制（详细实现层）

### 2.1 行级乐观锁

```sql
-- 核心扣款 SQL（原子操作）
UPDATE users
SET balance = balance - $estimated_cost
WHERE id = $user_id
  AND balance >= $estimated_cost - $overdraft_limit;  -- overdraft_limit = 10.00 (元)
  -- 注意：overdraft_limit 是绝对值，余额可降到 -10 元

-- 返回 ROW_COUNT 判断是否成功
-- ROW_COUNT = 1 → 预扣成功
-- ROW_COUNT = 0 → 余额不足，返回 402
```

**为什么不用事务+SELECT FOR UPDATE？**
- UPDATE + WHERE 条件是**原子行级锁**，不需要显式事务
- 避免了 SELECT FOR UPDATE 的行锁等待
- 并发扣款时，后到的请求直接因为 WHERE 条件不满足而失败（不会死锁）

### 2.2 预扣重试策略

| 场景 | 重试策略 |
|------|---------|
| 预扣 SQL 执行成功 | 不重试，直接 proceed |
| 数据库连接超时 | 最多重试 2 次，间隔 50ms |
| 死锁检测（PostgreSQL 自动检测） | 自动回滚后重试 1 次 |
| 主从切换 | 等待 200ms 后重试 1 次 |

### 2.3 预扣释放兜底定时器

```sql
-- 兜底定时器（cron: 每分钟执行）
-- 场景：预扣成功(pending)但供应商未返回、服务器崩溃等
UPDATE billing_logs
SET status = 'orphaned'
WHERE status = 'pending'
  AND created_at < NOW() - INTERVAL '60 seconds';

-- 每次兜底扫描后输出统计：
-- - 本次标记为 orphaned 的笔数
-- - 当前仍处于 pending 超过 30s 但不足 60s 的笔数（即将超时）
```

### 2.4 多退少补流程（供应商返回后的精确结算）

```sql
-- 场景 1：实际费用 ≤ 预扣金额（退款）
refund_amount = estimated_cost - actual_cost;
UPDATE users SET balance = balance + refund_amount WHERE id = $user_id;
UPDATE billing_logs SET status = 'settled', actual_cost = $actual_cost,
    refund_amount = refund_amount WHERE id = $log_id;

-- 场景 2：实际费用 > 预扣金额（追扣）
extra_charge = actual_cost - estimated_cost;
-- 追扣也要检查余额上限（避免追扣后余额低于 -overdraft_limit）
UPDATE users SET balance = balance - extra_charge
WHERE id = $user_id AND balance - extra_charge >= -10.00;
-- 如果追扣失败（余额不够），则：
--   1. 补录追扣失败的 billing_log 记录
--   2. billing_logs 主记录标记 extra_charge_failed = true
--   3. 后续通过"欠费回收"流程催缴
```

## 三、流式计费处理

### 3.1 流式请求的计费难点

流式（streaming）请求的计费与非流式有本质区别：
- 非流式：请求前已知 prompt_tokens，请求后已知 completion_tokens → 可精确预扣
- 流式：请求前只知道 max_tokens（上限），实际 completions_tokens 在响应过程中逐步产生，且无法预知总量

### 3.2 流式计费策略

```
方案：预估预扣 + 最终结算

1. 请求阶段（预扣）：
   - prompt_tokens 已知？→ 用已知值。未知？→ 用 max_input_tokens（默认 8192）
   - completion_tokens 用 max_tokens 估算（若未指定，用模型默认最大值）
   - 预扣金额 = max(prompt_tokens) × inputPrice + max(completion_tokens) × outputPrice
   - 注意：这是

| # | 场景 | 检测时机 | 自动处理 | 告警级别 | 人工介入 |
|---|------|---------|---------|---------|---------|
| B-001 | 预扣 SQL 执行失败 | 请求阶段 | 返回 500，不计费，不转发到供应商 | P0 告警 | 检查数据库连接 |
| B-002 | 定价查询失败（缓存+DB 都不可用） | 计费阶段 | 使用缓存中最后一次有效定价（不超过 5 分钟）。若缓存也为空，返回 503 | P0 告警 | 检查 Redis + DB |
| B-003 | 供应商正常返回但 tokens=0 | 响应阶段 | 实际费用 = 0，全额退款 estimated_cost | 无（标记日志）| — |
| B-004 | 实际费用 > 预扣金额 2 倍 | 响应阶段 | 正常追扣，但触发 P1 告警（运营核查定价是否正确）| P1 告警 | 核查定价配置 |
| B-005 | 实际费用 > 预扣金额且追扣失败 | 响应阶段 | billing_logs 标记 extra_charge_failed=true，后续单独催缴 | P1 告警 | 人工补扣（运营面板操作）|
| B-006 | 供应商 30s 无响应 | 响应阶段 | 回滚预扣，标记 refunded | P1 告警 | 检查供应商健康状态 |
| B-007 | API 服务器在预扣后重启 | 恢复阶段 | 60s 兜底定时器标记为 orphaned | P1 告警 | 人工核查并处理 |
| B-008 | 同一请求重复回调（供应商重复通知） | 响应阶段 | 检查 billing_logs 状态，已 settled 或 refunded 则忽略 | 标记日志 | — |
| B-009 | 计费金额异常巨大（¥10,000+ 单笔） | 预扣前 | 触发风控审核，返回 402 并提示联系客服 | P0 告警 | 立即核查 |

### 3.2 计费一致性校验（每日 cron）

```sql
-- 每日 00:30 执行
-- 校验 1：计费日志 vs 余额变动
SELECT user_id, SUM(actual_cost) AS total_cost, 
       (MAX(balance_before) - MIN(balance_after)) AS balance_change
FROM billing_logs 
WHERE created_at::date = CURRENT_DATE - 1
GROUP BY user_id
HAVING ABS(SUM(actual_cost) - (MAX(balance_before) - MIN(balance_after))) > 0.01;

-- 校验 2：orphaned 记录数 > 0 时触发告警
SELECT COUNT(*) FROM billing_logs 
WHERE status = 'orphaned' AND created_at::date = CURRENT_DATE - 1;
```

## 四、计费模块数据模型

### 4.1 billing_logs 表完整定义（重写版本）

```typescript
export const billingLogs = pgTable("billing_logs", {
  id: serial("id").primaryKey(),
  callLogId: integer("call_log_id").references(() => callLogs.id),
  userId: integer("user_id").notNull().references(() => users.id),

  // === 定价信息（快照，不关联外键）===
  priceSource: varchar("price_source", { length: 20 }),   // L0~L5
  inputPrice: numeric("input_price", { precision: 18, scale: 6 }),
  outputPrice: numeric("output_price", { precision: 18, scale: 6 }),
  discountRate: numeric("discount_rate", { precision: 5, scale: 4 }).default("1.0000"),

  // === 费用 ===
  estimatedCost: numeric("estimated_cost", { precision: 18, scale: 6 }),     // 预扣金额
  actualCost: numeric("actual_cost", { precision: 18, scale: 6 }),           // 实际费用（结算后写入）
  refundAmount: numeric("refund_amount", { precision: 18, scale: 6 }),       // 退款给用户
  extraCharge: numeric("extra_charge", { precision: 18, scale: 6 }),         // 追扣金额
  extraChargeFailed: boolean("extra_charge_failed").default(false),          // 追扣是否失败

  // === 余额快照 ===
  balanceBefore: numeric("balance_before", { precision: 18, scale: 6 }),
  balanceAfter: numeric("balance_after", { precision: 18, scale: 6 }),

  // === 状态机 ===
  status: varchar("status", { length: 20 }).notNull().default("pending"),
    // pending | settled | refunded | orphaned | reconciled
  reconciledAt: timestamp("reconciled_at", { withTimezone: true }),
  locked: boolean("locked").default(false),                 // 锁账后=true，不可修改

  // === 错误信息 ===
  errorReason: varchar("error_reason", { length: 500 }),
  errorCategory: varchar("error_category", { length: 50 }), // timeout / server_crash / pricing_fail / other

  // === 元数据 ===
  createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
  updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow(),
});

// 索引
// - idx_user_id_created: (user_id, created_at DESC)
// - idx_status_pending: (status) WHERE status = 'pending'
// - idx_status_orphaned: (status) WHERE status = 'orphaned'
// - idx_reconciled: (status) WHERE status = 'reconciled'
```

## 五、计费引擎降级策略

| 故障组件 | 降级行为 | 恢复后行为 |
|---------|---------|-----------|
| Redis 不可用 | 定价查询降级到 DB（延迟从 <5ms 升到 <50ms）| 恢复后缓存预热 |
| DB 主库不可用 | 计费暂停（请求不转发，返回 503），避免数据不一致 | DB 恢复后自动恢复 |
| DB 从库不可用 | 不影响计费（计费只用主库写） | — |
| 计费引擎进程崩溃 | 进程管理器自动重启。重启期间积累的请求走降级通道（不预扣，记录日志，事后补计费）| 补计费 cron 处理 |

## 六、关键精度与舍入规则（重申与细化）

| 项目 | 精度 | 存储类型 | 舍入方式 |
|------|------|---------|---------|
| 单价存储 | 6 位小数 | numeric(18,6) | — |
| 费用计算 | 不限（JS Number）| — | — |
| 最终扣费 | 6 位小数 | numeric(18,6) | Math.round (四舍五入) |
| 前端展示 | 2 位小数 | — | toFixed(2) |
| 对账偏差阈值 | ¥0.01 | — | — |
| 会计恒等式偏差阈值 | ¥10.00 | — | — |
| 余额显示 | 2 位小数 | numeric(14,2) | 向下取整（不展示无法使用的 0.001 级余额） |

**重要**：计算用 6 位，存储用 6 位，展示用 2 位。这是三个不同的精度层次，务必区分。

## 七、billing_logs 与周边模块的契约

| 关联模块 | 数据流向 | 一致性约束 |
|---------|---------|-----------|
| call_logs | billing_logs.call_log_id → call_logs.id | 每个 call_log 最多对应一条 billing_log（1:1）。重写时建议改为 1:1 内联以减少 JOIN |
| users.balance | UPDATE users SET balance = balance ± cost | SUM(billing_logs.actual_cost) == 用户期初期末余额差 |
| platform_ledger | 每日 T+1 归集 | SUM(billing_logs.actual_cost) == ledger.amount(WHERE type=user_consumption) |
| agent_commissions | 基于 billing_logs 的代理佣金计算 | 佣金计算使用 settled/reconciled 状态的 billing_logs，排除 refunded/orphaned |
| vendor_settlements | 基于 call_logs 的供应商结算 | 供应商结算使用 settled/reconciled 对应的 call_logs |
