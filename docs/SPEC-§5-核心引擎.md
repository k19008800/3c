## 5.1 智能路由系统

### 功能描述

当用户通过 API 调用平台时，路由系统负责鉴权→风控→限流→计费预检→供应商选择→发送请求→处理响应的全链路调度。核心能力是在多供应商之间智能选择最优路径。

### 完成能力 / 展示效果

**用户侧（无感）：**
用户只需传 `model` 参数（如 `"deepseek-chat"`），路由自动完成：
1. 鉴权：校验 API Key 存在/启用/未过期/IP 白名单
2. 风控：IP 黑名单检测、地理封锁、威胁情报、风控规则
3. 限流：四级限流检查（全局/用户/Key/模型）
4. 模型解析：找到请求的模型定义
5. 计费预检：查询定价策略 → 按 max_tokens 预估费用 → 检查余额 → 预扣
6. 供应商选择：加载该模型所有可用供应商映射 → 按优先级排序 → 排除熔断供应商/Key → 按权重轮询选择
7. 请求转发：添加供应商认证头 → 模型名映射 → 设置超时 → 发送
8. 响应处理：获取供应商响应 → 计算实际费用 → 多退少补扣款 → 记录日志

**管理后台（路由配置 `/admin/routing`）：**
- 决策树可视化：完整链路每个环节的通过/拒绝条件一目了然
- 供应商优先级配置：每个模型可设置各供应商的优先级和权重
- 手动覆盖：可指定某个模型强制使用某供应商（紧急切换场景）
- 路由推荐：系统基于历史数据推荐最优路由策略（价格/延迟/成功率综合）

### 上下游关系

```
上游：
  用户 API 请求 → 路由入口
  vendor_models → 供应商映射和价格
  models → 模型定义
  api_keys → 鉴权和定价策略
  site_configs → 全局限流参数
下游：
  供应商 API → 实际调用
  call_logs → 记录调用结果
  consumption_logs → 记录计费
  熔断器 → 失败计数 → 自动熔断异常供应商
  健康检查 → 更新供应商可用状态
```

### 负载均衡算法（P2）

当同一模型有多个供应商映射可用时，路由引擎使用以下策略选择：
- **加权轮询**：按供应商权重分配流量（权重在映射中配置）
- **最少连接**：优先选择当前活跃请求数最少的供应商
- **最低延迟**：基于最近 5 次请求的平均响应时间选择最快的
- **成本优先**：优先选择单价最低的供应商（在价格差距 > 10% 时启用）
- **故障转移**：当前选择失败 → 自动切换到下一个可用供应商

配置项：可为每个模型独立选择负载均衡策略。

### 熔断器状态机（P2）

熔断器监控每个供应商的请求失败率，实现自动故障隔离和恢复。

**三态转换：**
```
CLOSED（关闭）→ 请求正常转发
  ↓ 失败率 > 阈值（默认 30%，近 1 分钟）
OPEN（打开）→ 直接拒绝请求，不转发到该供应商
  ↓ 等待超时时间（默认 30 秒）
HALF_OPEN（半开）→ 允许少量请求试探
  ↓ 成功 → CLOSED（恢复）
  ↓ 失败 → OPEN（继续熔断）
```

**配置项：**
- 失败率阈值：默认 30%
- 统计窗口：默认 1 分钟
- 熔断超时：默认 30 秒
- 半开状态请求数：默认 3 个
- 熔断事件记录到 security_events 表

## 5.2 计费与结算精化

### 功能描述

六层定价体系（L0-L5），支持混合定价、实时计费（预扣→多退少补）、账单生成和自动对账。

### 完成能力 / 展示效果

**定价引擎（6 层优先级）：**
| 层级 | 名称 | 说明 |
|------|------|------|
| L0 | 供应商成本价 | 上游原始价格（`vendor_models`）|
| L1 | 平台标准价 | L0 × (1 + 全局加价率) |
| L2 | 模型覆盖价 | 特定模型的独立售价 |
| L3 | 代理折扣价 | 代理名下用户专属价格 |
| L4 | 分组定价 | Key 组专属价格 |
| L5 | 活动价 | 活动期间临时价格 |

定价从上到下匹配：L5 存在→用活动价，否则 L4→L3→L2→L1

**实时计费流程：**
1. 用户请求到达 → 解析 model
2. 查询定价策略（按优先级）→ 计算预估单价
3. 按 max_tokens 预估最大费用 → 检查余额 → 预扣
4. 发送请求到供应商
5. 获取响应 → 计算实际费用（input_tokens×输入价 + output_tokens×输出价）
6. 余额调整：预扣金额→实际费用（多退少补）
7. 记录 consumption_logs + call_logs

**账单生成：**
- 月度账单 PDF：用户/代理月度消费汇总
- 供应商结算单：平台应付各供应商费用
- 自动对账：平台收入 vs 供应商成本，标记差异项

**智能定价建议（P2）：**
- 基于市场行情和历史定价，建议价格调整
- 提供"如果调整定价到 X，预计影响收入 Y%"

### 上下游关系

```
上游：
  vendor_models → 供应商成本价
  site_configs → 全局加价率
  agent_commission → 代理折扣
  campaigns → 活动价
  路由系统 → 传递用户/Key/模型信息
下游：
  users.balance → 扣款/退款
  consumption_logs → 消费记录
  call_logs → 调用明细
  账单引擎 → 月度账单生成
  对账引擎 → 平台vs供应商差异检查
```

## 5.3 限流引擎

### 功能描述

四级限流架构（全局→用户→Key→模型），保护平台不被突发流量冲垮。

### 完成能力 / 展示效果

| 级别 | 限制维度 | 默认值 | 作用范围 | 可调整 |
|------|---------|-------|---------|-------|
| L1 全局 | 全系统 QPS / TPM | 10000/60000000 | 所有请求 | 不可超（系统硬顶）|
| L2 用户 | 用户 QPS / TPM / 日调用 | 100/600000/不限 | 该用户 | admin 可调 |
| L3 Key | Key QPS / TPM / 日调用 | 50/300000/不限 | 该 Key | 用户可调 |
| L4 模型 | 模型全局 QPS / 模型用户 QPS | 2000/50 | 该模型所有请求 | admin 可调 |

**限流命中响应：**
用户收到 429 响应，包含：
```json
{
  "error": {
    "code": "rate_limit_exceeded",
    "message": "请求频率超限，请稍后重试",
    "limit_type": "user_qps",
    "limit_value": 100,
    "current_value": 156,
    "retry_after": 30
  }
}
```

**管理后台（限流可视化）：**
- 查看当前各维度限流值和命中率
- 哪些 Key/用户/模型命中限流最多（Top 排行）
- 在线调整限流参数，实时生效

### 上下游关系

```
上游：每个 API 请求 → 限流中间件
      管理员配置 → 更新限流阈值
下游：命中限流 → 429 响应 → 用户端重试
      命中分析 → 限流可视化看板
```

## 5.4 通知与告警精化

### 功能描述

7 项告警指标配置、多通道推送（站内/邮件/WebSocket）、告警命中趋势分析。

### 完成能力 / 展示效果

**管理后台（告警规则配置 → 4 个标签页）：**
- **告警指标**：7 项告警指标逐一配置阈值/严重等级/启用禁用

**7 项告警指标完整定义：**

| 告警指标 | 条件 | 等级 | 通知对象 | 频率 |
|---------|------|------|---------|------|
| API 失败率 | > 5%（最近 5 分钟）| 🔴 紧急 | 全部管理员 | 5 分钟 1 次 |
| 供应商可用率 | < 95%（最近 5 分钟）| 🔴 紧急 | 运维管理员 | 5 分钟 1 次 |
| 响应时间 P95 | > 2s（最近 5 分钟）| 🟡 告警 | 运维管理员 | 15 分钟 1 次 |
| 平台余额 | < ¥100 | 🟡 告警 | super_admin | 1 小时 1 次 |
| 用户失败率 | 单用户 > 20%（5 分钟）| 🟠 提醒 | 安全管理员 | 15 分钟 1 次 |
| 磁盘使用率 | > 85% | 🟡 告警 | 运维管理员 | 30 分钟 1 次 |
| CPU 使用率 | > 80%（持续 5 分钟）| 🟡 告警 | 运维管理员 | 30 分钟 1 次 |

| 告警指标 | 条件 | 等级 | 通知对象 | 频率 |
|---------|------|------|---------|------|
| API 失败率 | > 5%（最近 5 分钟）| 🔴 紧急 | 全部管理员 | 5 分钟 1 次 |

- **通知配置**：用户可配置各类型通知的推送通道
- **告警历史**：历史告警记录，支持搜索和趋势分析
- **近 7 天命中趋势**：柱状图展示各指标告警命中频率

**推送架构：**
```
事件源 → 通知服务 → 通知类型判断 → 推送队列
    ├─ 站内通知 → notifications 表 → 前端轮询/WebSocket 推送
    ├─ 邮件通知 → SMTP 发送（队列消费）
    └─ WebSocket 实时 → 直接推送到在线用户
```

### 上下游关系

```
上游：
  监控指标采集 → 检测阈值触发
  site_configs → 通知通道配置
下游：
  告警触发 → 通知推送 → 管理员响应
  告警历史 → 趋势分析看板
```
