## 1. 版本升级影响评估清单

每次版本升级前，运营需完成以下评估：

| 评估项 | 检查内容 | 影响等级 |
|--------|---------|---------|
| 数据库 Schema 变更 | 是否涉及表结构变更、索引重建、数据迁移 | 高（需停服或灰度） |
| API 接口变更 | 是否新增/修改/废弃接口，是否向后兼容 | 中（需通知开发者） |
| 前端路由变更 | 是否新增/修改页面路由 | 低（自动） |
| 定价/计费逻辑变更 | 是否影响价格计算、余额扣减 | 高（需财务确认） |
| 路由/限流策略变更 | 是否影响供应商选择、频率限制 | 高（需运维确认） |
| 权限/角色变更 | 是否新增/修改角色权限 | 中（需管理员确认） |
| 缓存/Redis 变更 | 是否修改缓存键或 TTL | 低（热加载） |
| 通知模板变更 | 是否修改用户通知内容 | 低（可随时发布） |

## 2. 灰度发布策略

| 阶段 | 流量比例 | 持续时长 | 验证指标 | 成功条件 |
|------|---------|---------|---------|---------|
| 金丝雀 | 1% 用户 | 15 分钟 | P99 延迟、错误率、计费偏差 | 错误率 < 0.1%，计费偏差 = 0 |
| 小批量 | 10% 用户 | 30 分钟 | 同上 + 用户反馈 | 无投诉 |
| 中批量 | 50% 用户 | 1 小时 | 同上 + 对账偏差 | 对账通过 |
| 全量 | 100% 用户 | 观察 24h | 所有指标 | 无异常告警 |

### 2.1 灰度用户选择规则

```
1. 按 user_id 哈希取模（如 hash(user_id) % 100 < 1 为金丝雀）
2. 优先选择低活跃用户（减少影响范围）
3. 支持手动添加指定用户到灰度组（运营可指定特定代理商或测试账号）
4. 灰度用户在整个发布周期保持不变（保持一致性）

流控方式：
- 后端：Nginx 或 API 网关根据灰度标签（x-canary-version header）分流
- 前端：路由不变化，仅 API 请求指向不同版本
- 数据库：灰度用户和全量用户共用同一数据库（通过 version_tag 区分配置）
```

### 2.2 逐阶段验证要点

| 阶段 | 验证重点 |
|------|---------|
| 金丝雀 | 计费准确性（逐笔比较新旧计费结果）、API 响应时间 P99 |
| 小批量 | 对账结果一致性、通知推送是否正常、告警规则是否触发 |
| 中批量 | 批量操作性能、报表生成、代理佣金计算 |
| 全量 | 所有模块功能正常、无批量异常告警 |

## 3. 回滚方案

| 回滚场景 | 回滚方式 | 预计耗时 | 影响范围 |
|---------|---------|---------|---------|
| 代码 Bug | 回退到上一个版本部署 | 5 分钟 | 灰度用户 |
| 数据库 Schema 变更 | 执行 migration 回滚 | 10 分钟 | 全量（需短暂停服） |
| 数据迁移错误 | 执行回滚脚本 + 从备份恢复 | 30 分钟 | 全量（需停服） |
| 定价/计费错误 | 恢复旧版定价配置 + 余额补偿 | 15 分钟 | 受影响用户 |

### 3.1 回滚执行流程

```
1. 发现异常
   → 2. 立即停止灰度/全量发布（禁止新请求到新版本）
   → 3. 评估影响范围（检查错误日志、告警通知）
   → 4. 选择回滚方式（代码回滚 / DB 回滚 / 配置回滚）
   → 5. 执行回滚操作
   → 6. 验证回滚成功（检查关键指标恢复）
   → 7. 通知受影响用户（如涉及计费偏差需补偿）
   → 8. 排查根因
   → 9. 修复后重新走灰度流程
```

### 3.2 回滚条件触发规则

| 触发条件 | 阈值 | 动作 |
|---------|------|------|
| 错误率突增 | > 5% (相对于基线) | 自动暂停发布，通知运维 |
| P99 延迟翻倍 | > 2x 基线 | 自动暂停，通知运维 |
| 计费偏差 > 0 | 任何偏差 | 自动回滚计费变更 |
| 用户投诉 > 3 起 | 人工判断 | 运营决策是否回滚 |
| 对账偏差 > ¥10 | 自动告警 | 运营决策是否回滚 |

## 4. 用户通知策略

| 升级类型 | 提前通知 | 期间通知 | 结束后通知 |
|---------|---------|---------|---------|
| 停服升级（30 分钟以上） | 提前 48h 站内信 + 邮件 | 首页公告横幅 | 服务恢复通知 |
| 灰度升级（不影响用户） | 无需通知 | 无需通知 | 变更日志 |
| 接口变更（不兼容） | 提前 7 天通知开发者 | API 文档更新 | 发布公告 |
| 定价变更 | 提前 7 天通知 + 邮件 | 价格页面更新 | 变更日志 |

### 4.1 通知模板

**停服通知：**

> 通知标题：3cloud 平台计划内维护通知
> 通知内容：
> 尊敬的 3cloud 用户：
> 为提升服务质量，我们计划于 2026-08-05 02:00-03:00（UTC+8）进行系统升级维护。
> 维护期间 API 服务将暂停 30-60 分钟，请提前安排您的业务。
> 维护完成后，您将可以正常使用所有服务。
> 如有疑问，请联系客服。

**计费变更通知：**

> 通知标题：模型价格调整通知
> 通知内容：
> 尊敬的 3cloud 用户：
> 自 2026-08-10 00:00 起，以下模型价格将进行调整：
> - deepseek-chat：输入 ¥0.0100 → ¥0.0120 / 1K tokens
> - gpt-4o：输入 ¥0.0200 → ¥0.0180 / 1K tokens
> 其他模型价格保持不变。详情请查看价格页面。
> 如有疑问，请联系客服。

## 5. 升级检查清单

```
□ 1. 影响评估完成（填写 14.1 影响评估清单）
□ 2. 数据库备份完成（完整备份 + 增量备份）
□ 3. 回滚方案已验证（在测试环境验证过回滚脚本）
□ 4. 灰度配置就绪（Nginx/API 网关灰度分流规则已配置）
□ 5. 用户通知已发送（如需提前通知）
□ 6. 监控告警已配置（错误率、P99 延迟、计费偏差、对账偏差）
□ 7. 对账脚本已准备（升级前后对账结果对比）
□ 8. 客服已被告知升级计划（准备好 FAQ 和话术）
□ 9. 升级窗口确认（非业务高峰期，建议凌晨 02:00-06:00）
□ 10. 回滚联系人确认（运维、开发、财务各确认一个回滚决策人）
□ 11. 升级操作手册已准备（每步操作的详细步骤和预期结果）
□ 12. 升级后观察期确认（全量发布后至少观察 24h）
```
