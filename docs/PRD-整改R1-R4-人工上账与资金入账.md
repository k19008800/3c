## 2. 背景与目标

### 2.1 背景（引用整改方案）

整改方案（RECT-2026-ADMIN-RECHARGE-001）以"管理员给用户 `13819008800@163.com` 充值 ¥1,000"为场景完成系统演练，结论：该业务**可以完成，但只能借道「手动调账」路径**；语义上最应走的「人工上账」路径缺少创建入口，且两条资金路径共暴露 **4 个 P0** 问题：

| # | 问题 | 核心影响 |
|---|------|---------|
| P0-1 | 人工上账无创建入口：只有列表 + 审核，无创建能力；用户端 `ALLOWED_METHODS` 不含 `manual` | 管理员"充值"语义无正规通道，只能借道调账，财务口径混乱 |
| P0-2 | 余额账户缺失无兜底：入账统一 `UPDATE customer_balances ... RETURNING`，无余额行即 404 `BALANCE_NOT_FOUND`；`initBalance` 仅在注册时调用 | 历史/异常用户充值直接失败且无自愈 |
| P0-3 | 权限"假授权"与按角色硬编码：权限树授予 `finance.topup`，但路由层只放行 `admin/super_admin`，未按权限点鉴权 | finance 角色"有权限却操作不了"，权限体系形同虚设 |
| P0-4 | 入账后无用户通知：人工上账审核、调账生效、充值订单审核均未触发站内信/邮件 | 用户无感知 → "充值未到账"客诉、SLA 风险 |

### 2.2 阶段目标

阶段一（约 1 周）完成 P0 止血，使下述主流程可完整闭环：

```
管理员登录 → 定位用户（搜索/核对状态与余额）→ 选择资金路径
  ├─ 对公/线下已到账，凭凭证入账 → 【R1 人工上账：创建 → 待审 → 审核通过 → 入账】
  ├─ 平台赠送/补偿/纠错       → 调账（现状保留，仅权限收敛 R3）
  └─ 用户已提交对公转账       → 充值订单审核（现状保留，通知补齐 R4）
入账时 → 【R2 无余额账户自动建户兜底】→ 余额增加 + 流水
入账后 → 【R4 通知用户：站内信必发 + 邮件按偏好】
全程   → 【R3 权限点鉴权：finance.topup / finance.adjust，越权 403】
```

### 2.3 产品设计原则对齐

- P1（不可降级）：本期涉及页面/按钮全部按本 PRD 第 7、8 节实现 `[?]` 帮助；
- P3（操作可逆与安全优先）：发起上账、审核入账均为资金写操作，前端必须二次确认；全部写审计日志；
- P4（状态可见性）：创建/审核成功/失败必须有明确 toast 反馈，列表状态实时刷新，空列表有引导文案。

## 3. 功能模块清单

### 3.1 R1 人工上账创建入口（对应 P0-1）

#### 3.1.1 业务规则

1. **谁可以发起**：持有权限点 `finance.topup` 的操作者（finance / admin / super_admin）。无该权限点 → 前端隐藏/禁用入口 + 后端 403（详见 R3）。
2. **给谁上账**：目标用户必须是已存在的平台用户（`users` 表），通过用户搜索选择，搜索维度：**邮箱（精确/模糊）、用户 ID（精确）、手机号（精确，仅对已绑定手机号的用户）**。
3. **入账类型（建议新增产品字段，待裁决 A6）**：为驱动"凭证/转账单号是否必填"，创建时需选择入账类型：
   - `bank_transfer`（对公/线下到账入账）：凭证 + 转账单号**必填**；
   - `grant`（平台赠送/补偿/纠错/客服补单）：凭证 + 转账单号**选填**（原因 note 必填）。
4. **金额约束**：> 0；≤ 单笔上限（**裁决建议 ¥50,000**，见 §9 差异说明 A1）；最多 2 位小数（元/分）。超限直接拒绝创建，提示"大额入账需走分级审批（后续版本开放）"。
5. **凭证**：对公到账场景必填，格式 JPG/PNG/PDF，≤ 5MB（对齐 ref-2.2.6 §7.2.1 凭证要求）。
6. **转账单号唯一性**：若填写 `transfer_no`，全平台唯一 —— 同一转账单号重复创建被拒绝（对应整改方案 R1 验收"重复创建同单号被拒"，也是防重复入账的第一道闸）。
7. **审核规则（本期）**：单步审核，对齐现状（`pending → paid/failed`）；**不做金额分级、不强制"创建人 ≠ 审核人"** —— 分级审批与职责分离属 **R5 后续阶段，本期预留**。
8. **2FA 预留说明**：按 `SPEC-§20` L3 分层，资金写操作（发起上账 / 审核入账）应要求 2FA + 二次确认；**本期不实现 2FA 校验（R7 阶段接入）**，但创建/审核交互流程须预留二次确认弹窗位（前端二次确认本期即实现）。
9. **入账后动作**（联动 R2/R4）：审核通过 → 余额入账（自动建户兜底）→ 写资金流水 → 触发 `recharge_success` 通知 → 写审计。
10. **错误入账处理**：本期无独立冲正入口；若审核通过后发现错误，由 admin/super_admin 走现有调账（红字冲销）纠正，正式方案见 R12（后续阶段）。

#### 3.1.2 字段定义表

| 字段 | 业务含义 | 必填 | 类型 | 长度/精度 | 校验规则 | 备注 |
|------|---------|------|------|-----------|---------|------|
| `user_id` | 目标用户 ID | ✅ | integer | — | 用户必须存在且状态正常（见 A8） | 通过用户搜索选择，展示邮箱/名称/当前余额/状态 |
| `amount` | 入账金额（CNY） | ✅ | numeric | 18,2 | >0；≤50,000；最多 2 位小数 | 与用户端充值金额口径一致 |
| `topup_type` | 入账类型 | ✅ | enum | — | `bank_transfer` / `grant` | 建议新增；驱动凭证/单号必填逻辑（待裁决 A6） |
| `note` | 入账原因 | ✅ | text | ≤500 字 | 非空（trim 后）；对公填"银行流水核实说明"，赠送填"赠送/补偿原因，可含工单号" | 列表页展示；驳回后作驳回原因展示源之一 |
| `evidence` | 凭证附件 | 条件必填 | 文件 | JPG/PNG/PDF ≤5MB | `bank_transfer` 必填；`grant` 选填 | 对公到账凭证/回单截图；正式凭证落库方案见 R9（后续阶段） |
| `transfer_no` | 转账单号 | 条件必填 | varchar | ≤64 | `bank_transfer` 必填；填写则全平台唯一 | 银行流水号；重复创建同单号被拒 |
| `currency` | 币种 | 系统默认 | varchar | 10 | CNY | 本期仅支持 CNY |
| `order_no` | 订单号 | 系统生成 | varchar | 50 | 唯一，生成规则沿用现有充值订单规则 | 创建时自动生成，用户不可填写 |
| `status` | 订单状态 | 系统 | enum | — | `pending`（初始）/ `paid` / `failed` | 存储层现有枚举 |
| `paid_at` | 入账时间 | 系统 | timestamp | — | 审核通过时写入 | — |
| `reviewer_id` | 审核人 | 系统（审核时写入） | integer | — | — | **建议本期落库**（低成本审计基础）；正式凭证/审核人落库方案 R9 完善 |
| `review_note` | 驳回原因 | 驳回时必填 | text | ≤500 字 | 驳回操作必须填写 | 管理员侧可见；后续可透出给用户 |

#### 3.1.3 校验规则（创建时）

| # | 校验项 | 规则 | 失败提示（产品侧文案） |
|---|--------|------|----------------------|
| C1 | 用户存在性 | `users` 表存在该用户 | "用户不存在，请重新搜索" |
| C2 | 用户状态 | 状态为正常（active） | "该用户处于禁用/冻结状态，请先在用户管理中解锁后再上账"（待裁决 A8） |
| C3 | 金额下限 | `amount > 0` | "入账金额必须大于 0" |
| C4 | 金额上限 | `amount ≤ 50,000` | "单笔上账金额不得超过 ¥50,000；大额入账请走分级审批（后续版本开放）" |
| C5 | 金额精度 | 最多 2 位小数 | "金额最多保留 2 位小数" |
| C6 | 原因必填 | `note` 非空且 ≤500 字 | "请填写入账原因（对公到账请注明核实说明）" |
| C7 | 凭证必填 | `bank_transfer` 必须上传凭证 | "对公到账必须上传转账凭证（JPG/PNG/PDF，≤5MB）" |
| C8 | 单号必填 | `bank_transfer` 必须填写转账单号 | "对公到账必须填写转账单号" |
| C9 | 单号唯一 | `transfer_no` 不与已有订单重复 | "该转账单号已存在上账记录，请核实是否重复入账" |
| C10 | 凭证格式/大小 | JPG/PNG/PDF，≤5MB | "凭证格式仅支持 JPG/PNG/PDF，且不超过 5MB" |

#### 3.1.4 状态流转

```
创建（pending，写入订单 + 凭证 + 单号 + 审计）
   │
   ├── 审核通过（approve）→ paid（入账：余额增加 + 流水 + 通知 + 审计）
   └── 审核驳回（reject）→ failed（记录驳回原因 + 审计）
```

- 状态机约束：仅 `pending` 可流转；已 `paid` / `failed` 的单据不可再次审核（并发/重复审核由状态条件原子更新拦截，现状已具备）。
- 本期不提供"取消"操作（创建后若需撤回，走驳回；与现状行为一致）。
- 审核结果语义：`paid` = 资金已入账；`failed` = 未入账、单据关闭。

#### 3.1.5 前端交互（产品描述）

**页面落点**：管理后台 → 财务 → **人工上账**页（现有列表页，路由路径沿用现状）。

**交互流程**：

1. 列表页顶部操作栏新增 **[发起上账]** 按钮（右上，`[?]` 帮助见第 8 节）；无 `finance.topup` 权限的角色该按钮不渲染。
2. 点击后弹出**发起上账表单弹窗**：
   - **用户选择器**：搜索框（支持邮箱/手机号/用户ID）→ 下拉/列表选中 → 回显"邮箱 · 名称 · 用户ID · 当前余额 · 状态"；状态非正常时显示警示条"该用户处于禁用/冻结状态，请先解锁"（提交被拦截）；
   - **入账类型**：单选"对公到账 / 平台赠送（赠送·补偿·纠错）"；
   - **入账金额**：数字输入框，旁注"最低 ¥0.01，最高 ¥50,000"；实时展示"到账后余额预览"；
   - **入账原因**：textarea（≤500 字），占位提示示例；
   - **凭证上传**：拖拽/点击上传；对公到账显示"* 必填"；上传后显示文件名与大小；
   - **转账单号**：对公到账显示"* 必填"；失焦时做唯一性校验（重复即红字提示）；
   - 提交按钮 **[确认提交]**。
3. 点击确认提交 → **二次确认弹窗**（P3 要求）：汇总展示"用户 / 金额 / 类型 / 到账后余额 / 转账单号"，提示"提交后进入待审核，审核通过前不改变用户余额"，[确认] / [返回修改]。
4. 提交成功 → toast "已提交，等待审核" → 弹窗关闭 → 列表刷新，新单据以 `pending` 状态置顶展示。
5. 列表操作列（仅 `pending` 行）显示 **[审核通过]** / **[驳回]**：
   - 审核通过 → 二次确认弹窗（"确认后将 ¥X 计入用户余额并通知用户"）→ 成功 toast "上账成功，金额已入账" → 行状态变 `paid`；
   - 驳回 → 弹窗必填"驳回原因" → 行状态变 `failed`，原因展示于列表"驳回原因"列。

### 3.2 R2 余额账户兜底（对应 P0-2）

#### 3.2.1 业务规则

1. **核心规则**：任何资金入账路径（人工上账审核通过 / 调账生效 / 充值订单审核通过）在更新余额前，若目标用户**不存在 `customer_balances` 余额行**，系统**自动创建零余额账户后再入账**；建户与入账在同一事务内完成，保证原子性。
2. **幂等，不重复建户**：建户采用"存在即跳过"语义（复用注册时 `initBalance` 的 `ON CONFLICT DO NOTHING` 行为），并发请求下不会重复建户、不会覆盖已有余额。
3. **覆盖范围**：三条入账路径统一收口到同一"建户兜底 + 更新"逻辑（现状各路由各自 `UPDATE ... RETURNING`，需收口；实现方式由 arch-agent 定，本 PRD 只定业务规则）。
4. **用户不存在**：建户依赖用户外键；若用户本身不存在（脏数据），入账失败并返回友好错误"用户不存在"（R1 创建时已前置校验；调账路径本期同步补校验，见边界表 B2）。
5. **用户端余额展示**：无余额行用户登录用户端后余额展示为 **¥0.00**（现状余额查询已对无行用户返回零值占位，无感）；自动建户后与正常零余额用户完全一致，无需用户端改动，仅需回归验证。
6. **对账影响**：自动建户为**零金额**操作，不改变任何资金合计口径；建户事件须写入审计/日志（来源标识 `auto_create`），供对账排查时定位"账户为何存在/何时建立"；§29 对账口径无新增差异。
7. **审计**：自动建户作为入账事务的一部分，随入账审计记录（含 `balance_before` 空、建户标识）。

#### 3.2.2 字段定义表（自动建户）

| 字段 | 值 | 说明 |
|------|-----|------|
| `user_id` | 目标用户 ID（唯一） | 建户前置条件：用户存在 |
| `total_balance` | 0 | 零余额建户 |
| `available_balance` | 0 | 零余额建户 |
| `frozen_balance` | 0 | 零余额建户 |
| `currency` | CNY | 与默认币种一致 |
| `version` | 0 | 初始版本号 |
| `created_at` / `updated_at` | 当前时间 | 系统写入 |

#### 3.2.3 校验规则

| # | 校验项 | 规则 |
|---|--------|------|
| D1 | 用户存在 | 建户前用户必须存在于 `users` 表；不存在 → 友好错误，不入账 |
| D2 | 建户幂等 | 同一用户并发建户只生效一次（不重复建户、不覆盖已有行） |
| D3 | 事务原子 | 建户 + 余额更新 + 流水写入在同一事务，任一失败整体回滚 |

#### 3.2.4 状态流转

- R2 无独立状态流转：自动建户是**入账事务内的前置步骤**（"无余额行 → 建户 → 更新余额 → 写流水"），不产生任何可被管理员操作的独立单据状态；外部可见的状态变化只有入账路径本身的 `pending → paid`。

#### 3.2.5 前端交互

- 无新增页面/按钮。管理员操作无感知（自动完成），仅要求：入账成功后列表/台账展示"入账成功"且**不出现 404 报错**；用户端余额卡正确显示入账后金额。

### 3.3 R3 权限点鉴权对齐（对应 P0-3）

#### 3.3.1 权限点定义表

| 权限点 | 业务含义 | 现状 | 本期动作 | 授予角色 |
|--------|---------|------|---------|---------|
| `finance.topup` | 人工上账（创建 + 审核） | 权限树已授予 finance/admin/super_admin，但路由只放行 admin/super_admin（假授权） | 路由层改为按权限点鉴权，使授权真实生效 | finance、admin、super_admin |
| `finance.adjust` | 手动调账（发起 + 审核） | **权限树中不存在该权限点**（当前仅有 refund/topup/invoice/reconciliation） | **建议新增该权限点**（待裁决 A5）并接入调账路由 | 仅 admin、super_admin |
| （充值订单审核） | 充值订单 audit 通过 | 路由放行 admin/super_admin | 本期**保持现状**；是否开放给 finance 见待裁决 A4 | admin、super_admin（现状） |
| `super_admin` 通配 | 全部权限 | 现有 `*` 语义 | 保持 | super_admin |

> 权限点与 SPEC-§30 权限位映射：`finance.topup` ≈ §30「资金操作」组 `RECHARGE_MANAGE（管理充值）`；`finance.adjust` 对应 §30 `BALANCE_ADJUST（调整余额，二次确认）` 的管理侧操作位。两套口径由 arch-agent 对齐，本 PRD 以权限树现有 key 为准。

#### 3.3.2 业务规则

1. **鉴权模型**：资金路由的访问控制从"角色白名单（role 字段）"改为"**权限点校验**"——校验操作者是否持有对应权限点；`super_admin` 持通配权限点，天然放行。实现（requirePerm 中间件）由 arch-agent 设计，本 PRD 只定业务映射。
2. **人工上账**（列表 / 创建 / 审核）：要求 `finance.topup`。→ finance 角色**可发起、可审核**人工上账（对齐本任务要求；整改方案验收以"finance 可审核人工上账"为底线）。
3. **手动调账**（发起 / 审核，含红字冲销入口）：要求 `finance.adjust`（仅 admin/super_admin）。→ finance 角色**不可发起调账**。
4. **审批级别维持现状**：调账的免审批/一级审批逻辑（<¥10,000 免审）本期不改造，仅做权限点收敛（分级审批属 R5）。
5. **越权反馈规范**：
   - **前端**：按钮/入口按当前操作者权限点渲染——无 `finance.topup` 不显示"发起上账/审核"；无 `finance.adjust` 不显示"发起调账"；不出现"能看见但点不了"的假入口。若因权限变化导致页面局部失效，用禁用态 + tooltip"您暂无该操作权限"。
   - **后端**：越权请求一律返回 **403**，统一错误码与文案（错误码取值由 arch-agent 定，文案建议："无权执行该操作，请联系管理员（PERMISSION_DENIED）"）。**前端不得以 200 掩盖 403**，需按 403 统一提示并可选跳转权限说明。
6. **权限树同步**：`ROLE_PERMS` 增补 `finance.adjust`（admin / super_admin 授予）；用户权限详情接口（有效权限 + 权限树）能正确反映 finance 拥有 `finance.topup`、不拥有 `finance.adjust`。
7. **审计**：所有鉴权拒绝不写业务审计；通过的操作照常写审计（含操作者）。

#### 3.3.3 字段定义 / 校验规则 / 状态流转

- R3 无业务字段、无业务状态流转：字段定义由「权限点定义表」（3.3.1）替代，校验规则即"操作者有效权限是否含目标权限点"（缺失 → 403），状态概念不适用。

#### 3.3.4 前端交互

- 无新页面。现有"人工上账"页与"调账"入口按权限点控制可见性；权限不足时的交互反馈见上。

#### 3.4.1 通知时机（触发点）

| # | 触发点 | 事件名 | 状态前提 | 本期是否覆盖 |

| N4 | 调账生效（调减/扣减） | — | — | ❌ 本期不覆盖（扣减属余额变动类，事件与文案后续阶段定义，见 §9 差异项 9） |

|------|------|------|

#### 3.4.3 通知文案要点与模板变量

**站内信与邮件共用的文案要点**（模板由运营侧维护，本期给出变量与要点）：

| 要点 | 变量建议 | 示例 |
|------|---------|------|
| 入账金额 | `{amount}` | ¥1,000.00 |
| 到账后余额 | `{balance_after}` | ¥1,250.00 |

**文案骨架（示例）**：

#### 3.4.4 通知失败降级

1. **不影响主交易**：通知发送失败（站内信写入失败 / 邮件发送失败）不得回滚入账事务、不得阻断审核响应；
2. **留痕可查**：通知记录落库（含渠道、状态 success/failed、失败原因、重试次数），满足整改方案 R4 验收"通知记录可查"；
3. **重试与告警**：失败通知进入重试（次数与间隔由 arch-agent 按通知引擎现状定），重试耗尽后告警给运维；本期不阻断业务。

#### 3.4.5 与 SPEC-§22 通知偏好设置的衔接

- 复用 §22.6 的 `recharge_success` 事件标识与 `user_notification_preferences`（`inAppPreferences` / `emailPreferences` JSONB、`emailEnabled`、`emailFrequency`）；
- 差异点：§22 事件表中 `recharge_success` 站内信"可关闭"，本期产品裁决建议**改为强制开启**（见 §9 差异 A3，需同步修订 §22 表格）；
- 用户端通知偏好页（`/console/settings/notifications`）对 `recharge_success` 站内信显示"不可关闭（资金到账通知）"，邮件开关维持可配置。

#### 3.4.6 前端交互

- 管理端无新页面；人工上账列表建议增加"通知状态"列（已通知 / 通知失败 / 无需通知），用于管理员核验（整改方案"到账核验"环节）；
- 用户端：站内信出现在用户通知中心（按现有通知中心展示）；邮件按模板发送，用户无需操作。

## 7. ### [?] 页面帮助

> 数据源：以下内容作为人工上账页 `PageHelp` 弹窗内容（pageKey 建议 `finance-manual-topup`，最终由 frontend-agent 按现有帮助组件约定落地）。

**页面名称**：财务 → 人工上账

**适用角色**：财务（finance）、管理员（admin / super_admin）；调账入口仅 admin / super_admin 可见

**功能定位**：管理员/财务为指定用户账户进行资金入账。线下/对公转账已到账的，凭凭证走「人工上账」；平台赠送/补偿/纠错的，走「手动调账」。全过程权限点校验、审核留痕、入账必通知。

**核心操作**：
1. 搜索用户（邮箱 / 手机号 / 用户ID）→ 核对状态与当前余额
2. 点击「发起上账」→ 选择入账类型（对公到账 / 平台赠送）→ 填写金额、原因、凭证、转账单号 → 确认提交
3. 待审核列表 → 审核通过（入账）或驳回（填原因）
4. 审核通过后用户收到站内信 + 邮件（按偏好），管理员可在列表核验到账

**注意事项**：
- 涉及资金变动，提交与审核均需二次确认，全程写审计日志
- 对公到账必须上传凭证（JPG/PNG/PDF，≤5MB）并填写转账单号；同一转账单号不可重复入账
- 单笔上账金额不超过 ¥50,000；大额入账请走分级审批（后续版本开放）
- 用户无余额账户时系统自动建户后入账，无需人工干预
- 禁用/冻结用户需先解锁再上账
- 本期为单步审核（创建≠审核的职责分离在后续版本生效）

**常见问题**：
Q: 为什么 finance 角色看不到「发起调账」？
A: 调账仅限 admin / super_admin；finance 角色可发起并审核人工上账。
Q: 入账后用户余额没变？
A: 请检查单据状态：`pending`（待审核）尚未入账；`paid`（已入账）后仍未见变动请检查流水与对账一致性（联系技术排查）。
Q: 提交时提示"该转账单号已存在上账记录"？
A: 该转账单号已有一笔上账，请核实是否重复入账，勿重复创建。
Q: 用户提示"未收到到账通知"？
A: 入账成功即发站内信（不可关闭）；邮件按用户偏好发送，可提示用户在「设置 → 通知偏好」开启邮件通知。
