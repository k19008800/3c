### 🟠 P1（资金安全 / 高优先级，必须清零）

#### P1-1 调账驳回缺少原子状态守卫：并发"驳回 × 通过"可致"已入账却显示已驳回"

- **位置**：`api/src/routes/admin-adjust.ts:690-692`（`db.update(...).set({status:'rejected',...}).where(eq(adjustmentRecords.id, adjustId))`，**WHERE 无 status 条件**）
- **描述**：reject 先预读 `rec.status` 校验，随后 UPDATE 仅按 id 匹配。若并发一个 approve（守卫 `status='pending'` 0 行→409 回滚）先提交成功（余额已入账），reject 的 UPDATE 仍会命中该行并覆盖为 `rejected` → **资金已加、单据显示已驳回**，账实矛盾且无法从状态机自愈。对比：人工上账/充值订单 reject（`admin-finance-missing.ts:601`、`recharge.ts:605`）均带 `status='pending'` 守卫。
- **违反条款**：`coding-standards-control-logic.md §二`（状态转换原子守卫）、ARCH v1.1 §2.2.3（"仅当前环节可流转（原子守卫）"、E6/E7）。
- **修复建议**：`UPDATE ... WHERE id=? AND status IN ('pending','pending_level2','pending_super')`，0 行 → 409 `ORDER_ALREADY_PROCESSED`；补并发 reject×approve 测试。

#### P1-2 退款审核状态更新与入账不在同一事务：addBalance 失败 → "已通过"但未退款，且无法重试

- **位置**：`api/src/routes/admin-finance-stats.ts:531-552`（先 `db.update(refund_requests status='approved')`，再 `await addBalance(...)`，两者均独立自动提交）
- **描述**：UPDATE 先落库提交，`addBalance` 若抛错（DB 抖动/余额行异常），退款申请已 `approved` 但用户未收到退款；再次审核命中 `REFUND_ALREADY_PROCESSED`(409) 无法补偿，资金丢失需人工干预。与同一文件 review 端点外的其他资金路径（creditBalance 均事务内）不一致。
- **违反条款**：`coding-standards-api-db-test.md §2.5`（多表写入必须 `db.transaction()`）、ARCH v1.1 §2.2.2（"仅最终批准的事务内调 creditBalance"）。
- **修复建议**：`db.transaction(tx => { UPDATE 守卫（status='pending'）0 行→409；tx 内 creditBalance/addBalance；})` 整体原子。

#### P1-3 默认 `hard_limit=100,000` 与终裁 B3 / 边界 E12 冲突：单笔 >10 万的人工上账与调账调增创建即 429，tier3 终审链默认配置下不可达

- **位置**：`api/src/lib/finance-rules.ts:51`（`CREDIT_HARD_LIMIT = 100_000`）、`api/src/services/billing/credit-limit.ts:179-188`（`projectedYuan = usedYuan + amountYuan`，> hard → 429）、调用点 `admin-finance-missing.ts:426-436`、`admin-adjust.ts:281-291`
- **描述**：判定含本笔金额。全新操作人首笔人工上账/调增 15 万 → `projected=150,000 > hard=100,000` → 429 `DAILY_LIMIT_EXCEEDED`（文案"今日累计加钱将超过限额 ¥100,000"，对单笔大额语义误导）。于是：① §10 B3 终裁"人工上账上限 50,000→1,000,000、tier3 对人工上账有效"落空（100,000~1,000,000 区间全部被 429 拦截）；② E12"调账 >10 万 → 终审档三人链"落空（仅用户自助充值订单因 B10 不计限额能走到 tier3）。测试作者已知晓该冲突并以 `withRaisedHardLimit`（hard 调 1,000,000）绕过（`admin-manual-topup.test.ts:63-71`、`admin-adjust.test.ts:396-399`），即**默认配置下该验收路径不可达**。
- **违反条款**：ARCH §10 B3 终裁、PRD §5 E12、§6 R6 验收"9×¥9,999 第 6 笔升级"（soft 语义即已覆盖拆分，hard 属额外闸）。
- **修复建议**：明确 hard 语义并修正默认值——若 hard 是"同维度 24h 累计硬顶"（合理），默认值应 ≥ 单笔上限 1,000,000（或 ≥ super_review_threshold），否则单笔大额被误拒；或将 hard 判定改为"不含本笔的既有累计"。无论取哪种，需调度/arch 补记该终裁并同步 ARCH §2.1 配置表与 PRD 校验表。

## 4. 通过项摘要（实现侧质量确认）

1. **生产代码 typecheck 0 错误**（51 处错误全部在测试侧），R5–R7 后端主链路可编译。
