# 渠道化改造-架构评审报告

> 评审对象：`docs/SPEC-渠道化术语统一与用户自选渠道定价.md` / `docs/PRD-渠道化术语统一与用户自选渠道定价.md`
> 
> 评审范围：数据层、后端 API、路由锁定、`/me/models` 兼容、D2 约束一致性
> 
> 结论先行：**有条件通过**。Spec 的总体方向正确，但要进入开发前，必须补齐若干架构边界，否则会出现**定价口径不一致、渠道锁定后计费不一致、以及数据重复导致的非确定性查询**。

---

## ① 总体结论

**结论：有条件通过。**

原因：
1. 数据层现有表结构**可以表达**“同模型多渠道 + 多 pricing_group 生效价”，不一定需要立即新增大改 DDL。
2. 但当前实现里，`getPricingForModel` 仍是**模型级合并价**，而 Spec 要求的“用户自选渠道”与“渠道价目公布”是**渠道级价格语义**，两者必须显式分层，否则展示价、路由价、扣费价容易不一致。
3. `selectChannel` 当前没有 `channelCode` 入参，Spec 的“按指定渠道锁定”属于合理增量，但要把**自动路由**与**显式锁定**路径严格分开，并补齐错误码边界。
4. `/me/models` 的“平铺字段兼容 + channels[]”方案是可行的，但平铺字段只能作为**旧组件兼容的最低价展示**，不能作为用户侧权威价。

**必须修正后再推进开发：**
- 渠道锁定后的**计费口径**必须与所选渠道一致，不能继续仅靠模型级 `getPricingForModel`。
- `supplier_models` 与 `vendor_pricing` 需要明确**去重/排序/唯一性口径**，否则多行命中时结果不确定。
- `parseModelVendor` / `selectChannel` 的错误码与任务型渠道边界要补清楚，避免把普通模型锁定逻辑误扩散到 task 供应链。

---

## ② 数据层结论

### 结论

**总体可支撑，但“无需 DDL”只能算功能上可用，不算架构上足够稳。**

### 现状核对

- `supplier_models`：`supplier_id + model_name` 在语义上确实可以定位“某渠道提供的某模型”。
- `vendor_pricing`：`pricing_group` 非唯一，天然支持同模型多组价格。
- `suppliers.code`：现有 `unique`，适合作为渠道唯一编码。

### 评审判断

1. **“同模型多渠道”**：现有结构可表达，不需要新增关系表。
2. **“多 pricing_group 生效价”**：现有结构可表达，但**查询必须定义明确选择规则**。
3. **`(supplier_id, model_name)` 是否足够唯一定位？**
   - 语义上够用；
   - 但**当前 schema 没有复合唯一约束，也没有复合索引**，因此仅靠业务习惯并不稳。
4. **`vendor_pricing` 是否需要补充查询口径？**
   - 是。当前 `getPricingForModel` 对 `vendor_pricing` 是“按 group/model 取第一条”，没有显式的稳定排序；
   - 若同一 `(supplier_model_id, pricing_group)` 出现多条记录，结果可能非确定。

### 建议

- **最低要求**：补一个明确的查询口径，按以下顺序取价：
  1. `supplier_id + model_name` 精确定位渠道模型；
  2. `pricing_group = ctxGroup` 命中则优先；
  3. 否则回退 `pricing_group = 'default'`；
  4. 若同组多条，必须按 `effective_from / updated_at / id` 明确排序。
- **更稳妥方案**：为 `supplier_models(supplier_id, model_name)` 增加复合唯一或至少复合索引；为 `vendor_pricing(supplier_model_id, pricing_group)` 增加稳定约束或应用层去重规则。

### 对 Spec 的判断

- “`supplier_models` 天然支持一个模型名 × 多个渠道多条记录”——**成立，但需要补充去重约束/排序口径**。
- “`supplier_models` / `vendor_pricing` 无需 DDL 即可支撑”——**功能上成立，架构稳健性上不充分**。

## ③ 定价改造结论

### 结论

**新增 `getChannelPricing(model, channelCode, ctx)` 方向合理，且复用度高；但它不能替代主计费链的上下文传递。**

### 现状事实

- `getPricingForModel(model, ctx)` 当前是**模型级合并价**：
  - L5 活动价
  - L4 用户分组价
  - L3 代理价
  - L2 默认模型覆盖价
  - L1 平台兜底价
- 它只关心“这个模型今天该按什么价算”，**不关心具体选了哪个渠道**。

### 对 Spec 的评审

1. **新增 `getChannelPricing` 是否合理？**
   - 合理，而且是必须的。
   - 因为用户侧要展示“每个渠道各自的生效价”，这是模型级聚合函数做不到的。
2. **复用度多高？**
   - 很高。`L4` 的分组解析逻辑、`vendor_pricing` 的价格解析、缓存价回退逻辑都可以复用。
   - 最好不要复制一份定价逻辑，而是抽一个底层 helper：
     - 先定位渠道模型
     - 再复用同一套“group → default → fallback”解析
3. **有无更优方案？**
   - 更优的做法不是只加一个 `getChannelPricing`，而是把“**选路结果**”作为计费上下文的一部分：
     - 自动路由时：由 `selectChannel` 返回具体 `supplierModelId` / `channelCode`，再按这个渠道算价；
     - 显式锁定时：直接按锁定渠道算价。
   - 这样“展示价”与“实际扣费价”可以一致。
4. **对现有计费主链是否有破坏风险？**
   - **有。**
   - 现在 `chat.ts`、`openai-compat.ts`、`responses.ts`、`messages.ts` 等主链路依赖 `getPricingForModel`。
   - 如果新增渠道价却不把路由结果传给计费，出现以下问题：
     - 用户看到的是渠道 A 的价，实际路由到了渠道 B，却仍按模型聚合价扣费；
     - 或者锁定渠道后仍按默认模型价扣费。

### 评审结论

- **`getChannelPricing` 应新增。**
- **`getPricingForModel` 不应被替代，应继续保留现有兼容语义。**
- **但主链必须补一个“路由结果 → 计费上下文”的闭环。**

### 必须修正项

- 若请求带 `channelCode` 或路由已选定渠道，则计费层必须能拿到该渠道信息。
- 如果本期不打算改所有链路，则 Spec 必须明确：
  - `getChannelPricing` 仅用于**价格矩阵展示**；
  - 实际扣费仍按**现有模型级主链**，并说明暂不支持按渠道精确扣费。

如果不明确这一点，本次改造会产生**展示价 ≠ 扣费价**的新争议，这与 PRD 的目标冲突。

## ④ 路由锁定结论

### 结论

**“parseModelVendor + selectChannel 增加 channelCode 入参”是合理的，但要限定只影响显式锁定路径，不能污染自动路由和任务型渠道逻辑。**

### 现状事实

- `selectChannel(model, opts)` 当前只支持：
  - `groups`
  - `userId`
- 路由逻辑是“扫描候选渠道 → 过滤分组 → 过滤熔断 → 选 key”。
- `selectTaskChannel(apiType, opts)` 是另一条任务型链路，靠 `apiType` 选渠道，不是模型路由。

### 评审判断

1. **新增 `channelCode` 入参**：合理。
   - 显式锁定时应优先查 `suppliers.code`。
   - 验证：`active`、分组可见、`supplier_models` 提供该 model、对应 key 可用。
2. **是否会破坏自动路由？**
   - 不会，前提是 `channelCode` 仅在显式传参时生效。
   - 未传时应完全保持现有自动路由路径。
3. **是否会破坏 `selectTaskChannel`？**
   - 有风险。
   - 任务型渠道没有模型名语义，不能直接套 `parseModelVendor`。
   - 如果要支持任务依赖动作锁回原渠道，应该在任务记录中保存原渠道信息，而不是依赖模型字符串拆解。
4. **错误码设计是否合理？**
   - 基本合理，但有两个边界需要补：
     - `CHANNEL_NOT_FOUND`：仅适用于 `suppliers.code` 真不存在；
     - `CHANNEL_UNAVAILABLE`：适用于存在但停用、维护、apiType 不符、或不可服务当前分组；
     - `GROUP_FORBIDDEN`：适用于**显式锁定**时确认组不可见。
   - 对自动路由，不应把“候选被过滤”转成这些错误码，而应继续按现有兜底逻辑找其他渠道。

### 建议

- `parseModelVendor` 只做纯解析，不做业务判断。
- `selectChannel` 才做校验和错误归类。
- `selectTaskChannel` 只在任务闭环需要时接受 `channelCode`，并且必须先校验 `apiType` 一致。
- 错误返回要统一包装，避免不同路由返回不一致 payload。

## ⑤ 兼容结论

### 结论

**`/me/models` 保留平铺字段作最低价兼容 + 新增 `channels[]` + `DEFAULT_MODELS` 兜底，方案整体稳，但必须限定平铺字段只服务旧组件。**

### 评审判断

1. **`channels[]` 作为新主数据结构**：正确。
2. **平铺字段保留**：可行，但只能当兼容层。
3. **`DEFAULT_MODELS` 兜底**：合理，能防止 DB 空时回归。
4. **风险点**：
   - 如果平铺字段被前端当作最终价格展示，就会和 `channels[]` 形成双口径；
   - 如果 DB 部分缺失而直接回退 `DEFAULT_MODELS`，可能掩盖数据不完整问题。

### 建议

- `/me/models` 的平铺字段请明确标注为：
  - **最低价兼容字段**，仅供旧 Playground/下拉使用。
- `channels[]` 应为唯一权威的用户侧价格来源。
- `DEFAULT_MODELS` 只在**DB 无数据**时使用，不要与真实数据混排。
- 如果未来要展示“推荐价”，应由 `channels[]` 计算，不要从平铺字段反推。

## ⑥ D2 约束自洽性

### 结论

**大方向自洽，但需要把 D2 解释清楚，否则字面上会与新增能力冲突。**

### 评审意见

- D2 写的是“只改中文文案 / UI / 文档；不改 DB 表名/字段名/代码标识符”。
- 但 Spec 中新增了：
  - `getChannelPricing`
  - `parseModelVendor`
  - `channels[]`
  - `channel_code`
- 这些属于新增功能所需的**新增标识符**，不是重命名既有标识符。

### 结论

- 如果 D2 被理解为“**不重命名已有实体和接口**”，则完全自洽。
- 如果 D2 被理解为“**不能新增任何代码/响应标识符**”，则与本次需求冲突，必须修订。

### 建议在 Spec 中补一句

> D2 的限制仅指“不对既有表名/字段名/路由名/组件名做重命名”，允许为本次功能新增必要的内部函数、响应字段和新页面路由。

这样最稳。

## ⑦ 风险清单

### P0

1. **风险：渠道锁定后，计费仍可能走模型级合并价**
   - 影响：用户看到渠道价、实际扣费不一致，直接破坏“展示价≠扣费价”目标。
   - 建议：把路由结果中的 `channelCode/supplierModelId` 传入计费层，或明确本期仅做展示不做渠道精确扣费。
   - 归属阶段：后端

2. **风险：`supplier_models` / `vendor_pricing` 无复合唯一约束，查询存在非确定性**
   - 影响：同渠道同模型或同组多价并存时，`limit(1)` 结果可能漂移。
   - 建议：至少补复合索引；若业务上本就只允许一条，则补唯一约束并在导入/同步时做去重。
   - 归属阶段：后端 / 数据层

3. **风险：显式锁定与自动路由错误码边界不清**
   - 影响：前端无法稳定处理“渠道不存在 / 不可用 / 被分组排除 / 该渠道不提供该模型”。
   - 建议：统一错误码与 payload，明确自动路由不抛“候选过滤失败”类业务错误。
   - 归属阶段：后端 / 测试

### P1

4. **风险：`/me/models` 平铺字段和 `channels[]` 双口径并存**
   - 影响：旧页面可能继续误用平铺字段做主展示。
   - 建议：平铺字段只作为旧组件兼容字段，前端新页面只读 `channels[]`。
   - 归属阶段：前端 / 后端

5. **风险：`DEFAULT_MODELS` 兜底掩盖真实数据缺失**
   - 影响：开发或运营可能误以为模型数据已同步成功。
   - 建议：仅在 DB 空时兜底，并增加日志或显式状态标记。
   - 归属阶段：后端 / 测试

6. **风险：任务型渠道与模型锁定逻辑混用**
   - 影响：`selectTaskChannel` 被误接入 `parseModelVendor` 后，任务路由语义会错乱。
   - 建议：任务类 API 仅从任务记录继承渠道，不从 model 字符串解析。
   - 归属阶段：后端

### P2

7. **风险：渠道价目页排序口径不统一**
   - 影响：不同页面看到的推荐排序不一致。
   - 建议：Spec 固化排序规则（推荐优先、价格次之、信用再其次）。
   - 归属阶段：前端 / 产品 / 文档

8. **风险：术语统一容易误改代码标识符**
   - 影响：破坏已有接口契约或测试基线。
   - 建议：文档中显式声明“仅中文展示层改名，代码标识符保留”。
   - 归属阶段：文档 / 前端 / 后端

## ⑧ 各阶段派发任务边界补充

### 后端任务边界

- 只做**增量**，保留现有 `/v1/chat/completions`、`/v1/completions`、`/v1/messages` 等主链兼容。
- 新增 `getChannelPricing` 时，必须复用现有 L4 分组解析，不要复制另一套定价逻辑。
- `selectChannel` 的 `channelCode` 只影响显式锁定，不影响自动路由。
- 如果本期不改主计费链，请在实现里明确：`getChannelPricing` 先用于展示，后续再接实际扣费；否则必须同步改路由→计费上下文。
- 错误码必须统一，并补单测覆盖：存在/不存在、可用/不可用、模型不在渠道、分组拒绝、自动路由回退。

### 前端任务边界

- 新页面只认 `channels[]`，平铺字段只当兼容。
- 不要从 UI 端自己推断最低价作为扣费依据；价格展示与调用参数要分离。
- `model@channelCode` 只用于调用输入展示，不要在前端臆造路由可用性。
- 所有新增页面标题和按钮都要带 `[?]`，这是硬约束。

### 文档任务边界

- 全文统一“渠道”中文语义，但**不重命名**既有表名、字段名、路由名、类型名。
- 补一段 D2 解释，避免后续实现误解。
- 新接口、新字段的契约示例要和 PRD/SPEC 保持完全一致。

### 测试任务边界

- 必测：
  - 同模型多渠道的价格展开
  - 指定渠道锁定
  - 渠道不存在 / 不可用 / 不提供该模型 / 分组被禁
  - 自动路由保持旧行为
  - `/me/models` DB 空回退 `DEFAULT_MODELS`
  - 旧平铺字段兼容不破坏
- 必测数据稳定性：重复 `supplier_models` / 重复 `vendor_pricing` 记录时结果是否确定。

---

## ⑨ 最终结论

**评审结论：有条件通过。**

**进入开发前必须补齐的 3 项：**
1. 明确“渠道锁定后计费”的数据闭环，避免展示价与扣费价不一致。
2. 明确 `supplier_models` / `vendor_pricing` 的唯一性或排序口径，避免非确定性。
3. 明确 `selectChannel` / `selectTaskChannel` 的边界与错误码语义，避免误伤自动路由与任务链路。

只要以上三项在后端实现说明和测试计划里补齐，本次 Spec 可以进入 Phase 1 的后续实现派发。
