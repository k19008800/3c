## 详细差距分析

### 模块 1: 计费结算引擎（Billing Engine）

| # | 缺失类型 | 描述 | 严重程度 | 涉及文档 |
|---|---------|------|---------|---------|
| 1 | **异常处理** | **计费链路中的预扣失败回滚流程缺失**：预扣 balance 后，若供应商请求失败或超时（无实际 tokens 返回），当前描述只提到"多退少补"，但缺少预扣金额回滚的具体时序、补偿窗口期（多久未收到响应则自动释放预扣）、以及预扣记录与消费日志的一致性校验机制 | P0 | ref-5.2-billing.md, ref-4.4-finance.md |
| 2 | **异常处理** | **并发扣款场景的竞态条件未定义**：同一用户的多个并发请求可能导致余额扣减超卖（balance_after 计算在 DB 层是否使用行锁或乐观锁），没有定义并发扣款的保护机制 | P0 | ref-5.2-billing.md |
| 3 | **运营场景** | **计费异常时运营如何干预未定义**：当出现计费日志缺失（billing_logs 与 call_logs 不一致）、定价缓存未刷新导致计费偏差时，运营/财务如何识别、回滚、补偿的具体流程缺失 | P0 | ref-5.2-billing.md, ref-4.4-finance.md |
| 4 | **SLA** | **计费引擎自身可用性 SLA 未定义**：计费引擎是整个平台收入核心，但没有定义其自身的可用性目标、降级策略（如 Redis 宕机时定价查询降级到 DB）、计费服务自身的熔断机制 | P1 | ref-5.2-billing.md, ref-7-nfr.md |
| 5 | **边界条件** | **精度溢出场景未覆盖**：价格字段精度为 18,6，但计费运算中的中间结果（如 `prompt_tokens × input_price / 1,000,000`）可能产生超过 6 位小数的结果，未定义舍入规则（银行家舍入 vs 四舍五入）和偏差累积的运营检查点 | P1 | ref-5.2-billing.md |
| 6 | **边界条件** | **T+1 结算的场景未覆盖**：当某个请求的计费跨越了结算周期边界（如请求在 23:59:59 发起，供应商响应在次日 00:00:01 返回），计费归属哪个周期未定义 | P1 | ref-5.2-billing.md, ref-4.4-finance.md |
| 7 | **数据流转** | **计费结果到财务总账的数据同步时序缺失**：计费流水如何归集到 `platform_ledger`（实时 vs 批量 T+1）、归集前如何验证数据完整性（笔数核对、金额核对）未定义 | P0 | ref-5.2-billing.md, SPEC-§29 |

### 模块 2: 供应商管理（Vendor Management）

| # | 缺失类型 | 描述 | 严重程度 | 涉及文档 |
|---|---------|------|---------|---------|
| 8 | **运营场景** | **供应商上下线对用户的影响处理流程缺失**：当供应商主动下线或被动熔断时，对正在进行的 API 请求的处理（等待完成 vs 中断重试）、对已分配但未消耗的 Key 资源的释放策略、对用户的体验影响说明（是否透明切换？是否提示用户？）均未定义 | P0 | ref-4.3-vendor-model.md, flowcharts/04-vendor-status-switch.md |
| 9 | **运营场景** | **供应商 Key 耗尽/过期/限流后的运营通知流程缺失**：当供应商 API Key 因余额不足或过期失效时，系统如何通知运营（告警）、运营如何紧急切换供应商、如何评估对已有用户的影响、补偿方案均未定义 | P0 | ref-4.3-vendor-model.md, ref-5.4-alert-rules.md |
| 10 | **异常处理** | **供应商入驻审核超时处理缺失**：供应商入驻提交后，审核状态为 pending 超时（如超过 3 个工作日）时的自动升级/通知机制未定义 | P1 | ref-4.10-vendor-self-service.md |
| 11 | **运营场景** | **供应商自助修改价格后的审核流程缺失**：供应商自助修改模型价格后，是否需要平台审核？审核期间是否影响现有定价策略？修改历史如何追溯？ | P1 | ref-4.10-vendor-self-service.md, ref-4.3-vendor-model.md |
| 12 | **数据流转** | **供应商健康检查结果如何驱动运营决策缺失**：健康检查发现供应商异常后，告警通知到运营的延迟指标、运营手动切换 vs 自动切换的边界条件（连续失败次数、响应时间阈值）、切换后如何通知用户均未定义 | P0 | ref-4.3-vendor-model.md, ref-5.4-alert-rules.md |
| 13 | **边界条件** | **供应商批量异常场景未覆盖**：当多个供应商同时出现故障时（如大型模型厂商集体宕机），系统的降级策略（是熔断所有相关模型还是逐个降级）、运营的操作面板（一键切换备选供应商）未定义 | P0 | ref-4.3-vendor-model.md, ref-5.1-routing.md |

### 模块 3: 代理商体系（Agent System）

| # | 缺失类型 | 描述 | 严重程度 | 涉及文档 |
|---|---------|------|---------|---------|
| 14 | **异常处理** | **佣金计算异常处理缺失**：当佣金规则配置有误（如阶梯阈值重叠、阶梯缺失、佣金率超过 100%）、计费流水缺失导致佣金计算偏差、多级代理佣金重复计算等场景的检测和运营修复流程缺失 | P0 | ref-3-agent-system.md |
| 15 | **运营场景** | **提现失败处理流程缺失**：提现申请通过双审后，实际打款失败（银行退票、账户信息错误、风控拦截）的处理流程：系统是否自动重试？重试次数上限？失败后金额解冻的时序？运营如何通知代理重新提交？均未定义 | P0 | ref-3-agent-system.md, ops-manual.md |
| 16 | **运营场景** | **代理批量审核场景缺失**：当前只支持逐个审核代理晋升，运营建议增加批量审核接口和场景描述（`POST /api/v1/admin/agents/batch-audit`），包括批量通过/拒绝的条件筛选和操作确认 | P1 | ref-3-agent-system.md |
| 17 | **数据流转** | **代理佣金与财务总账的对账链路缺失**：代理佣金计算完成后，如何同步到结算单、如何与 `platform_ledger` 中 `agent_commission` 条目对应、月度结算与实时佣金计算的差异核对机制均未定义 | P1 | ref-3-agent-system.md, SPEC-§29 |
| 18 | **边界条件** | **代理佣金封顶场景未覆盖**：佣金规则中的 `maxCap` 字段定义了单笔/单月佣金上限，但达到上限后，超出的佣金如何处理（截断 vs 滚动到下期）、如何通知代理，未定义 | P1 | ref-3-agent-system.md |
| 19 | **异常处理** | **代理被降级后关联用户价格变化影响缺失**：代理从高级降级为预备后，其名下用户的折扣/价格如何变化（即时生效还是渐变）、如何通知用户、是否允许过渡期，均未定义 | P0 | ref-3-agent-system.md |
| 20 | **运营场景** | **代理佣金结算周期与提现周期的运营操作 SOP 缺失**：结算周期（月结 vs 周结）、提现冻结期（7 天）、提现冷却期（24h）的运营操作日历、节假日顺延规则、财务封账期间提现处理策略未定义 | P1 | ref-3-agent-system.md, ops-manual.md |

### 模块 4: 限流引擎（Rate Limiter）

| # | 缺失类型 | 描述 | 严重程度 | 涉及文档 |
|---|---------|------|---------|---------|
| 21 | **运营场景** | **限流/熔断触发后的运营通知流程缺失**：当 L1 全局限流被频繁触发（接近阈值 80%/90%/100%）、用户/Key 级限流命中率异常升高、或供应商熔断器打开时，运营如何收到通知、如何快速扩容/调整阈值、如何与受影响的用户沟通，均未定义 | P0 | ref-5.3-rate-limiter.md, ref-5.4-alert-rules.md |
| 22 | **异常处理** | **限流系统自身降级策略缺失**：当 Redis 不可用时，限流引擎如何处理（降级为全放行还是全拒绝？）、降级期间的流量峰值如何保护后端、降级恢复后的流量平滑策略，均未定义 | P0 | ref-5.3-rate-limiter.md |
| 23 | **边界条件** | **四级限流规则冲突时的优先级处理缺失**：当不同级别限流配置冲突时（如 L1 全局限流 100 QPS，L2 用户限流 200 QPS，L3 Key 限流 50 QPS），当前取最小值策略可能导致用户感知不一致，需要定义各层级之间的权重和用户通知策略 | P1 | ref-5.3-rate-limiter.md |
| 24 | **运营场景** | **限流配额调整的运营操作流程缺失**：运营调整用户配额/Key 配额后，何时生效（即时 vs 周期性刷新）、对正在进行的请求的影响、调整记录的审计追溯，均未定义 | P1 | ref-5.3-rate-limiter.md |
| 25 | **SLA** | **限流引擎自身的可用性 SLA 缺失**：限流是系统第一道防线，其自身可用性、响应延迟（P95 < 5ms？）、故障影响范围（限流系统挂掉是否影响正常 API 调用？）未定义 | P1 | ref-5.3-rate-limiter.md, ref-7-nfr.md |

## 关键建议

### 1. 最高优先级修复（P0 中的前 5 项）

1. **计费预扣失败回滚流程** — 计费是收入核心，预扣→失败→回滚的时序和补偿机制是资金安全的命脉
2. **供应商批量异常降级策略** — 供应商是平台的生命线，批量故障时的应急流程必须优先定义
3. **充值→消费→对账全链路监控** — 资金链路的端到端可见性是财务合规的基础
4. **数据迁移/版本升级运营影响** — 缺少此定义将导致上线时的运营混乱和用户投诉
5. **全局配置变更审批流程** — 定价、限流等核心配置变更缺少审批是运营风险

### 2. 文档改进建议

- **为每个 ref-*.md 增加"运营视角"章节**，补充运营日常操作、异常处理、通知触发条件
- **创建一份跨模块数据流地图（Data Flow Map）**，用图形方式展示充值→计费→结算→对账的完整链路及各环节的数据一致性校验点
- **补充 ops-manual.md 的异常处理部分**，将各模块的异常场景统一归集到运营手册中
- **为所有 API 端点定义告警阈值**：在 ref-5.4-alert-rules.md 中补充每个模块关键 API 的告警规则模板

### 3. 建议后续迭代纳入

- 运营工作台（Operations Workbench）：统一展示待办队列、异常告警、批量操作入口
- 自动对账差异处理工作台：按优先级排序、批量处理、操作审计
- 运营数据看板（实时/日报/周报/月报）：统一的数据定义和自动推送机制
