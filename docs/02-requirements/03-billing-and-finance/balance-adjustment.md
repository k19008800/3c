## 1. 目标与非目标

### 1.1 目标

调账是平台对用户余额进行人工调整（调增/调减）的核心资金路径，用于平台赠送、补偿、纠错与扣减等运营场景。R5–R7 阶段目标为补齐资金安全三层风控，使调账（以及人工上账、充值订单审核）的资金写操作形成统一风控闭环：

1. **分级审批统一（R5）**：调账按**入账金额**统一分级，取消金额型免审批的拆分漏洞；调增默认至少一级审批。
2. **拆分规避与限额（R6）**：操作人与被入账用户双维度 24h 滚动累计限额，防"9×¥9,999"式拆分绕过。
3. **操作级 2FA + 二次确认（R7）**：全部资金写操作后端强制操作级 2FA 与二次确认（AND 关系），`super_admin` 不默认豁免。

调账状态机语义为 `pending → pending_level2 → pending_super → approved`（按实际审批级别跳过阶段），可转 `rejected`/`failed`，生效后可转 `reversed`（ADR-0003）。

### 1.2 非目标（本期明确不做）

- **不做 R8–R15**：`platform_ledger` 联动（R8）、凭证落库（R9）、正式幂等键（R10，调账侧）、科目字典（R11）、红冲审批链（R12）、审计 diff（R13）、台账导出（R15）——这些不属 R5–R7 范围，仅在交互相关处作依赖说明。
- **不改变调减入账口径的现状语义**：除分级与限额归入统一规则外，调账的余额入账/红冲语义沿用 ADR-0003、ADR-0020（纠错使用独立反向资金记录，不使用"退款"语义）。
- **不开放给 finance 角色**：调账权限点 `finance.adjust` 仅授予 `admin`/`super_admin`；finance 不可发起或审批调账（`docs/PRD-整改R1-R4` R3，保持）。

## 2. 角色与业务场景

### 2.1 角色与权限点（引用 ADR-0004、ADR-0024）

- **权限点模型**：后端统一按权限点鉴权，角色只作权限聚合（ADR-0004）；无权限统一返回 HTTP 403 `PERMISSION_DENIED`。
- **角色枚举**：当前正式角色仅 `customer / agent / sales / admin / super_admin`（ADR-0024）。`finance_ops / ops / support / auditor` 非当前枚举，须另行 ADR 方可启用。
- **调账权限点**：`finance.adjust`（手动调账：发起 + 审批 + 红冲）仅授予 `admin`、`super_admin`；`finance` 角色无该权限点，不可见/不可调用（R3 阶段收口）。
- **职责分离**（ADR-0004 + R5 B4）：申请人 ≠ 任一审批环节操作者；一级 ≠ 二级；`super_admin` 终审 ≠ 前两级；`super_admin` **不**豁免"创建 ≠ 审批"（自建自审仅能走降级代审路径，必填原因）。
- **数据范围与操作权限分离**；权限变更不追溯已完成资金记录（ADR-0004）。

### 2.2 业务场景

| 场景 | 描述 | 触发路径 | 审批档位（R5） |
|------|------|---------|----------------|
| 平台赠送 | 运营赠送用户余额（营销/关怀） | 财务 → 手动调账 → 调增 | ≤¥10,000 单审；>¥10,000 双人；>¥100,000 追加 super_admin 终审 |
| 补偿/纠错 | 因平台过错、异常交易补偿或余额纠错 | 财务 → 手动调账 → 调增/调减/红冲 | 同上；调减恰为 ¥10,000 仍双人特例（B1） |
| 客服补单 | 客服补登（历史异常补录） | 财务 → 手动调账 | 同上 |
| 扣减纠错 | 误增后的余额扣减 | 调减/红字冲销 | 同档分级 |

## 3. 业务规则

### 3.1 单笔上限与审批阈值（ADR-0001）

- 管理员调账**单笔上限 ¥50,000**（ADR-0001）；超过即拒绝，不进入调账终审档。
- 审批阈值独立于单笔上限：≤¥10,000 单人；>¥10,000 且 ≤¥100,000 双人；>¥100,000 追加 `super_admin` 终审（ADR-0001）。金额边界语义：恰为 ¥10,000 → 单审档（调减恰为 ¥10,000 仍双人，特例见 3.3）；¥10,000.01 起 → 双人档；恰为 ¥100,000 → 双人档；¥100,000.01 起 → 终审档。

### 3.2 金额精度（ADR-0002）

- 调账输入最多 2 位小数（元）；余额/Token 内部 `numeric(18,8)`；用户展示金额固定 2 位小数。
- 禁止使用 JavaScript `Number` 作为金融最终计算依据；使用 Decimal 或数据库 numeric 运算。

### 3.3 统一大额规则（R5，可配置）

1. **判定基数**：调账按**调增金额**（调减 = 调减金额绝对值）分级；红冲（加钱方向）按反向记录金额作为新单据重新定级。
2. **调减规则（裁决 B1）**：调减与调增同档（≤¥10,000 单审、>¥10,000 双人、>¥100,000 追加 super_admin）；**特例**：调减恰为 ¥10,000 仍按双人档（不放松现状更严语义）。
3. **免审批的取舍（裁决 B2）**：取消"调增 <¥10,000 免审批"（none 档废止），全部调增默认至少一级审批；提供可选**白名单科目免审开关（默认关闭）**：开启时科目 ∈ `{赠送, 补偿, 纠错}` 且单笔 ≤¥1,000 且调增方向 → 免审（提交即生效），且**免审单同样计入 R6 24h 累计限额**。
4. **职责分离**（ADR-0004 + B4）：申请人 ≠ 任一审批环节；一级 ≠ 二级；super_admin 终审 ≠ 前两级；super_admin 不豁免。
5. **审批人落库与补足**：一级/二级/终审审批人分别落库；调账新增 `super_reviewed_by`（终审人）。审批人不足 → 单据滞留 + 创建人提示"审批人不足，已通知管理员" + 通知 super_admin；super_admin 代审必填 `escalation_reason`（审计标记 `degraded:true`）。
6. **配置化（裁决 B17/B18）**：大额规则阈值来自 `finance_rules.large_amount` 配置（admin/super_admin 可改，保存需 2FA；`operation_2fa` 段仅 super_admin）。**按单据提交时点固化审批级别**（B18）：存量待审单据沿用提交时级别，阈值调整不影响存量，仅新单据用新规则。读取优先级 配置 → 常量默认值，缓存 60s，读失败回退常量。
7. **大额规则配置键**（对齐 `finance_rules.large_amount`，默认值见 SPEC §3）：`single_review_max=10000`、`dual_review_threshold=10000`、`super_review_threshold=100000`、`review_exempt.*`、`adjustment_decrease_same_tier=true`。

### 3.4 24h 累计限额（R6，引用 ADR-0013、ADR-0022）

1. **双维度**：操作人 24h 累计（`limits.operator_24h`）与被入账用户 24h 累计（`limits.recipient_24h`），默认均为 **¥50,000**（ADR-0013）。两维度独立计算，任一超限即触发处置。
2. **计数范围（ADR-0013 + R5 B9/B10）**：计入人工上账创建、调账**调增**发起、红冲**加钱方向**发起；不计入调账调减、充值订单审核、兑换码入账。
3. **计入时点**：创建/提交时预占（含本笔判定）；**驳回/红冲不回退累计**（B19，防"提交-撤销-再提交"循环绕过）。
4. **窗口语义**：`now - 24h ≤ created_at ≤ now` 滚动窗口，非自然日，无需定时重置（ADR-0013）。
5. **超限处置（ADR-0022 + B7）**：`exceed_action` 仅取 `escalate` 或 `reject`。默认 `escalate`（升级至少双人审批，级别 = `max(金额档, 双人档)`，不自动升终审）；可配置 `reject`（直接拒绝，当前创建返回 429 `DAILY_LIMIT_EXCEEDED`）。`escalate` 不得降低原有审批级别（ADR-0022）。
6. **豁免（B8）**：`limits.exempt_roles` 默认空数组；`super_admin` 默认**不豁免**限额。豁免记录写审计。
7. **配置键与优先级冻结（ADR-0022）**：对外统一使用 `limits.operator_24h` / `limits.recipient_24h` / `limits.exceed_action`；`soft_limit`/`hard_limit` 不作为对外配置键。**优先级**：`invalid input → hard business limit（单笔上限）→ 24h operator/recipient limit → approval threshold → normal processing`。单笔上限优先于累计限额。
8. **并发（ADR-0013 + ARCH 裁决）**：限额并发计算原子化（PG `credit_limit_events` + advisory lock 串行化同维度 + UNIQUE 幂等；Redis ZSET 作热路径，PG 权威）。

### 3.5 操作级 2FA + 二次确认（R7，引用 ADR-0008、ADR-0022-B12）

1. **适用范围**：调账的发起、一级审批（通过/驳回）、二级复核（通过/驳回）、红冲（发起/审批）均要求操作级 2FA + 二次确认（后端强制）。只读操作（列表/台账/待审/限额查询）不要求。
2. **AND 关系（ADR-0008）**：操作级 2FA = "我是本人"（身份），二次确认 = "我确认操作"（意图），两者 AND，任一缺失后端拒绝；前端二次确认不能替代后端校验。
3. **策略（B12）**：`operation_2fa.policy = mandatory_admin`（默认）——资金角色（admin/super_admin 作调账操作）未启用 2FA 时操作被拦截 + 引导启用；`disabled` 档仅用于紧急关闭。与登录 2FA 策略解耦。
4. **操作令牌（B11/B13/E27）**：验证通过签发短时操作令牌（默认 5 分钟，窗口内同操作者多次资金写操作可复用，每次仍校验）；可复用；不可跨操作者；支持备用码（一次性，用尽提示重生成）；管理员重置 2FA → 该用户全部未过期操作令牌失效。
5. **失败锁定（B14/E23/E31）**：TOTP/备用码连续错误 5 次锁定 15 分钟（与登录 2FA 失败计数共享），锁定期间返回 429 + 倒计时，锁定写审计并通知管理员。
6. **错误码红线**：资金端点中间件错误码**不使用 401**（避免前端 axios 401 全局拦截器误登出），使用 403/429（见 SPEC §5）。

## 4. 状态与结果

调账状态机详见 [调账状态机](../../06-data-and-architecture/state-machines/adjustment.md)。核心状态转移（ADR-0003 + R5 tier3）：

```
发起（定级：金额档 + R6 限额升级；无免审档或按白名单免审开关）
  ├─ 白名单免审（开关开启且命中）→ approved（提交即生效；计入 24h 累计）
  ├─ level1（单审档 ≤¥10,000）：pending ──一级通过──► approved（生效）
  ├─ level2（双人档）：pending ──一级通过──► pending_level2 ──二级通过──► approved
  ├─ level3（终审档 >¥100,000）：pending ──一级──► pending_level2 ──二级──► pending_super ──super_admin 通过──► approved
  ├─ 任一步驳回 → rejected
  └─ approved ──红冲(reverse)──► reversed（反向记录作为新单据按规则重新定级）
```

- 状态机约束：仅当前环节状态可流转（原子守卫，对齐阶段一 P1-2 修复语义）；已终态单据不可再审批（E7）。
- 结果语义：`approved` = 调账已生效（余额已入账/扣减，写流水 + 通知 + 审计）；`rejected` = 驳回（记驳回原因，不改余额）；`reversed` = 已红冲（独立反向资金记录生效后原单转该态）。

## 5. 异常与边界

| # | 场景 | 触发条件 | 预期行为 |
|---|------|---------|---------|
| E1 | 金额恰为 ¥10,000 | 调增单笔 = 10,000 | 单审档（调减仍双人，特例 B1） |
| E2 | 金额 ¥10,000.01 | 越过阈值 | 双人档 |
| E3 | 审批人 = 申请人 | 申请人审批自己的单据 | 拒绝 409/400，提示"您不能审批自己发起的单据"；前端按钮禁用 |
| E4 | 一级 = 二级 | 同人对双人档执行一级与二级 | 拒绝，提示"一级与二级审批不能为同一人"（调账已有该校验） |
| E5 | 终审人 = 前两级之一 | 前两级审批人执行终审 | 拒绝（职责分离） |
| E6 | 重复/并发审批 | 同一环节并发审批（双击） | 409 `ORDER_ALREADY_PROCESSED`（原子状态守卫，不重复入账/扣减） |
| E7 | 终态单据再审批 | 对 `approved/rejected/reversed` 再操作 | 拒绝，单据已终态 |
| E8 | 审批人不足 | 双人档无第二人可审 | 单据滞留 + 提示 + 通知 super_admin；super_admin 代审必填降级原因（审计标记 `degraded`） |
| E9 | 白名单免审不命中 | 开关开但科目非白名单 / 金额 >¥1,000 / 调减 | 按金额档正常审批 |
| E10 | 大额规则配置变更 | 阈值调整 | 按提交时点固化（B18）：存量沿用提交时级别，新单用新规则 |
| E11 | 调账超单笔上限 | 金额 > ¥50,000 | 创建拒绝（ADR-0001），提示大额走充值订单路径或拆分 |
| E12 | 调账 >¥100,000 | 调增超 10 万 | 终审档三人链（一级 → 二级 → super_admin） |
| E13 | 9×¥9,999 拆分 | 同操作人 24h 内 9 次 ¥9,999 调增 | 第 6 笔起累计 >¥50,000 → 强制升级双人审批 |
| E14 | 双维度超限 | 操作人与用户维度同时超限 | 任一超限即升级本笔（取更严行为） |
| E15 | 24h 窗口跨日 | 23:59 与次日 00:01 | 按滚动窗口（当前时刻回看 24h），不按自然日重置 |
| E16 | 并发提交同操作人 | 两笔并发超限 | 逐笔原子判定（advisory lock 先到先得），后笔按新累计升级/拒绝 |
| E17 | 驳回/红冲后累计 | 单据被驳回或红冲 | 累计不回退（B19） |
| E18 | 调减与限额 | 调减金额巨大 | 不计入限额（B9），但按金额档审批（调减 ≥¥10,000 双人） |
| E19 | super_admin 超限 | super_admin 24h 累计超限 | 默认不豁免（B8），按配置升级/拒绝 |
| E20 | exceed_action=reject | 超限且配置为拒绝 | 提交被拒 429 `DAILY_LIMIT_EXCEEDED` + 拒绝文案 |
| E21 | 限额配置变更 | 限额调整 | 读配置即时生效；存量单据级别不回改 |
| E22 | 未启用 2FA 操作者 | admin/super_admin 未启用 2FA 执行调账 | 拦截 + 引导启用（`mandatory_admin` 默认），403 `OPERATION_2FA_NOT_ENABLED` |
| E23 | TOTP 连续失败 | 连续 5 次验证失败 | 锁定 15 分钟，429 + 倒计时 + 审计 + 管理员告警（与登录共享计数） |
| E24 | 备用码一次性 | 操作级使用备用码 | 校验通过后该码作废 |
| E25 | 备用码用尽 | 剩余 0 个且尝试使用 | 提示"备用码已用尽，请重新生成或使用认证器" |
| E26 | 操作令牌过期 | 验证后超过 5 分钟提交 | 请求被拒 403 `OPERATION_2FA_EXPIRED`，提示重新验证 |
| E27 | 2FA 被强制重置 | 管理员重置用户 2FA | 该用户全部未过期操作令牌失效 |
| E28 | TOTP 时间偏差 | 手机时间不准 | 内置 ±1 窗口容差（±30s） |
| E29 | 令牌跨单据复用 | 5 分钟窗口内审核多笔 | 允许复用（免重复输入），每次操作仍校验 |
| E30 | 2FA 与二次确认缺一 | 请求缺令牌或缺确认标记 | 后端拒绝（AND 关系，不得前端放行） |

> 以上 E1–E30 列举为调账相关边界；完整 E1–E31 含人工上账/充值订单通用场景，见主权威来源 `PRD-整改R5-R7-资金风控.md` §5。暂未纳入边界单独说明的 `E31 锁定期间操作 → 429 + 倒计时` 同样适用于调账。

### 余额与负余额约束

- **禁止负余额**（ADR-0003、ADR-0020）：调减/扣减/冲销在余额不足时返回受控业务错误，不得强行写入负余额；当前版本不允许因红冲写入负余额，不引入平台垫付账户。
- **纠错不用"退款"语义**（ADR-0020）：调账/人工上账纠错统一通过红冲创建独立反向资金记录，不使用退款语义；原单金额不可修改/删除。

### 并发与幂等（ADR-0009）

- 创建类资金操作强制 `Idempotency-Key`（`POST /api/v1/admin/adjust`）；审批、红冲纳入统一幂等规范并执行状态条件更新（ADR-0009 §"审批、红冲…纳入统一幂等规范"）。
- 状态条件更新与幂等**同时生效**：Redis 仅作加速锁；DB 唯一约束、事务与状态守卫是最终边界；Redis 不可用返回 `503 IDEMPOTENCY_UNAVAILABLE`，不得静默绕过。

## 6. 权限与安全

### 6.1 权限矩阵（调账相关，引用 ADR-0004 + R5 §4）

## 7. 通知、审计与合规

### 7.1 通知（ADR-0010）

- **强制通知**：调账生效（调增）→ 用户站内信**必发**（入账到账通知）；调减/扣减通知文案后续定义，本期不覆盖（R4 边界）。
- **规范**：资金事务提交成功后才写 outbox/event 再异步发送；通知失败不回滚资金事务；资金失败不得产生成功通知；重试不得造成重复可见通知。状态统一 `queued/sent/failed/skipped`。
- 事件包含 event_id、event_type、aggregate、user、amount、currency、occurred_at、idempotency_key（ADR-0010）。

### 7.2 审计（R3/R7）

- 所有调账写操作写审计日志：发起、审批（每次环节）、驳回、红冲；含操作者、操作类型、结果、IP。
- 操作级 2FA 校验成功/失败/锁定/令牌签发均写审计（R7 规则 10）。
- 降级代审标记 `degraded:true`；限额豁免标记 `limit_exempt`（B8）。

### 7.3 对账与合规（ADR-0012 + supplement/02）

- 当前版本**不启用、不写入 `platform_ledger`**（ADR-0012）；调账/红冲不得依赖该表完成；余额与对账依据为 `customer_balances`、`balance_transactions`、调账单据和 `billing_logs`。
- 余额对账恒等式（supplement/02 §七）：`Σ(期初余额) + Σ(充值) − Σ(消费) − Σ(退款) − Σ(提现) + Σ(调账) = Σ(期末余额)`；`adjust_amount` 为对账输入之一。偏差处理：≤¥10 INFO、¥10–¥100 WARN、>¥100 CRITICAL 紧急告警。

## 8. 页面与交互要求

页面：**财务 → 手动调账**，含三个页签：**发起调账 / 待我审批 / 调账台账**（R5 §3.1.4）。适用角色：admin / super_admin（持 `finance.adjust`）。

- **发起调账**：选择用户 → 方向（调增/调减）→ 金额 → 会计科目 → 原因 → 提交。金额 ≤¥10,000 单审；>¥10,000 双人；>¥100,000 追加 super_admin 终审；调增默认至少一级审批（免审取消）。白名单免审时展示"本单符合白名单免审条件，提交即生效"或"本单需审批"。
- **待我审批**：一级/二级/终审队列，排除自己申请的单据；新增"待双人复核 / 待终审"筛选；职责分离不满足时审批按钮禁用 + tooltip"您不能审批自己发起的单据"。
- **调账台账**：展示审批链（申请人 → 一级 → 二级 → 终审）与 `limit_escalated` / `escalation_reason` 标记。
- **审批链进度**：双人/终审档审核弹窗展示"一级已通过，待二级复核"。
- **审批人不足**：创建人/审批人侧警示条"审批人不足，已通知管理员"；super_admin 代审弹窗必填"降级代审原因"。
- **风控规则配置页**：大额规则 + 限额 + 2FA 策略统一在一个配置页。
- **2FA + 二次确认弹窗**：同一弹窗两步——第一步输入 TOTP/备用码验证身份；通过后同窗切换第二步操作摘要（用户/金额/到账后余额/审批级别/限额升级提示）与 [确认执行]；两步全过才发请求。未启用 2FA → 弹窗提示 + [前往启用]（跳转安全设置）；锁定 → 倒计时禁用输入。
- **P1 合规**：页面标题旁 `[?]` 页面帮助 + 每个操作按钮旁 `[?]` 按钮级帮助（见 8.1、8.2 数据源）。

### 8.1 [?] 页面帮助

**页面名称**：财务 → 手动调账

**适用角色**：管理员（admin / super_admin），持 `finance.adjust` 权限点（finance 角色不可见）

**功能定位**：为指定用户调增/调减余额（平台赠送、补偿、纠错、扣减），按金额分级审批，防拆分，全程审计，错误调账可红冲。

**核心操作**：
1. 发起调账：选择用户 → 方向（调增/调减）→ 金额 → 会计科目 → 原因 → 提交
2. 金额 ≤¥10,000 单审；>¥10,000 双人复核；>¥100,000 追加 super_admin 终审
3. 待我审批：一级/二级/终审队列，排除自己申请的单据
4. 调账生效后错误可「红字冲销」生成反向记录

**注意事项**：
- 调增免审批已取消（除非开启白名单科目免审：仅赠送/补偿/纠错且 ≤¥1,000，计入 24h 累计）
- 申请人 ≠ 审批人；一级 ≠ 二级；红冲需独立审批
- 操作人/被入账用户 24h 累计调增+上账超过 ¥50,000 → 后续笔升级双人审批
- 资金写操作需操作级 2FA + 二次确认
- 错误调账不删除不编辑，通过红字冲销纠正

**常见问题**：
Q: 调增 ¥500 也要审批吗？A: 默认是的（免审批已取消）；若运营开启白名单免审（赠送/补偿/纠错科目且 ≤¥1,000），符合条件的调增可提交即生效。
Q: 为什么"待我审批"看不到某些单据？A: 该队列已排除您自己申请的单据（职责分离）。
Q: 调减如何审批？A: 调减按金额分级：≤¥10,000 单审、>¥10,000 双人复核（恰为 ¥10,000 亦双人，保留更严语义），与调增同档统一。

**风控规则配置页**（页面级 `[?]` 帮助）见主权威来源 R5 §7.3（大额规则/限额/2FA 策略，pageKey `finance-risk-config`）。

## 9. 验收标准

验收依据：`PRD-整改R5-R7-资金风控.md` §6 验收清单（R5/R6/R7/P1 合规）+ 各 accepted ADR。调账相关关键项（勾选式，逐条可验收）：

- [ ] 调账单笔上限 ¥50,000 生效（ADR-0001）；超限拒绝创建
- [ ] 金额精度：调账输入最多 2 位小数，内部 `numeric(18,8)`（ADR-0002）
- [ ] 统一大额规则配置生效（`finance_rules.large_amount`）：≤¥10,000 单审、>¥10,000 双人（申请人 ≠ 审核）、>¥100,000 追加 super_admin 终审
- [ ] 调增 <¥10,000 免审批已取消（或白名单科目免审开关默认关闭）；调增全部至少一级审批（B2）
- [ ] 职责分离：申请人 ≠ 审批人；一级 ≠ 二级；super_admin 终审 ≠ 前两级；super_admin 自建自审需降级代审原因（B4/E3/E4/E5/E8）
- [ ] 调账新增 level3（pending_super）终审链可用；调减恰为 ¥10,000 仍双人（B1/E1）
- [ ] 任一步骤驳回均可用且驳回原因必填、落库
- [ ] 24h 限额双维度：操作人/被入账用户各 ¥50,000，`limits.operator_24h`/`recipient_24h`/`exceed_action` 键与优先级符合 ADR-0022
- [ ] 9×¥9,999 第 6 笔起强制升级双人审批（E13 整改方案验收）
- [ ] 调减不计入限额、调增计入（B9）；驳回/红冲不回退累计（B19）
- [ ] 操作级 2FA + 二次确认为 AND，任一缺失后端拒绝（ADR-0008/E30）
- [ ] 资金写操作未携带有效操作令牌 → 403（对应整改方案"未 2FA 请求被拒"）
- [ ] 未启用 2FA 的 admin/super_admin 被执行调账成功拦截并引导启用（E22）
- [ ] 连续 5 次失败锁定 15 分钟（与登录共享计数），备用码一次性，令牌 5 分钟过期与失效联动（E23/E24/E26/E27）
- [ ] 自动建户兜底（无余额行用户调增生效成功建户，R2 基线）
- [ ] 调增生效 → 站内信必发（ADR-0010）；通知失败不影响入账
- [ ] 操作级 2FA 校验/失败/锁定/令牌签发写审计；降级代审审计标记 `degraded`
- [ ] P1 合规：调账页/到账审批/风控配置页标题旁 `[?]` 页面帮助 + 本期涉及按钮均有 `[?]` 帮助（数据源 = 第 8 节）
