## 1. 目标与非目标

### 1.1 目标

- **提供正规人工上账通道**：为线下/对公转账已到账场景，管理员/财务凭凭证与转账单号为指定用户账户入账，避免借道「手动调账」造成财务口径混乱。
- **分级审核闭环**：按金额阈值执行一至二级审批，创建人不得审批本人单据，全流程审核留痕。
- **余额账户兜底**：目标用户无余额账户行时自动建户后再入账，不再因 `BALANCE_NOT_FOUND` 失败。
- **权限点鉴权**：资金写操作按 `finance.topup` 权限点鉴权，越权返回 403，前端按权限显隐入口。
- **入账通知闭环**：入账成功后强制站内信 + 按用户偏好邮件，通知可追溯、失败可重试、不回滚资金。
- **资金安全**：单笔上限、幂等键、操作级 2FA、24 小时滚动限额、状态条件更新作为不可绕过的资金安全闸。

### 1.2 非目标

- 不支持一次性开放大额（>¥50,000）人工上账：超限即拒绝，**不进人工上账终审档**；大额对公入账走充值订单（`recharge-order`）路径。
- 用户自助充值单笔上限（¥1,000,000）维持独立业务对象，本文档不改动用户端充值。
- 不实现用户端自助发起人工上账（`ALLOWED_METHODS` 不含 `manual`，人工上账仅管理端可创建）。
- 本办法仅覆盖人工上账的创建、审批、入账、驳回，不定义退款（原路退回）语义；人工上账纠错使用调账/红冲（见 §5），不使用退款。
- 凭证文件的持久化落库（正式 `evidence_url` 存储）不在本期；本版本 `transfer_no`/`evidence_remark` 写入 `metadata`。

## 2. 角色与业务场景

### 2.1 角色与权限点

| 角色 | `finance.topup`（创建+审核人工上账） | `finance.adjust`（手动调账） | 说明 |
|------|:---:|:---:|------|
| `super_admin` | ✅（`*` 通配） | ✅ | 全权限；依职责分离仍不得审批本人单据 |
| `admin` | ✅ | ✅ | 可创建/审核人工上账，可发起调账 |
| `finance` | ✅ | ❌ | 可创建与审核人工上账；不可发起调账 |
| `agent` / `sales` / `customer` | ❌ | ❌ | 权限树不含 `finance.*` |

> 权限点依据：ADR-0004（后端按权限点鉴权、角色只作聚合）、ADR-0001（审批阈值）、整改方案 R3（finance 可发起并审核人工上账、不可调账）。前端按权限点控制入口（`usePerm`），但不得替代后端校验。

### 2.2 业务场景

| # | 场景 | 说明 | 路径 |
|---|------|------|------|
| S1 | 线下/对公已到账入账 | 用户在平台外转账已到账，凭凭证/回单人工入账 | 人工上账（对公语义） |
| S2 | 平台赠送/补偿/纠错 | 运营补单、赠送、补偿等非对公入账 | 人工上账（`grant` 语义，凭证/单号选填） |
| S3 | 无余额账户用户入账 | 历史/异常用户无余额行 | 自动建户兜底（§5） |
| S4 | 大额对公入账（>¥50,000） | 运营确有大额需求 | 走充值订单路径，人工上账拒绝 |

### 2.3 分级审核职责分离

依据 ADR-0001（审批阈值）、ADR-0004（职责分离）、ADR-0021（审批阶段表达）：

| 单笔金额 | 审批级别 | 审批阶段（`approval_phase`） | 审批人要求 |
|---------|---------|------------------------------|-----------|
| ≤ ¥10,000 | 单人一级审批 | `level1 → completed` | 一级审批人 ≠ 创建人 |
| > ¥10,000 且 ≤ ¥50,000 | 双人二级审批 | `level1 → level2 → completed`（超 24h 限额升级时同双人） | 一级≠二级、均≠创建人 |
| > ¥50,000 | **拒绝创建**（不进终审档） | — | 大额对公走充值订单 |

> 说明：ADR-0001 定义 `>¥100,000` 追加 `super_admin` 终审（`approval_phase=super`），但人工上账单笔上限固定为 ¥50,000（超过即拒绝），故人工上账业务对象**不会到达终审档**；`super` 阶段仅在充值订单路径可达。24 小时滚动限额（§3）中 `exceed_action=escalate` 时升级为双人审批，但不得降低原本审批级别（ADR-0022）。

## 3. 业务规则

1. **谁可以发起**：持有 `finance.topup` 权限点（finance / admin / super_admin）；无该权限点前端隐藏/禁用入口 + 后端 403（ADR-0004、ADR-0011）。
2. **给谁上账**：目标用户必须是已存在且状态为 `active` 的 `users` 记录；通过用户搜索选择（邮箱精确/模糊、用户 ID 精确、手机号精确，仅对已绑定手机号的用户）。`frozen`/禁用/已删除用户拒绝创建，提示先解锁。
3. **金额约束**（ADR-0001、ADR-0002、ADR-0011）：
   - `amount > 0`；
   - 单笔上限 `≤ ¥50,000`（配置默认 `50000.00`，可经 `system_config finance_rules` 覆盖）；超限直接拒绝创建，**不进入人工上账终审档**；
   - 输入最多 2 位小数（元/分），内部余额与流水使用 `numeric(18,8)`（ADR-0002）；
   - 余额与 Token 消费内部统一 `numeric(18,8)`；禁止以 JavaScript `Number` 作为最终计算依据。
4. **入账类型**：为驱动凭证/转账单号必填，支持两种语义：
   - `bank_transfer`（线下/对公到账）：凭证 + 转账单号**必填**（凭证文件正式上传随 `R9`，本版本以 `evidence_remark` 文字记录并在 `metadata` 记录 `transfer_no`）；
   - `grant`（赠送/补偿/纠错）：凭证 + 转账单号**选填**，入账原因必填。
   - 【待人工裁决】`topup_type` 是否作为落库字段由产品与架构最终确认（ADR 未覆盖），当前版本不强制落库，仅驱动表单提示。
5. **转账单号唯一性**：若填写 `transfer_no`，全平台唯一；同一转账单号重复创建被拒（`409 DUPLICATE_BUSINESS_REFERENCE`，ADR-0009）。
6. **分级审批**（ADR-0001/0003/0004/0021）：按 §2.3 阈值与职责分离规则流转；`status` 业务状态仅 `pending/paid/rejected/failed`，审批阶段独立为 `approval_phase`（`none/level1/level2/super/completed`）。
7. **2FA**（ADR-0008）：创建、审批等所有资金写操作强制后端操作级 2FA；`super_admin` 不默认豁免；前端二次确认不能替代后端校验。
8. **幂等**（ADR-0009）：创建端点 `POST /api/v1/admin/manual-topup` 强制 `Idempotency-Key`；审批/驳回执行状态条件更新；Redis 不可用返回 `503 IDEMPOTENCY_UNAVAILABLE` 而非静默绕过。
9. **24 小时滚动累计限额**（ADR-0013/0022）：按操作人与被入账用户两维度统计，默认均 ¥50,000；统计人工上账创建（及调账调增、红冲加钱方向发起）；`exceed_action` 仅取 `escalate` 或 `reject`；任一维度超限触发处置；`super_admin` 不豁免；统计按滚动窗口 `now-24h ≤ created_at ≤ now` 计算。
10. **入账后动作**：审核通过 → 余额入账（无余额行自动建户兜底）→ 写资金流水 → 触发 `recharge_success` 入账通知（站内信必发 + 邮件按偏好）→ 写审计。
11. **错误入账处理**：审核通过入账后若发现错误，由 admin/super_admin 走现有调账/红冲（创建独立反向资金记录）纠正，不使用退款语义；原单金额不可修改、不可删除（ADR-0003/0020）。
12. **取消语义**：创建后不提供「取消」操作；需撤回走驳回。
13. **通知不出资金**：通知失败不回滚入账事务、不阻断审核响应（ADR-0010）。

## 4. 状态与结果

人工上账状态与结果以 [人工上账状态机](../../06-data-and-architecture/state-machines/manual-topup.md) 为唯一权威，本文档仅摘录关键口径：

- 业务状态 `status`（数据库持久化与 API 展示，ADR-0021）：`pending`（待审核，未入账）→ `paid`（已入账，终态）| `rejected`（已驳回，终态）| `failed`（入账异常，终态）。
- 审批阶段 `approval_phase`：`none`（无需审批）→ `level1`（一级）→ `level2`（二级）→ `completed`（审批完成并已入账）；`super` 仅供充值订单路径。
- 管理端响应同时返回 `status`、`approval_phase`、`approval_required`；用户端只暴露 `pending/paid/rejected/failed`，不暴露内部审批阶段。
- `pending_level2`、`pending_super` 为旧响应状态，**已标 deprecated**（ADR-0021），新接口不得用作业务 `status`。

| 业务状态 | 含义 | 是否终态 | 用户可见文案 |
|---------|------|:---:|------|
| `pending` | 待审核（审批未全部通过） | 否 | 待处理 |
| `paid` | 已入账（余额已增加 + 流水 + 通知） | 是 | 已到账 |
| `rejected` | 已驳回（记录驳回原因） | 是 | 已驳回 |
| `failed` | 入账异常（未入账、单据关闭） | 是 | 处理失败 |

## 5. 异常与边界

### 5.1 边界条件与异常场景

| # | 场景 | 触发条件 | 预期行为 | 依据 |
|---|------|---------|---------|------|
| B1 | 无余额行用户入账 | 目标用户无 `customer_balances` 行 | 自动建户（零余额）+ 入账成功，不再 404；建户写审计、对账口径不变 | 主权威来源 R2 |
| B2 | 用户不存在 | 目标用户已删除或 ID 无效 | 创建拦截，友好错误「用户不存在」 | 主权威来源 |
| B3 | 用户禁用/冻结/非 active | 目标用户状态非 `active` | 创建被拦截，`frozen` 返回 400 `VALIDATION_ERROR`，提示先解锁 | 主权威来源 + ARCH §12 A7 |
| B4 | 单笔超上限 | `amount > ¥50,000` | 拒绝创建，**不进终审档**；提示大额对公走充值订单 | ADR-0001 + open-issues 项 13（已解决） |
| B5 | 金额 ≤ 0 / 超 2 位小数 | 非法金额 | 拒绝创建，对应校验提示 | ADR-0002 |
| B6 | 重复创建同转账单号 | 同 `transfer_no` 再次创建 | `409 DUPLICATE_BUSINESS_REFERENCE`，拒绝创建 | ADR-0009 |
| B7 | 同 Idempotency-Key 重复提交 | 同一表单重复提交 | 相同 Key/摘要 → 回放首次结果；不同摘要 → `409 IDEMPOTENCY_CONFLICT` | ADR-0009 |
| B8 | 重复审核 | 已 `paid`/`rejected`/`failed` 单据再次审核（含并发） | 状态条件更新拦截，`409 ORDER_ALREADY_PROCESSED`；余额不重复累加 | ADR-0009 |
| B9 | 24h 累计超限 | 操作人/被入账用户任一维度 24h 累计超配置阈值 | 按 `exceed_action`：`reject` 拒绝 / `escalate` 升级双人审批 | ADR-0013/0022 |
| B10 | 入账事务失败 | 建户/更新/流水任一步失败 | 整体回滚，订单保持 `pending`，不产生部分入账 | 主权威来源 R2 |
| B11 | 并发建户 | 同一无余额用户同时被两条路径入账 | 建户幂等（不重复建户、不覆盖），两条入账按各自金额累加 | 主权威来源 R2 |
| B12 | 越权访问 | 无 `finance.topup` 者调用人工上账接口 | 后端 `403 PERMISSION_DENIED`；前端入口隐藏/禁用 | ADR-0004/0011 |
| B13 | 创建人审批本人单据 | 创建人尝试审批自己创建的单据 | 拒绝，职责分离（创建人≠审批人） | ADR-0004 |
| B14 | 重复一级/二级审批人 | 同一人担任连续审批级 | 拒绝（一级≠二级、终审不重复前级） | ADR-0004 |
| B15 | 缺少操作级 2FA | 资金写操作未携带有效操作 token | `403 OPERATION_2FA_REQUIRED`；错误/过期/重放固定错误码 | ADR-0008 |
| B16 | 通知发送失败 | 站内信/邮件写入或发送异常 | 入账不受影响；通知记录 `queued/sent/failed/skipped`，可重试/人工补发，重试耗尽告警 | ADR-0010 |
| B17 | 用户关闭邮件偏好 | 邮件偏好关闭 | 仅发站内信（站内信强制不可关闭）；不发邮件 | ADR-0010 |
| B18 | 余额不足的扣减/纠错 | 调账/红冲冲销扣减时余额不足 | 返回受控业务错误，**禁止负余额** | ADR-0020 |
| B19 | 重复入账通知 | 同订单状态重复流转 | 非成功不入账，通知仅在入账成功那一刻触发一次（由 outbox/事件去重保证） | ADR-0010 |

### 5.2 金额上限与审批阈值优先级（ADR-0022）

优先级：`invalid input → hard business limit（单笔上限） → 24h operator/recipient limit → approval threshold → normal processing`。单笔上限优先于 24h 累计限额：超单笔上限直接拒绝；未超单笔上限但超累计限额时按 `exceed_action` 处置。

### 5.3 自动建户兜底（R2，已收口）

任何资金入账路径（人工上账审核通过 / 调账生效 / 充值审核通过）统一收口到同一「建户兜底 + 增额 + 流水」逻辑（`creditBalance`），在调用方事务内执行；建户采用 `INSERT ... ON CONFLICT (user_id) DO NOTHING`，并发不重复建户；增额 `UPDATE` 依赖行级锁不丢失更新；流水与余额同事务强一致。

## 6. 权限与安全

- **权限点鉴权**（ADR-0004、ADR-0011）：资金路由由「角色白名单」改为「权限点校验」，后端 `requirePerm('finance.topup')`；越权统一 `403 PERMISSION_DENIED`，前端不得以 200 掩盖 403。`super_admin` 的 `*` 仅由统一权限守卫解释。
- **职责分离**（ADR-0004）：创建人≠审批人、一级审批人≠二级审批人、终审人不与前级重复；`finance` 可创建并可审核人工上账，但创建人不得审批本人单据。
- **操作级 2FA**（ADR-0008）：创建、审批（通过/驳回）等全部资金写操作强制后端操作级 2FA，`super_admin` 不默认豁免；登录 2FA 与操作级 2FA 分离；操作 token 一次性、短时有效、绑定操作者与操作摘要。
- **幂等**（ADR-0009）：创建强制 `Idempotency-Key`；审批/驳回状态条件更新；Redis 不可用返回 `503 IDEMPOTENCY_UNAVAILABLE`。
- **资金精度**（ADR-0002）：禁止 JavaScript `Number` 作为最终计算，使用 Decimal/数据库 numeric。
- **审计**：所有资金写操作（创建/审批/驳回/自动建户）写审计日志，含操作者、操作摘要、`approval_phase`、`request_id`（ADR-0011）。

## 7. 通知、审计与合规

- **通知**（ADR-0010）：资金类站内通知强制发送（人工上账到账），事件 `recharge_success`；Email/SMS/Webhook 等其他渠道遵循用户偏好。资金事务提交成功后写入 outbox/event 再异步发送；通知失败不回滚资金事务；资金失败不得产生成功通知；重试不得造成重复可见通知。通知状态统一 `queued/sent/failed/skipped`，事件含 `event_id/event_type/aggregate/user/amount/currency/occurred_at/idempotency_key`。
- **审计**（ADR-0011）：`request_id` 写入日志、审计与响应；审计记录审批阶段与审批人。
- **合规**：符合 PRODUCT-DESIGN-PRINCIPLES P1 —— 页面标题旁 `[?]` 页面帮助 + 每个操作按钮旁 `[?]` 帮助，SPEC 底部含「页面帮助与按钮级帮助对照表」。

## 8. 页面与交互要求

页面落点：管理后台 → 财务 → 人工上账（路由 `/admin/finance/manual-topup`）。

### 8.1 页面级 `[?] 页面帮助`

- 页面标题右侧 `[?]`（`pageKey=finance-manual-topup`）弹出页面帮助；内容见 SPEC §8 对照表（定制文案，非占位符）。

### 8.2 关键交互（含按钮级 `[?]`）

1. 列表页顶部「发起上账」按钮（右上，旁带 `[?]`）；无 `finance.topup` 权限该按钮不渲染（`usePerm`）。
2. 用户选择器：搜索框（邮箱/手机号/用户ID）→ 选中回显「邮箱 · 名称 · 用户ID · 当前余额 · 状态」；非 active 用户显示警示条并拦截提交。
3. 入账类型（对公到账 / 平台赠送）、入账金额（旁注「最低 ¥0.01，最高 ¥50,000」，实时「到账后余额预览」）、入账原因（≤500 字）、凭证上传、转账单号（对公标必填；失焦做唯一性校验）。
4. 提交 → 操作级 2FA 校验 + 二次确认弹窗（汇总用户/金额/类型/到账后余额/转账单号），提示「提交后进入待审核，审核通过前不改变用户余额」。
5. 提交成功 → toast + 列表刷新，新单据 `pending` 置顶。
6. 审批链路：`pending` 行显示审批操作（一级通过 / 驳回；需二级时显示二级审批入口）；每步操作均需 2FA + 二次确认；`approval_required` 为空时隐藏「通过」按钮。
7. 每个操作按钮（发起上账 / 确认提交 / 审核通过 / 驳回 / 上传凭证 / 用户搜索 / 重置表单）旁带 `[?]` 帮助。
8. 列表建议展示「通知状态」列（已通知 / 通知失败 / 无需通知）供管理员核验。

## 9. 验收标准

> 验收以「真实证据映射」为准：每条标准对应可执行测试或用例，映射到 SPEC §9 与状态机「测试映射」章节。

| # | 验收标准 | 映射 |
|---|---------|------|
| A1 | 列表/创建/审核三端点均按 `finance.topup` 鉴权；finance 可创建与审核；agent/sales/customer 越权 `403 PERMISSION_DENIED` | SPEC §6；ADR-0004 |
| A2 | 创建金额 >0、≤¥50,000、最多 2 位小数，超限拒绝且不入终审档；>¥50,000 提示大额对公走充值订单 | §3；ADR-0001 |
| A3 | 目标用户须存在且 `active`；`frozen`/禁用拒绝创建 | §3 |
| A4 | 同 `transfer_no` 重复创建被拒（`409 DUPLICATE_BUSINESS_REFERENCE`）；同 Idempotency-Key 重放回放首次 / 不同摘要 `409 IDEMPOTENCY_CONFLICT` | ADR-0009 |
| A5 | 分级审批：≤¥10,000 单人一级通过即入账；>¥10,000 且≤¥50,000 双人二级通过后入账；创建人≠审批人、一级≠二级被强制 | §2.3；ADR-0001/0004/0021 |

| A8 | 24h operator/recipient 双维度滚动限额生效；任一超限按 `exceed_action` 处置 | ADR-0013/0022 |
| A9 | 入账成功触发 `recharge_success` 站内信（必发）+ 邮件（按偏好）；通知失败不入账回滚、可重试/补发；事件含 idempotency_key | ADR-0010 |
| A10 | 事务失败整体回滚，订单保持 `pending`，无部分入账；余额不足的扣减/纠错返回受控错误，禁止负余额 | §5；ADR-0020 |
