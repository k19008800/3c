## 1. 目标与非目标

### 1.1 目标

充值主题为平台资金流入主链路，覆盖用户自助充值与管理端人工上账两类资金入账通道，目标：

1. **用户自助充值闭环**：用户通过支付宝/微信扫码支付、对公转账充值，支付回调幂等入账、余额增加、入账必通知（`recharge_success`）。
2. **管理员人工上账闭环**：为线下/对公已到账场景提供正规入账通道（创建 → 分级审批 → 入账 → 通知 → 审计），修复历史"只能借道调账"的 P0-1 断点。
3. **无余额账户兜底**：任意入账路径对缺失 `customer_balances` 行的用户自动零余额建户后再入账，修复 P0-2 的 `404 BALANCE_NOT_FOUND`。
4. **权限点鉴权对齐**：资金路由从"角色白名单"改为"权限点鉴权"，使 API 授权真实生效，修复 P0-3 "假授权"。
5. **入账通知闭环**：入账成功必发站内信 + 按偏好发邮件，修复 P0-4 "充值未到账"客诉。
6. 全流程符合 PRODUCT-DESIGN-PRINCIPLES P1：每页标题与每个操作按钮旁均有 `[?]` 帮助。

### 1.2 非目标（本期不做）

- **不做**分级审批外的专项拆分规避（R6）、2FA 强制接入（R7，本期仅预留二次确认交互）、`platform_ledger` 建表（R8）、凭证上传落库（R9，本期凭证能力后在 R9）、`finance.adjust` 之外的动态权限系统（随 SPEC-§30 二期）。
- **不做**负余额/平台垫付：当前版本禁止退款或红冲产生负余额（ADR-0020）。
- **不做**：充值订单退款的展开实现（退款状态机独立，见 `docs/02-requirements/.../refund-and-reversal.md`）；本期充值主题仅声明退款边界。
- 调账（手动余额调整、红冲）为独立资金主题，本期仅在权限与入账收口处相关，不展开其业务规则。

## 2. 角色与业务场景

### 2.1 角色

| 角色 | 说明 | 充值相关权限点 |
|---|---|---|
| `super_admin` | 全权限（`*`） | 全部资金权限 |
| `admin` | 平台管理员 | `finance.topup`、`finance.adjust` 等 |
| `finance` | 财务 | `finance.topup`（**可创建 + 可审核人工上账**）、充值订单审核；**无** `finance.adjust` |
| `agent / sales` | 业务/销售 | 无任何 `finance.*` 权限点 |
| `customer`（用户） | 被入账/自行充值主体 | 用户侧充值行为，与后台角色无关 |

> 权威依据：ADR-0004（finance 可创建和审核人工上账，但创建人不得审批本人单据；admin 可调账；super_admin 全权限）。`finance` 充值订单审核（audit/reject）归属 `finance.topup`（ARCH §12.1 Q2 裁决）。

### 2.2 业务场景

- **场景 A：用户自助充值（在线支付）** — 用户选金额+支付方式（支付宝/微信）→ 生成订单 pending → 扫码支付 → 渠道回调 → 幂等入账 → 余额增加 → 通知。30 分钟未支付自动 expired。
- **场景 B：用户对公转账充值** — 用户选对公转账 → 上传凭证 → `bank_pending`/`pending_confirm` → 财务审核 → 入账（无余额行自动建户）→ 通知；驳回可重新上传。
- **场景 C：管理员人工上账（线下/对公已到账）** — 管理员（finance/admin/super_admin）搜用户 → 发起人工上账 → 分级审批 → 入账 → 自动建户兜底 → 写流水 → 通知。
- **场景 D（边界）**：充值订单退款走支付渠道原路退款，不同时余额回滚（ADR-0020）。

## 3. 业务规则

以下为已冻结业务规则，来源为 ADR 与主权威来源；来源不明确处标 `【待人工裁决】`。

### 3.1 金额规则（引用 ADR-0001、ADR-0002）

1. **单笔上限（精确）**：
   - **用户自助充值单笔上限：¥1,000,000**（ADR-0001；`open-issues.md` 项 13 明确用户自助充值与人工上账为独立业务对象，不得混同）。
   - **管理员人工上账单笔上限：¥50,000**（ADR-0001、`open-issues.md` 项 13）；超过即拒绝，不进入人工上账终审档；大额对公入账走用户充值订单路径。
   - **管理员调账单笔上限：¥50,000**（ADR-0001）。
2. **最低金额**：用户充值最低 ¥1；人工上账最低 ¥0.01（来源 `ref-2.2.6 §4.4`、PRD-整改 §3.1.2 `amount>0`）。
3. **金额精度（ADR-0002）**：充值、人工上账、调账、退款、红冲输入最多 **2 位小数**（元/分）；余额与 Token 消费内部统一 `numeric(18,8)`；用户展示固定 2 位小数。禁止 JavaScript `Number` 作为金融最终计算依据，使用 Decimal 或数据库 numeric 运算。
4. **单日累计上限**：`open-issues.md` 项 3/13 —— 单日/24h 累计不混用单笔上限；配置键与优先级见 ADR-0022（`limits.operator_24h`、`limits.recipient_24h`、`limits.exceed_action`）。本期人工上账不设单日上限（对公不受限口径），留档 R6 拆分规避使用 `【待人工裁决：是否本期引入 24h 累计限额】`。
5. **审批分级（精确，独立于单笔上限，ADR-0001）**：
   - ≤ ¥10,000：**单人审批**；
   - > ¥10,000 且 ≤ ¥100,000：**双人审批**（一级 + 二级）；
   - > ¥100,000：追加 **`super_admin` 终审**。
   - 与 `ref-2.2.6 §7.2.1` 对公转账分级一致（金额 ≤¥10,000 运营终审；>¥10,000 需财务复审双人；>¥100,000 需 super_admin）。

> 注：主权威来源（PRD-整改 R1–R4，2026-08-18）首期实为单步审核 `pending→paid/failed`，不做分级、不强制创建人≠审核人（分级审批属 R5）。但 ADR-0001/0003/0004（2026-08-29，accepted）已**冻结分级审批与职责分离**。本审阅稿以 ADR 为准：审批分级见 §3.1.5，职责分离见 §6。首期单步实现作为分级模型的过渡形态保留在状态机 §0 说明中。

### 3.2 人工上账业务规则（来源 PRD-整改 §3.1，结合 ADR）

1. **谁可发起**：持有 `finance.topup` 的操作者（finance/admin/super_admin）。无权限点 → 前端隐藏/禁用入口 + 后端 403（ADR-0004）。
2. **给谁上账**：目标用户必须是已存在平台用户（`users` 表），搜索维度：邮箱（精确/模糊）、用户 ID（精确）、手机号（精确，仅对已绑定手机号用户）。用户状态仅 `active` 可入账；`frozen`/禁用拒绝入账（400 `VALIDATION_ERROR`，提示"请先解锁"；ADR 0004 未直接规定用户状态，来源 ARCH §12.1 A7 裁决）。
3. **入账类型**：`topup_type` —— `bank_transfer`（对公/线下到账）与 `grant`（平台赠送/补偿/纠错/客服补单）。首期按 ARCH §12.1 A6 裁决**不新增存储列**；凭证上传能力后置 R9，故"对公必填凭证/单号"校验本期不强制 `【待人工裁决：A6 降低课后是否仍需要 topup_type 区分必填】`。
4. **凭证与转账单号**：凭证格式 JPG/PNG/PDF ≤5MB；`transfer_no` 填写则平台唯一；对公到账建议填写（入库 `metadata.transfer_no`、`evidence_remark`）。`evidence_url` 本期不接受（传入即 400，防止前端误以为已支持上传）。
5. **审核职责分离**：见 §6；分级审批见 §3.1.5。
6. **入账后动作**：审核通过 → 余额入账（自动建户兜底）→ 写资金流水 → 触发 `recharge_success` 通知 → 写审计。
7. **错误入账处理**：本期无独立冲正入口；审核通过后发现错误由 admin/super_admin 走现有调账（红字冲销）纠正（ADR-0003 用独立反向资金记录，不使用退款语义）。

### 3.3 用户自助充值业务规则（来源 ref-2.2.6、SPEC-充值中心）

1. 支付方式：支付宝扫码 / 微信支付 / 对公转账（需审核）；支付渠道熔断时自动隐藏不可用渠道。
2. 用户端 `ALLOWED_METHODS` 不含 `manual`（天然保证 manual 订单只能由管理端创建）。
3. 支付回调：校验签名 → 幂等 → 更新订单 → 增加余额 → 写流水 → 通知；重复/迟到回调幂等忽略；金额不一致 → 保持待验证 + 标记异常 + P0 告警，不增加余额。
4. 订单超时：30 分钟未支付自动 `expired`，过期二维码不可支付，需重新发起充值。
5. 对公转账：用户填金额 + 上传凭证（JPG/PNG/PDF ≤5MB）→ 财务审核 → 入账 / 驳回重新上传；超 72 小时未到账自动 `expired` 并通知。

### 3.4 余额账户兜底（来源 PRD-整改 §3.2）

1. 任何资金入账路径（人工上账审核通过 / 调账生效 / 充值订单审核通过）在更新余额前，若目标用户无 `customer_balances` 行，系统自动创建零余额账户后再入账；建户与入账在同一事务内完成，保证原子性。
2. 建户"存在即跳过"（复用 `initBalance` 的 `ON CONFLICT DO NOTHING` 行为），并发不重复建户、不覆盖已有余额。
3. 三条管理端入账路径统一收口到同一 `creditBalance` 函数；本期收口**仅"加钱方向"**（人工上账审核 / 调账加钱 / 充值审核 audit）；调减、红冲扣钱方向保持现状 UPDATE（ARCH §12.1 Q6）。
4. 自动建户为零金额操作，不改变资金合计口径；建户事件写审计（来源标识 `auto_create`）。

### 3.5 状态与审批阶段（引用 ADR-0003、ADR-0021；详见状态机）

- 业务 `status ∈ {pending, paid, rejected, failed}`；审批阶段独立 `approval_phase ∈ {none, level1, level2, super, completed}`。
- 报销从任一待审核阶段转 `rejected`；入账异常转 `failed`；不使用 `approved` 中间态（充值主题）。
- 管理端响应返回 `status + approval_phase + approval_required`；用户端只暴露 `pending/paid/rejected/failed`。
- `pending_level2`、`pending_super` 为 deprecated 旧响应状态，新接口一律用拆分字段。

## 4. 状态与结果

详见 [充值订单状态机](../../06-data-and-architecture/state-machines/recharge-order.md)。

关键结果语义：
- `pending` = 已创建待审核；`paid` = 资金已入账；`rejected` = 已驳回（不改动余额）；`failed` = 入账执行异常（事务整体回滚）。
- 终态单不可再次审核，重复审核返回冲突码（409 `ORDER_ALREADY_PROCESSED`）。
- 入账成功 = 余额增加 + `balance_transactions` 流水 + `recharge_success` 通知 + 审计。

## 6. 权限与安全（引用 ADR-0004、ADR-0008、ADR-0009）

1. **权限点鉴权（ADR-0004）**：后端统一按权限点鉴权，角色只作权限聚合；前端按权限点控制入口但不得替代后端校验；无权限统一返回 HTTP 403 `PERMISSION_DENIED`；`super_admin` 的 `*` 仅由统一权限守卫解释。
2. **职责分离（ADR-0004）**：强制"创建人 ≠ 审批人、一级审批人 ≠ 二级审批人、终审人不得与前级重复"。数据范围与操作权限分离；权限变更不追溯已完成资金记录。
3. **操作级 2FA（ADR-0008）**：所有资金写操作强制后端操作级 2FA，`super_admin` 不默认豁免；操作 token 一次性、短时、绑定操作者和操作摘要；缺少/未启用返回 `403 OPERATION_2FA_REQUIRED`；适用于收益写端点（人工上账、充值审核、调账、红冲、退款）。前端二次确认不能替代后端校验。
4. **资金幂等（ADR-0009）**：创建类资金操作（`POST /api/v1/recharge`、`POST /api/v1/admin/manual-topup`、`POST /api/v1/admin/adjust`）强制 `Idempotency-Key`；审批、红冲、退款等资金写操作纳入统一幂等规范并执行状态条件更新；Redis 不可用不得静默绕过（503）。Redis 仅作加速锁，DB 约束、事务、状态守卫为最终边界。
5. **前端权限渲染（来源 ARCH §5.5）**：无 `finance.topup` 不显示"发起上账/审核"；无 `finance.adjust` 不显示"发起调账"；不出现"能看见但点不了"的假入口；因权限变化失效时用禁用态 + tooltip"您暂无该操作权限"。

## 7. 通知、审计与合规（引用 ADR-0010）

1. **资金类站内通知强制发送（ADR-0010）**：充值成功、人工上账到账、调账生效、退款完成、红冲完成；Email/SMS/Webhook 等渠道遵循用户偏好。
2. **站内信强制开启不可关闭**（资金到账强通知）；邮件按用户偏好（`emailEnabled` + `emailPreferences.recharge_success` + 频率非 `off`）。
3. **事务与通知分离（ADR-0010）**：资金事务提交成功后写入 outbox/事件，再异步发送；通知失败不回滚资金事务；资金失败不得产生成功通知；重试不得产生重复可见通知。
4. **事件字段（ADR-0010）**：event_id、event_type、aggregate、user、amount、currency、occurred_at、idempotency_key。
5. **审计**：创建/审核/入账写审计（含操作者、审批人、审批时间、审批结果、审批历史、`balance_after`、通知状态）。审批历史单独记录，不与 `status`/`approval_phase` 混用（ADR-0021）。
6. **入账通知文案要点**（来源 PRD-整改 §3.4）：金额、到账后余额、时间、入账类型、关联单据号；事件 `recharge_success` 与 SPEC-§22 事件表一致。

## 8. 页面与交互要求（含 `[?]` 帮助）

> 充值主题涉及两组页面：**用户端充值中心** `ConsoleLayout /console/recharge`（来源 ref-2.2.6、SPEC-充值中心）与**管理端人工上账页** `ConsoleLayout /admin/finance/manual-topup`（来源 PRD-整改 §7/§8）。按 PRODUCT-DESIGN-PRINCIPLES P1，二者标题旁与每个按钮旁均须有 `[?]` 帮助。

### 8.1 页面 HTML 级帮助要求

- 每页标题右侧必有 `[?]` 图标，点击弹出 `PageHelp` 弹窗；
- 每个操作按钮/入口旁必有 `[?]` 图标，悬停显示 `ButtonHelp` Tooltip；
- 帮助内容须与开发/验收内容一致（见 8.3 管理端对照表与 8.4 用户端对照表）；缺失 → 不得进入开发/验收（AGENTS.md P1 红线）。

### 8.2 管理端人工上账页交互（来源 PRD-整改 §3.1.5、ARCH §6.3）

交互流程：列表顶部"发起上账"按钮（`finance.topup` 显隐）→ 表单弹窗（用户选择器/入账类型/金额+余额预览/原因/凭证/转账单号）→ 二次确认弹窗 → toast + 列表刷新；待审核行显示"审核通过/驳回"，均需二次确认与驳回原因，成功后触发入账与通知。

### 8.3 管理端人工上账页 `[?]` 页面帮助

> 数据源：PRD-整改 §7。以下为人工上账页 `PageHelp` 弹窗内容（pageKey `finance-manual-topup`）。

**页面名称**：财务 → 人工上账　**适用角色**：finance / admin / super_admin（调账入口仅 admin/super_admin）

**功能定位**：管理员/财务为指定用户账户进行资金入账。线下/对公转账已到账的，凭凭证走「人工上账」；平台赠送/补偿/纠错的，走「手动调账」。全过程权限点校验、审核留痕、入账必通知。

**核心操作**：① 搜索用户（邮箱 / 手机号 / 用户ID）→ 核对状态与当前余额；② 发起上账 → 选类型 → 填金额/原因/凭证/转账单号 → 确认提交；③ 待审核列表 → 审核通过（入账）或驳回（填原因）；④ 审核通过后用户收到站内信 + 邮件（按偏好）。

**注意事项**：资金变动需二次确认并写审计；对公到账须上传凭证（JPG/PNG/PDF ≤5MB）并填写转账单号（同一单号不可重复入账）；单笔上账不超过 ¥50,000，大额走充值订单/后续分级；无余额账户自动建户后入账；禁用/冻结用户需先解锁；分级审批与职责分离按 ADR-0001/0004 执行。

**常见问题**：Q:finance 为何看不到「发起调账」？A: 调账仅限 admin/super_admin，finance 可发起并审核人工上账。Q:入账后余额没变？A: 检查单据状态，`pending` 未入账、`paid` 已入账，`paid` 后仍未见变动请联系技术排查流水与对账。Q:提示"该转账单号已存在上账记录"？A: 该单号已有一笔上账，请核实勿重复创建。Q:用户未收到到账通知？A: 入账成功即发站内信（不可关闭）；邮件按偏好，可提示用户在「设置 → 通知偏好」开启邮件。

### 8.4 管理端人工上账页 `[?]` 按钮级帮助对照表

## 9. 验收标准（真实可测）

> 以下验收条目对应来源 PRD-整改 §6 与 ARCH §8 真实测试用例；均可在 `pnpm test`（真实 PG+Redis）下验证。

### R-1 用户自助充值
- [ ] `POST /api/v1/recharge`（或 `/me/recharge`）创建订单返回 201、`status=pending`、金额/支付方式正确（ARCH §8 用例 2 参数校验扩展）。
- [ ] 30 分钟未支付自动 `expired`；过期二维码不可支付（ref-2.2.6 §4.2 扩展测试）。
- [ ] 支付回调幂等：重复/迟到回调返回 200 且不重复入账；金额不一致不增加余额（状态机 §4、E15/E16）。
- [ ] 用户自助充值单笔上限 ¥1,000,000 精确校验，超限拒绝（ADR-0001）。

### R-2 人工上账创建/审核
- [ ] 管理端"人工上账"页出现"发起上账"入口（持 `finance.topup` 角色可见），点击弹出表单（ARCH §8 用例 1）。
- [ ] 创建成功新订单以 `pending` 出现在列表（含用户/金额/类型/原因/单号）；字段校验：用户不存在、金额≤0/超限、原因为空、单号重复全被拦截并提示（ARCH §8 用例 2）。
- [ ] 同一转账单号重复创建被拒（`DUPLICATE_BUSINESS_REFERENCE`）。
- [ ] 创建幂等：同 `Idempotency-Key` 重复提交 → 回放/409，`recharge_orders` 仅 1 行（ARCH §8 用例 3）。
- [ ] 审核通过 → `paid`、余额增加、写流水、写 `recharge_success` 通知；驳回 → `rejected` 且记录驳回原因（ARCH §8 用例 5/6）。
- [ ] 重复审核 → 409 `ORDER_ALREADY_PROCESSED`（ARCH §8 用例 5）。
- [ ] 分级审批按金额档位（≤¥10,000 单人 / >¥10,000 双人 / >¥100,000 追加 super_admin 终审）流转（状态机 §2；测试待建真实分级映射）。

### R-3 余额账户兜底
- [ ] 对无余额行用户入账成功，不再 404 `BALANCE_NOT_FOUND`；余额行自动建户且=amount（ARCH §8 用例 4）。
- [ ] 并发建户不重复、不覆盖已有余额（ARCH §8 用例 10）。
- [ ] 无余额行用户登录用户端余额展示 ¥0.00 且不报错。
- [ ] 自动建户事件写审计（来源 `auto_create`），对账金额口径无变化。

### R-4 权限点鉴权
- [ ] finance 角色可创建/审核人工上账、前端可见入口（ADR-0004）；sales/customer 前端无入口且后端 403（ARCH §8 用例 7）。
- [ ] 越权请求统一 403 `PERMISSION_DENIED`，不出现 200 掩盖。
- [ ] 职责分离：创建人≠审批人（金额审批档采用双人时）被拦截（ADR-0004；测试待建）。
- [ ] `hasPerm` 矩阵：super_admin 全放行、admin 有 topup/adjust、finance 有 topup 无 adjust、sales 全无（ARCH §8 用例 13）。

### R-5 入账通知闭环
- [ ] 审核通过 → 用户收到站内信（必发）+ 邮件（按偏好，默认发）（ARCH §8 用例 6）。
- [ ] 文案含金额、到账后余额、时间、入账类型；事件统一 `recharge_success`。
- [ ] 用户关闭邮件偏好 → 仅站内信，站内信不可关闭。
- [ ] 通知失败不影响入账结果；通知记录（失败与重试）可查（ADR-0010）。

### R-6 P1 合规（不可降级）
- [ ] 人工上账页标题旁有 `[?]` 页面帮助，内容与 §8.3 一致。
- [ ] 新增/涉及按钮（发起上账、确认提交、审核通过、驳回、上传凭证、用户搜索等）均有 `[?]` 帮助，内容与 §8.4 一致。
- [ ] 用户端充值中心各操作元素均有 `[?]` 帮助（§8.5）。
