# 核心资金 PRD：退款与红冲

- 文档 ID：PRD-BILLING-004
- 状态：review
- 生效版本：v1.0.0
- 主权威来源：`docs/ref-4.4-finance.md` §4、`docs/ref-9.5-refund.md`、`docs/supplement/03-充值退款状态机.md` §三（与 ADR-0003/ADR-0020 冲突处均已以 ADR 为准，旧冲突口径标记 superseded）
- 上游 ADR：ADR-0001、ADR-0002、ADR-0003、ADR-0004、ADR-0006、ADR-0008、ADR-0009、ADR-0010、ADR-0012、ADR-0020

## 1. 目标与非目标

### 1.1 目标
1. 将退款流程标准化、可追溯、可审计，替代当前"运营手动查余额、调账、手工记录"的不透明流程。
2. 按**业务类型分流**处理退款：消费/API 失败退**余额**、充值订单退**原路**、调账/人工上账纠错走**红冲**（独立反向资金记录），同一业务事件不得并行"原路退款 + 余额回滚"（ADR-0020）。
3. 支持退款类型分型、审核分级（按金额阈值）、渠道失败重试、佣金扣回（仍为既有需求，详见 §7.4 备注）。
4. 当前版本**禁止负余额**：任何退款/红冲导致的扣减在余额不足时返回受控业务错误，不写入负余额（ADR-0020）。

### 1.2 非目标
1. **不**引入平台垫付账户或"下次充值优先抵扣"机制（ADR-0020 明确当前版本不做）。
2. **不**启用 `platform_ledger` 作为退款入账依赖；当前余额与对账依据为 `customer_balances`、`balance_transactions`、业务单据和 `billing_logs`（ADR-0012）。
3. 退款不修改、不删除原单金额（ADR-0020 原单不可修改/删除）。
4. 红冲采用独立反向资金记录语义，不与"退款"语义混用。

## 2. 角色与业务场景

### 2.1 角色
| 角色 | 退款/红冲能力 | 依据 |
|------|--------------|------|
| 运营/客服 | 发起退款申请（不允许依据退款单成为本人初审） | ADR-0004 |
| 财务（finance_ops/财务员） | 初审、执行重试 | ADR-0004、ref-9.5 |
| 财务主管/管理员 | 复审 | ADR-0004 |
| `super_admin` | 全权限，含大额终审 | ADR-0004 |

### 2.2 业务场景
| # | 场景 | 处理类型 | 说明 |
|---|------|---------|------|
| S1 | 消费扣费错误（API 失败多扣） | 余额退款（balance refund） | 退回用户余额，余额只增加一次；需引用关联计费单据 |
| S2 | 充值订单未到账/重复充值/平台责任退款 | 充值订单原路退款 | 走支付渠道原路退回，**不同时余额回滚** |
| S3 | 调账/人工上账纠错 | 红冲（reversal） | 创建独立反向资金记录，原单转 `reversed` |
| S4 | 用户充值后退款（争议等） | 充值订单原路退款 | 走原路退款审核流程，提交争议按争议流程处理 |

> 场景与类型映射以 ADR-0020 为准；ref-4.4 旧口径"order_refund = 原路退回 + 余额回滚"与 supplement "充值已到账则扣回余额" 均被 superseded。

## 3. 业务规则

### 3.1 退款类型与资金方向（ADR-0020）
| 业务类型 | 资金方向 | 负余额 | 备注 |
|---------|---------|--------|------|
| 消费/API 失败退款 | 退回用户余额 | 只加一次，不写负 | 余额只增加一次，禁止同一事件重复补偿 |
| 充值订单退款 | 支付渠道原路退款 | n/a | 不同时执行余额回滚 |
| 调账/人工上账纠错 | 红冲独立反向资金记录 | 禁止负 | 不使用"退款"语义 |
| 扣减类冲销 | 扣减用户余额 | 禁止负 | 余额不足返回受控业务错误 |

### 3.2 审批阈值（ADR-0001）
审批阈值独立于单笔上限，与"人工上账/调账"共用同一套规则：
- 单笔 ≤ ¥10,000：单人审批（财务初审即可，运营/客服可发起）。
- > ¥10,000 且 ≤ ¥100,000：双人审批（初审 + 复审）。
- > ¥100,000：追加 `super_admin` 终审。
- 24 小时累计限额独立定义，不与单笔阈值混用。

> 注：ref-9.5 旧的"≤¥500 客服直接提交、>¥500 复审" 阈值已被 ADR-0001 统一阈值 superseded。

### 3.3 金额与精度（ADR-0002）
- 退款/红冲**输入**最多 2 位小数。
- 内部计算与落库采用 `numeric(18,8)`（余额与 Token 消费）；佣金相关 `numeric(18,4)`。
- 禁止 JS `Number` 作为金融最终计算依据，必须使用 Decimal 或 DB numeric 运算。
- 用户展示固定 2 位小数。

### 3.4 状态流转（ADR-0003/0020）
`pending → approved → processing → completed`；
审核驳回为 `rejected`；执行异常为 `failed`。
- `approved` = 审核通过、尚未完成执行；退款成功后才进入 `completed`。
- `failed` 可按幂等规则重试。
- 完整状态机见 [退款状态机](../../06-data-and-architecture/state-machines/refund.md)。

### 3.5 唯一性与金额上限（ADR-0020）
- 每类退款必须有**独立业务唯一键**和**退款金额上限**。
- 原单金额不可修改、不可删除。
- 业务唯一约束是最终边界，Redis 仅作加速锁（ADR-0009）。

### 3.6 职责分离（ADR-0004）
- 创建人 ≠ 审批人；一级审批人 ≠ 二级审批人；终审人不得与前级重复。
- 前端按权限点控制入口，但不得替代后端校验；无权限统一返回 `403 PERMISSION_DENIED`。

## 4. 状态与结果

引用并展开 [退款状态机](../../06-data-and-architecture/state-machines/refund.md)：
- 用户/客服提交 → `pending`（待审核）。
- 审核通过 → `approved`；驳回 → `rejected`。
- 执行原路/余额退款 → `processing`。
- 成功 → `completed`（终态）；通道异常/执行失败 → `failed`（可按幂等规则重试）。

业务结果（成功完成后）：
| 类型 | 结果 |
|------|------|
| 余额退款 | `customer_balances` 减少对应金额 + `balance_transactions(type='refund')` 记录，余额不得为负 |
| 原路退款 | 只会退款 + 充值订单标记退款状态；不含余额回滚 |
| 红冲 | 生成独立反向资金记录；原单在反向记录成功生效后转 `reversed` |

## 5. 异常与边界

| # | 场景 | 处理 | 依据 |
|---|------|------|------|
| EX-1 | 消费/API 失败退款，用户余额不足 | 拒绝/不可用余额扣减，返回受控业务错误，禁止写负余额 | ADR-0020 |
| EX-2 | 充值订单无法原路（如超期/渠道关闭） | 标记原路失败，可走线下/人工流程（`【待人工裁决】` 线下兜底的具体规则） | ref-9.5、supplement R-004 |
| EX-3 | 重复退款 | 业务唯一键 + 幂等键拦截，返回 `DUPLICATE_BUSINESS_REFERENCE` / `ORDER_ALREADY_PROCESSED` | ADR-0009 |
| EX-4 | 退款金额超过可退金额 | 校验失败，提示"退款金额不能超过可退金额" | ref-4.4 §8.4-4 |
| EX-5 | 通道退款失败 | 自动重试（上限 3 次），仍失败标记 `failed` 需人工处理 | ref-9.5、supplement R-004 |
| EX-6 | 原单已冻结金额 | 退款冻结与退款金额核对顺序需定义 `【待人工裁决】`（冻结口径与 balance_transactions 交互） | ref-9.5 §3 |
| EX-7 | 用户已注销/冻结 | 不允许自动退款，转人工核实 | ref-9.5 §8 |
| EX-8 | 余额并发扣减（通兑超扣） | 行级锁 + 事务，扣减后为负则回滚 | ref-4.4 FIN-004（结合 ADR-0020 禁止负） |

## 6. 权限与安全
- **权限点鉴权**：按权限点控制（ADR-0004），角色仅作聚合；退款/红冲各端点绑定独立权限点。
- **操作级 2FA**：所有资金写操作（退款发起后的审核/执行、红冲）强制后端操作级 2FA，`super_admin` 不默认豁免（ADR-0008）。登录 2FA 与操作级 2FA 分离；token 一次性、短时、绑定操作者与摘要。
- **幂等**：退款/红冲创建与执行纳入统一幂等规范，执行状态条件更新（ADR-0009）。
- **职责分离**：创建人≠审批人、初审人≠复审人（ADR-0004）。

## 7. 通知、审计与合规
- **强制站内通知**：退款完成、红冲完成必须站内通知（ADR-0010）；Email/SMS 等其他渠道遵循用户偏好。
- **outbox**：资金事务提交成功后才写 outbox 异步发送；通知失败不回滚资金事务；资金失败不得产生成功通知；重试不得重复可见通知（ADR-0010）。
- **审计**：所有退款/红冲操作写入审计日志（操作人、前后值、生效时间），含时限与 diff（ref-9.5 关联 §12.1、ARCH R1-R4）。
- **账本**：当前版本仅写 `customer_balances` / `balance_transactions` / 业务单据 / `billing_logs`，不写入 `platform_ledger`（ADR-0012）。
- **合规**：对账平衡公式含退款项；每日对账差异 > ¥0.01 生成异常（ref-4.4 §6）。

## 8. 页面与交互要求
页面标题旁与每个操作按钮旁都必须有 `[?]` 帮助说明（PRODUCT-DESIGN-PRINCIPLES）。

**退款/红冲管理页（admin → 财务 → 退款管理）**：
- 列表：筛选（状态/类型/时间/搜索订单号或用户）、分页、统计卡片（今日/本月退款笔数与金额）。
- 操作：发起退款、初审、复审、驳回、执行/重试、红冲、详情。
- 各操作按钮旁 `[?]` 悬停说明；页面标题旁 `[?]` 页面帮助弹窗。
- 审核弹窗展示退款详情 + 用户账户状况；执行前置 2FA。
- 交互规范详见表单与校验（见 PRD 侧条目：退款表单字段 = 用户、退款金额、退款类型、关联订单、原因、是否通知用户、备注）。

## 9. 验收标准
1. **分型退款**：消费/API 失败 → 只退余额且只加一次；充值订单 → 只走原路；调账纠错 → 只走红冲；任一输入不得同时触发原路+余额回滚（ADR-0020，真实集成测试）。
2. **禁负余额**：余额不足的扣减/冲销返回受控业务错误，DB 中不出现负余额；行级锁并发下不超扣（ADR-0020、ADR-0006）。
3. **审批阈值**：≤¥10k 单人、>¥10k 双人、>¥100k 终审；创建人≠审批人（ADR-0001、ADR-0004，映射到测试）。
4. **2FA**：发起审核/执行/红冲未带有效 2FA token 时拒绝（ADR-0008）。
5. **幂等**：同 Idempotency-Key 重放返回首次结果；不同摘要返回 409；重复凭证/已处理单据分别返回固定错误码（ADR-0009）。
6. **状态机**：`pending→approved→processing→completed`，驳回 `rejected`，执行异常 `failed` 可重试（ADR-0003/0020）。
7. **审计/通知**：退款/红冲完成触发审计与站内通知；通知失败不影响资金事务结果（ADR-0010）。
