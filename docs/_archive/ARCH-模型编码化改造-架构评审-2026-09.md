## 〇、结论摘要

1. **数据方案可行，但必须采用两阶段迁移**：`supplier_models.model_code` 部分唯一索引适合回填期，但不足以保证 active 行必填、编码不可修改和不可复用。`consumption_records` 是按 `created_at` 分区表，新增 `model_code` 必须对分区父表迁移并验证子分区。
2. **路由最小侵入方案**：保留 `selectTaskChannel`，重写 `selectChannel`。`selectChannel` 按 `model_code` 精确锁定唯一 `supplier_model` 和 supplier，只允许在该 supplier 的 Key 池内切换 Key；不得切到其他供应商或其他编码。chat、completions、embeddings、messages、responses、anthropic、rerank、ws-relay 均需接入；任务型 `task-relay` 保留按 `apiType` 选择。
3. **最高风险**：现有 `mockFallback` 违反"纯编码、无自动兜底"。改造后无效编码/分组禁止/编码不可用必须分别 404/403/400，且在预扣与上游调用前失败，不得产生消费记录。

## 一、数据层收口

### 1.1 `supplier_models.model_code`

- 采用 **部分唯一索引**（`WHERE model_code IS NOT NULL`）先回填；回填完成后建议升级约束确保 active 行必填。
- 新增列 Drizzle Schema：`supplier-models.ts` 增加 `modelCode` 列（`varchar(200)`），并加唯一索引（参考现有 `uq_supplier_models_model_code` 定义）。
- migration：参考 `api/src/db/migrate.ts` + migrations 目录机制，用 drizzle-kit generate 生成迁移；回填脚本放 `api/scripts/` 或 `api/src/db/seed.ts` 风格的一次性脚本。

### 1.2 `consumption_records` / `call_logs`

- `consumption_records` 为 `created_at` 分区表：新增列必须**对分区父表迁移**，并验证所有子分区继承该列。
- `call_logs`（lib/gateway-log 相关）确认是否存在 `model_code`；若无则加。
- 回填：能由 `supplier_model_id` 回溯则回填，否则置空。

## 二、路由重写评审

### 2.1 现状

- `selectChannel(model, opts)`：按 `model_name` 自动选第一个可用供应商（priority/分组/熔断）。
- `selectTaskChannel(apiType, opts)`：任务型渠道（midjourney/suno）按 `apiType` 选，请求体不含 model 名。

### 2.2 改造方案（最小侵入）

- **保留 `selectTaskChannel`**（任务型无 model 名，仍需按 apiType 选）。
- **重写 `selectChannel`**：入参改为 `modelCode`（必填），按 `model_code` 精确锁定唯一 `supplier_model` + supplier；只在该 supplier Key 池内选 Key；不得切供应商/编码。
- `modelMapping.platformModel` 仍用于构造上游请求体（`buildUpstreamBody(req, platformModel)`）。

### 2.3 接入点清单（逐一确认）

| 端点/路由 | 现状 selectChannel 用法 | 改造 |
|-----------|------------------------|------|
| `api/src/routes/chat.ts` | `selectChannel(req.model)` + `buildUpstreamBody` | 改传 `req.model`（即 model_code）精确锁定 |
| `api/src/routes/openai-compat.ts` | completions/embeddings | 接入 |
| `api/src/routes/messages.ts` | 接入 | 接入 |
| `api/src/routes/responses.ts` | 接入 | 接入 |
| `api/src/routes/anthropic.ts` | 接入 | 接入 |
| `api/src/routes/rerank.ts` | 接入 | 接入 |
| `api/src/services/upstream/ws-relay.ts` | 接入 | 接入 |
| `api/src/routes/task-relay.ts` | 任务型 → `selectTaskChannel` | **保留** |

## 三、`parseModelCode` 收口

- 签名：`parseModelCode(model: string): { code: string }`（严格模式，无 auto）。
- 逻辑：先查 `model_code` 唯一索引；`model` 为空 / 裸名 / 含 `@` / 不命中 → 一律 `MODEL_CODE_NOT_FOUND`(404)。
- 错误：`MODEL_CODE_NOT_FOUND`(404)，`MODEL_CODE_UNAVAILABLE`(400 + `availableModelCodes`)，`GROUP_FORBIDDEN`(403)。
- 放置：`api/src/services/upstream/routing.ts` 或独立 `api/src/services/upstream/model-code.ts`。

---

## 四、默认编码偏好（user_vendor_selections 复用）

- 若表存在：`user_id + model_id + vendor_id`；需确认 `model_id` → `supplier_models.id` 语义。
- 建议：新增列 `model_code` 快照（或模型归属承载逻辑模型 id），`vendor_id` 语义收敛为"默认编码对应的 supplier_models"。若改造字段语义过脏，更稳妥是**新建** `user_model_default_codes(user_id, model_name, model_code, ...)`，一次性清洗，避免复用 `user_vendor_selections` 的历史混杂语义。（backend 需先读 schema 判断。）

## 六、风险与 Gate

1. **mockFallback 泄漏**（最高风险）：无渠道仍走 mock 成功记账 → 必须改为精确失败，预扣前 404/403/400。
2. **分区表迁移**：consumption_records 分区父表加列后子分区未继承。
3. **ws-relay / task-relay 混用**：误把 selectTaskChannel 改成严格编码会破坏任务型。
4. **编码回填唯一冲突**：批量生成需去重 + 序号兜底。
5. **默认编码偏好语义**：复用 user_vendor_selections 可能引入历史脏数据，若如此则新建表更稳。

> Gate：G1 数据层迁移+回填校验；G2 路由/接口单测全绿 + tsc 0 错误；G3 前端；G4 端到端（无效编码预扣前失败、编码独立路由计费、偏好生效）；G5 文档同步。
