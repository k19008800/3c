## 2. 背景与目标

### 2.1 背景（引用整改方案）

整改方案（RECT-2026-ADMIN-RECHARGE-001）阶段一（R1–R4，P0 止血）已收官：人工上账可创建、余额账户自动兜底、权限点鉴权生效、入账必通知。但**资金安全三层**（权限点校验 → 分级审批 → 2FA + 二次确认）中后两层尚未落地，阶段一 PRD 明确将其留至阶段二：

| # | 问题（整改方案原文） | 现状依据 | 核心影响 |
|---|---------------------|---------|---------|
| P1-5 | **充值审核/人工上账无分级审批**：单步 approve 即入账，无金额阈值、无双人 | `recharge.ts:373-422`、`admin-finance-missing.ts:210-274` 单步审核；对照 `ref-2.2.6 §7.2.1`（>¥10,000 财务复审、>¥100,000 super_admin） | 大额资金单点放行，舞弊/误操作风险 |
| P1-6 | **调账免审批阈值可拆分规避**：调增 <¥10,000 免审批；无操作人/被调用户 24h 累计限额 | `admin-adjust.ts:44-47` `calcApproval`（`amount >= 10000 ? level1 : none`） | 9 × ¥9,999 可绕过审批 |
| P1-7 | **无 2FA + 二次确认后端强制** | `SPEC-§20` L3（余额调整等写操作需 2FA + 二次确认）；`2fa.ts` 仅登录链路（setup/enable/disable/verify/status），资金路由无 2FA 校验 | 账号被盗/越权操作可直达资金 |

> 另含配套口径统一项：P2-14 三处金额口径（大额预警 ¥10,000 / 调账审批线 ¥10,000 / 对公双档 ¥10,000–¥100,000）在 R5 统一大额规则下收敛，用户端单笔上限口径归属产品裁决（见 §9 差异 6）。

### 2.2 阶段目标

阶段二（约 2~3 周）完成 P1 风控闭环，使整改方案 §4.5 目标流程中的风控节点可验收：

```
资金写操作（人工上账创建/审核、调账发起/审批/红冲、充值订单审核、退款审核）
  → ① 权限点校验（R3 已建）
  → ② 操作级 2FA（我是本人）AND 二次确认（我确认操作）（R7 新增，后端强制）
  → ③ 24h 累计限额预检（操作人维度 + 被入账用户维度）（R6 新增，先查限额）
  → ④ 审批定级 = max(金额档, 限额升级档)（R5 统一大额规则，可配置）
  → ⑤ 单审 / 双人 / 追加 super_admin 终审（创建 ≠ 审批、一级 ≠ 二级）
  → ⑥ 入账（R1–R4 收口：余额兜底 + 流水 + 通知 + 审计）
```

### 2.3 产品设计原则对齐

- P1（不可降级）：本期涉及页面/按钮全部按本 PRD 第 7、8 节实现 `[?]` 帮助；
- P3（操作可逆与安全优先）：资金写操作 = 2FA + 二次确认 + 分级审批 + 全程审计；错误入账仍走红冲（不删除不编辑）；
- P4（状态可见性）：审批链每一环节的状态、审批人、限额升级原因在列表/台账可见；超限、锁定、令牌过期等均有明确提示。

## 3. 功能模块清单

### 3.1 R5 分级审批统一（对应 P1-5）

### 3.1.1 业务规则

1. **统一大额规则（业务口径，可配置）**：三类资金单据 —— 人工上账（manual-topup）、充值订单审核（recharge_order，含用户自助对公转账）、调账调增（adjustment）—— 统一按**入账金额**分级：
   - 入账金额 **≤ ¥10,000**：**单审**（一级审批，1 人）；
   - 入账金额 **> ¥10,000**：**双人审批**（一级 + 二级，创建人 ≠ 一级 ≠ 二级）；
   - 入账金额 **> ¥100,000**：**追加 super_admin 终审**（三人链：一级 → 二级 → super_admin 终审）。
   - 金额边界语义：恰为 ¥10,000 → 单审档；¥10,000.01 起 → 双人档；恰为 ¥100,000 → 双人档；¥100,000.01 起 → 终审档（对齐 ref §7.2.1"≤¥10,000 / >¥10,000 / >¥100,000"三档）。
   - 阈值全部来自 `finance_rules.large_amount` 配置（见 3.1.2），默认值如上，运营可改（配置权限见 §4）。
2. **判定基数**：人工上账 / 充值订单 = 订单 `amount`；调账调增 = 调增金额。**红冲（加钱方向）**按反向记录金额走同一套大额规则（反向记录作为新单据定级）。
3. **调减规则（裁决项 B1）**：建议**调减与调增同档**（≤¥10,000 单审、>¥10,000 双人、>¥100,000 追加 super_admin），口径统一；为不放松现状风控（现状调减 ≥¥10,000 即二级），建议保留特例"**调减恰为 ¥10,000 仍按双人档**"（即调减档位 = max(同档规则, 现状更严语义)）。最终以裁决为准。
4. **免审批的取舍（裁决项 B2）**：建议**取消"调增 <¥10,000 免审批"**（现状 `approvalLevel='none'` 提交即生效档废止），全部调增至少一级审批；同时提供**可选的白名单科目免审开关（默认关闭）**：
   - 开启时：科目 ∈ `{赠送, 补偿, 纠错}` **且** 单笔 ≤ ¥1,000 **且** 调增方向 → 免审（提交即生效），**且免审单同样计入 R6 24h 累计限额**；
   - 关闭时（默认）：所有调增至少一级审批，与人工上账 / 充值审核口径一致。
   - 理由：① 金额型免审是拆分规避（9×¥9,999）的直接根源，取消后 R6 限额兜底压力显著减小；② 三路径（人工上账 / 充值审核 / 调账）审批口径统一，收敛 P2-14 三处口径；③ 白名单免审为运营日常小额补偿保留效率出口，但以"更低免审线（¥1,000）+ 计入累计限额 + 科目白名单"三重约束兜底，不产生可被拆分的漏洞。
   - 依赖说明：科目白名单字典完整版属 R11（阶段三）；R5 阶段以最小集合 `{赠送, 补偿, 纠错}` 常量 + 配置承载，R11 上线后切换为字典驱动（见 §9 差异 7）。
5. **职责分离（对齐阶段一调账既有语义，扩展至全部单据）**：
   - 创建人 / 申请人 **≠** 审批人（任一审批环节）；
   - 一级审批 **≠** 二级审批；
   - super_admin 终审人 **≠** 前两级审批人（且 ≠ 创建人）；
   - super_admin 是否豁免"创建 ≠ 审批"：见裁决项 B4（默认不豁免，走降级代审机制）。
6. **审批状态机**：各单据在分级下的状态流转见 3.1.3；核心是人工上账 / 充值订单在单步 `pending` 基础上扩展 `pending_level2`（待二级复核）与 `pending_super`（待 super_admin 终审）环节，调账在既有 `pending / pending_level2` 基础上扩展 `pending_super`（level3）。
7. **越权与体验（裁决项 B4/B15）**：
   - **审批人不足降级**：双人档的"第二人"不限于 finance，可为任一持有对应权限点的 admin / super_admin（跨角色兜底，权限点见 §4）；若全平台仍无人可审（如仅一名 finance 且其为创建人）→ 单据滞留当前环节，创建人侧提示"审批人不足，已通知管理员"，系统通知 super_admin；
   - **super_admin 兜底代审**：审批人持续不足或滞留超时（SLA 见裁决项 B15，对齐 ref §7.2.2：初审 T+0.5、复审 T+1）时，super_admin 可代审，审计记录强制标记"降级代审 + 原因"；
   - **前端体验**：职责分离不满足时审批按钮禁用 + tooltip"您不能审批自己发起的单据"；双人档第一人通过后，单据在第二人队列可见并标注"待双人复核"。
8. **大额规则配置化（对齐 `finance-rules.ts` 模式）**：新增 `finance_rules.large_amount` 配置段，读取优先级 配置 → 常量默认值，缓存 60s，读失败回退常量（与 R1 `getManualTopupMaxAmount` 同一机制，扩展实现即可）。
9. **配置变更生效时点（裁决项 B18）**：建议**按单据提交时点固化审批级别**——单据创建时读取当时生效的大额规则定级并落库，此后阈值调整不影响存量待审单据；新提交单据使用新规则。
10. **审批人落库**：一级 / 二级 / 终审审批人分别落库（人工上账 / 充值订单建议 reviewer_id / reviewer2_id / super_reviewer_id，存储形态由 arch-agent 裁决，可复用 `recharge_orders.metadata` 或新增列；调账已有 approvedBy / reviewedBy，新增 superReviewedBy）。驳回任一步骤记录驳回原因。

### 3.1.3 审批状态机

**人工上账 / 充值订单（recharge_order）**

```
创建（pending）
  ├─ 单审档（金额 ≤ ¥10,000）
  │     ├─ 一级通过 → paid（入账 + 流水 + 通知 + 审计）
  │     └─ 一级驳回 → failed（记驳回原因）
  ├─ 双人档（¥10,000 < 金额 ≤ ¥100,000）
  │     ├─ 一级通过 → pending_level2 ── 二级通过 → paid
  │     └─ 任一步驳回 → failed
  └─ 终审档（金额 > ¥100,000，充值订单适用；人工上账受单笔上限 ¥50,000 约束，见边界 E11 / 裁决 B3）
        ├─ 一级通过 → pending_level2 ── 二级通过 → pending_super ── super_admin 通过 → paid
        └─ 任一步驳回 → failed
终态：paid / failed；paid 后不可再审批（错误入账走红冲）。
```

**调账（adjustment）**（none 档废止后）

```
发起（定级：金额档 + R6 限额升级，无免审档或按白名单免审开关）
  ├─ level1（单审档）：pending ── 一级通过 → approved（生效）
  ├─ level2（双人档）：pending ── 一级通过 → pending_level2 ── 二级通过 → approved
  ├─ level3（终审档）：pending ── 一级通过 → pending_level2 ── 二级通过 → pending_super ── super_admin 通过 → approved
  ├─ 任一步驳回 → rejected
  └─ approved 后可红冲 → reversed（反向记录作为新单据按规则重新定级）
状态机约束：仅当前环节状态可流转（原子守卫，对齐阶段一 P1-2 修复语义）；已终态单据不可再审批。
```

### 3.1.4 前端交互（产品描述）

- **人工上账页**（`/admin/finance/manual-topup`）：列表新增"审批级别 / 当前审批环节"列（单审 / 双人复核 / 待终审）；审核弹窗在双人档 / 终审档时展示审批链进度（"一级已通过，待二级复核"）；职责分离不满足时审批按钮禁用 + tooltip；

### 3.2 R6 拆分规避与限额（对应 P1-6）

### 3.2.1 业务规则

1. **操作人 24h 累计限额（裁决项 B5）**：同一操作人 **24h 滚动窗口**内"加钱方向运营操作"（人工上账创建、调账调增发起、红冲加钱方向发起）累计金额上限，**建议值 ¥50,000**（对齐人工上账单笔上限 ¥50,000，语义"单笔上限 = 单日累计上限"，便于运营记忆与 P2-14 口径统一）。
2. **被入账用户 24h 累计限额（裁决项 B6）**：同一被入账用户 24h 内被"加钱方向运营操作"累计上限，**建议值 ¥50,000**（跨操作人合并计数 —— 多个操作人给同一用户上账也受此约束，防"多人分摊拆分"）。
3. **拆分规避的业务说明（回答"9×¥9,999 如何被兜住"）**：
   - 9 × ¥9,999 单笔均 ≤ ¥10,000，按 R5 金额档全部为单审 —— 但**操作人维度 24h 累计**在第 6 笔（累计 ¥59,994 > ¥50,000）起**强制升级为双人审批**；
   - 被入账用户维度同理：若同一用户 24h 内被累计加钱 > ¥50,000，后续每笔升级双人；
   - 双维度任一超限即升级本笔；单笔 >¥10,000 本身即双人档，故"拆分"只能靠累计限额兜住 —— 累计限额因此是 R6 的核心防线；
   - 免审白名单单（若开关开启）同样计入累计，不能通过免审拆单绕过。
4. **超限行为（裁决项 B7）**：默认 **强制升级审批**（`exceed_action='escalate'`）：
   - 本笔审批级别 = **max(按金额定级, 双人档)**（即至少双人审批；若本笔按金额已是双人档则保持双人档，不自动升终审）；
   - 提供配置 `exceed_action='reject'`（超限直接拒绝），由运营在配置中切换；两种行为均即时生效（读配置）。
5. **叠加关系（先查限额 → 再定审批级别）**：资金写操作提交时，**先**计算 24h 累计（含本笔）判断是否超限，**再**按金额（R5）定级；最终级别 = 金额档与限额升级档取更严者。流程见 3.2.3。
6. **窗口语义**：24h **滚动窗口**（从当前时刻回看 24h），非自然日；跨日 / 跨周自然滚动，无需定时任务重置。
7. **豁免（裁决项 B8）**：**super_admin 默认不豁免**限额（限额防拆分，与角色无关；super_admin 的大额操作本就走双人/终审链，豁免会重新打开拆分漏洞）；提供配置 `exempt_roles`（默认空数组）供运营按需豁免，豁免记录写审计。
8. **计数范围（裁决项 B9/B10）**：
   - **计入**：人工上账创建（提交即预占）、调账调增发起、红冲加钱方向发起 —— 按**创建/提交时点**计入；
   - **不计入**：调减（扣钱方向，风险语义不同且已按更严档审批）、充值订单审核（用户自助充值，走支付渠道自身风控）、兑换码入账；
   - **驳回 / 红冲不回退累计（裁决项 B19）**：已计入的单据即使后续被驳回或红冲，累计不回退（保守风控，防止"提交-撤销-再提交"循环绕过；红冲本身另计新累计）。
9. **限额与单据状态**：限额判定在单据创建时一次性完成并固化级别（与 B18 同语义）；单据创建后累计已含本笔，后续并发提交逐笔原子判定（先到先得，后笔按新累计升级/拒绝）。
10. **提示文案（产品侧）**：
    - 升级："您 24 小时内已累计调增/上账 ¥X（限额 ¥50,000），本笔将升级为双人审批"；
    - 拒绝："您 24 小时内累计入账已超过限额（¥50,000），本笔已拒绝。如有特殊情况请联系管理员"；
    - 用户维度升级："该用户 24 小时内已被累计入账 ¥X（限额 ¥50,000），本笔将升级为双人审批"。

### 3.2.2 字段 / 配置定义表

**限额配置（`system_config` key=`finance_rules.limits`，JSON）**

| 配置键 | 业务含义 | 默认值 | 校验 | 备注 |
|--------|---------|-------|------|------|
| `limits.operator_24h` | 操作人 24h 累计上限（元） | `50000` | 正数 | 裁决 B5 |
| `limits.recipient_24h` | 被入账用户 24h 累计上限（元） | `50000` | 正数 | 裁决 B6 |
| `limits.exceed_action` | 超限行为 | `escalate` | `escalate` / `reject` | 裁决 B7 |
| `limits.exempt_roles` | 豁免角色列表 | `[]` | 角色名数组 | 默认空；super_admin 不豁免（裁决 B8） |
| `limits.count_decrease` | 调减是否计入 | `false` | boolean | 裁决 B9 |

### 3.2.3 限额判定流程（先查限额 → 再定审批级别）

```
资金写操作提交（人工上账创建 / 调账发起 / 红冲发起）
  ① 权限点校验（R3）
  ② 操作级 2FA + 二次确认（R7）
  ③ 24h 累计预检（含本笔）：
     a. 操作人维度：Σ(操作人 24h 内计入单据金额) + 本笔 → 是否 > operator_24h
     b. 被入账用户维度：Σ(该用户 24h 内被计入金额) + 本笔 → 是否 > recipient_24h
     c. 任一超限 → exceed_action = escalate ? 升级标记 : 拒绝返回
  ④ 审批定级：
     level = 金额档（R5 大额规则）
     若升级标记 → level = max(level, 双人档)
     若免审条件满足（白名单开关开启且命中）且无升级标记 → 免审
  ⑤ 生成单据（pending / pending_level2 / pending_super / approved[免审]），
     limit_escalated / escalation_reason 落库，累计已含本笔
```

### 3.2.4 前端交互（产品描述）

- 提交表单：触发升级时，提交前在二次确认弹窗内展示"本笔将升级为双人审批（累计超限 ¥X/¥50,000）"；触发拒绝时阻断提交并展示拒绝文案（见规则 10）；
- 列表 / 台账：新增"限额升级"标记（如"累计超限·已升级双人"）与"审批级别"列；
- （可选，标注）管理端提供"操作人 / 用户 24h 累计查询"辅助运营判断，本期不作为验收必选项；
- 配置页（风控规则配置）：大额规则 + 限额 + 2FA 策略统一在一个配置页（页面与 `[?]` 帮助见第 7 节）。

### 3.3 R7 操作级 2FA + 二次确认（对应 P1-7）

### 3.3.1 业务规则

1. **适用范围（建议清单，裁决项 B16）**：以下资金写操作要求**操作级 2FA + 二次确认**（后端强制，与 SPEC-§20 L3 对齐）：
   - 人工上账：创建、审核（通过）、复核（通过）、驳回；
   - 调账：发起、一级审批（通过）、二级复核（通过）、驳回、红冲（发起 / 审批）；
   - 充值订单：审核（audit 通过）、驳回；
   - 退款审核：通过（依赖 `admin-finance-stats.ts` 现状模块，路由鉴权需从 adminAuth 收敛到权限点，见 §9 差异 8）；
   - 建议**驳回/拒绝类同样要求 2FA**（防恶意驳回；不改余额但改单据状态，身份验证必要），二次确认可简化（仅摘要 + 确认）；
   - 只读操作（列表 / 台账 / 待审队列 / 限额查询）**不要求**操作级 2FA。
2. **校验时机与流程**：操作前输入 TOTP 码（或备用码）→ 服务端校验 → 通过后签发**操作授权令牌**（short-lived）→ 本次操作请求携带令牌 → 服务端校验令牌有效后执行；**服务端强制，不得仅前端拦截**。
3. **令牌有效期与复用（裁决项 B11）**：建议 **5 分钟**有效期（对齐登录 tempToken 语义）；**窗口内同一操作者的资金写操作可复用**（5 分钟内免重复输入，适配批量审核场景）；每次资金写操作均校验令牌（存在且未过期）；令牌不可跨操作者使用。实现形态（JWT / Redis / 一次性 vs 窗口复用）由 arch-agent 裁决，本 PRD 只定业务语义。
4. **未启用 2FA 的操作者（裁决项 B12）**：建议 **`mandatory_admin` 策略（默认）** —— 资金操作角色（finance / admin / super_admin）执行资金写操作前**必须已启用 2FA**；未启用 → 操作被拦截并引导跳转 2FA 设置页（管理端安全设置），启用后方可操作；策略提供 `disabled` 档（全部关闭，不推荐）。**与登录 2FA 策略解耦**：登录 2FA 仍按 SPEC-§20 现有 `two_factor_policy`（可保持 optional 等），操作级 2FA 由独立策略 `operation_2fa_policy` 控制（系统 × 用户开关 = AND 的两级开关语义沿用 §20.2）。
5. **备用码（裁决项 B13）**：**允许**用于操作级 2FA（与登录一致）；备用码**一次性**，使用后作废并从剩余列表移除（复用 `2fa.ts` verify 的备用码消费语义）；备用码用尽时提示重新生成或仅用 TOTP。
6. **失败处理（裁决项 B14）**：TOTP / 备用码连续错误达到阈值（**建议 5 次**，对齐 SPEC-§20 登录锁定）→ **锁定 15 分钟** → 锁定期间操作级 2FA 请求返回 429 + 前端倒计时；**建议与登录 2FA 失败计数共享**（同一账户安全状态，避免攻击者分链路分别试探）；锁定写审计并通知管理员（安全事件，对齐 §20.2 登录锁定告警语义）。
7. **二次确认的关系（AND）**：操作级 2FA = **"我是本人"**（身份验证），二次确认 = **"我确认要操作"**（意图确认），两者为 **AND** 关系，任一缺失后端拒绝。
8. **前端弹窗顺序（产品建议）**：**同一弹窗两步** —— 第一步输入 TOTP/备用码验证身份；通过后弹窗内切换第二步展示操作摘要（单据类型 / 用户 / 金额 / 到账后余额预览 / 审批级别 / 限额升级提示）与 **[确认执行]**；两步全部通过才发送请求。理由：先验身份再确认意图，避免未验身份先见摘要；单弹窗两步比双弹窗跳转更顺（P2 一致性）。
9. **2FA 重置联动**：管理员强制重置某用户 2FA（`POST /admin/2fa/reset/:userId`，SPEC-§20 既有）→ 该用户全部未过期操作令牌立即失效，下次资金操作须重新启用 2FA。
10. **审计**：操作级 2FA 校验成功 / 失败 / 锁定 / 令牌签发均写审计日志（含操作者、操作类型、结果、IP）。
11. **复用现状能力**：`totp.ts` 的 `verifyTOTP`（±1 窗口容差）、`verifyBackupCode`（bcrypt 比对）、`generateBackupCodes` 与 `2fa.ts` 的备用码一次性消费语义可直接复用；操作级 2FA 不改变登录 2FA 现有实现。

### 3.3.2 字段 / 配置定义表

**操作级 2FA 策略配置（`system_config` key=`finance_rules.operation_2fa`，JSON）**

| 配置键 | 业务含义 | 默认值 | 校验 | 备注 |
|--------|---------|-------|------|------|
| `operation_2fa.policy` | 操作级 2FA 策略 | `mandatory_admin` | `mandatory_admin` / `disabled` | 资金角色强制（裁决 B12） |
| `operation_2fa.token_ttl_seconds` | 操作令牌有效期（秒） | `300`（5 分钟） | 正数 | 裁决 B11 |
| `operation_2fa.lock_threshold` | 连续失败锁定阈值 | `5` | 正整数 | 与登录共享计数（裁决 B14） |
| `operation_2fa.lock_minutes` | 锁定分钟数 | `15` | 正整数 | 对齐 SPEC-§20 |
| `operation_2fa.allow_backup_code` | 是否允许备用码 | `true` | boolean | 裁决 B13 |
| `operation_2fa.scopes` | 适用操作清单 | 见规则 1 | 枚举数组 | 增删操作需同步前端弹窗 |

**操作令牌（业务对象，实现形态由 arch-agent 裁决）**

| 属性 | 业务含义 | 说明 |
|------|---------|------|
| 持有者 | 操作者用户 ID | 不可跨操作者 |
| 签发时间 / 过期时间 | 5 分钟窗口 | 过期需重新验证 |
| 适用范围 | 资金写操作（scopes） | 窗口内复用 |
| 状态 | 有效 / 已失效 | 2FA 重置、锁定、过期即失效 |

### 3.3.3 操作级 2FA 流程

```
进入资金写操作（点击 创建/审核/复核/驳回/红冲/终审 等）
  ① 检查操作者 2FA 启用状态
     ├─ 未启用（policy=mandatory_admin）→ 拦截 + 引导启用（跳转 2FA 设置页），操作终止
     └─ 已启用 → 继续
  ② 弹窗第一步：输入 TOTP 码 / 备用码
     ├─ 校验失败 → 提示"验证码错误" + 失败计数 +1
     │     └─ 连续 5 次失败 → 锁定 15 分钟（429 + 倒计时 + 告警）
     └─ 校验通过 → 签发操作令牌（5 分钟）
  ③ 弹窗第二步：操作摘要 + [确认执行]（二次确认）
  ④ 提交请求（携带操作令牌 + 二次确认标记）
  ⑤ 服务端校验：令牌有效（存在/未过期/持有者匹配）AND 二次确认 → 权限点 → 限额预检（R6）→ 审批定级（R5）→ 执行
  ⑥ 令牌持续有效至过期；窗口内后续资金操作免重复输入（每次仍校验令牌）
```

### 3.3.4 前端交互（产品描述）

- 资金操作按钮点击 → 弹出"身份验证"弹窗（第一步：TOTP/备用码输入框，自动聚焦 6 位）；
- 未启用 2FA：弹窗内提示"执行资金操作需先启用双因素认证" + [前往启用]（跳转管理端安全设置）；
- 锁定：弹窗展示倒计时（15:00），锁定期间输入框禁用；
- 验证通过 → 同弹窗切换第二步：操作摘要（用户/金额/到账后余额/审批级别/限额提示）+ [确认执行] / [返回修改]；
- 成功 → toast + 列表刷新；失败 → 明确错误（令牌过期 / 验证码错误 / 锁定）；
- 备用码输入切换（"无法使用认证器？使用备用码"），与登录 2FA 页交互一致。

- 职责分离以**单据维度**判定：创建人（申请人）≠ 任一审批环节操作者；一级 ≠ 二级 ≠ 终审；跨角色兜底时第二人可为任一持对应权限点者（见 3.1.1 规则 7）；
- super_admin 终审档不占用 finance 审批名额，三人链独立计数（裁决 B4 的"super_admin 代审降级"是审批人不足时的例外路径，审计必标记）；
- `agent` / `sales` / `customer` 角色无任何 `finance.*` 权限点，不进入本矩阵（R3 已收口，越权 403）；
- 配置类权限点归属（`sys.config` 或新增 `finance.rule_config`）待裁决（B17），本期建议并入 `sys.config`（admin / super_admin），2FA 策略仅 super_admin。

## 7. ### [?] 页面帮助

> 数据源：以下内容作为各页面 `PageHelp` 弹窗内容（pageKey 建议：`finance-manual-topup`、`finance-adjust`、`finance-recharge-audit`、`finance-pending-approval`、`finance-risk-config`，最终由 frontend-agent 按现有帮助组件约定落地）。

### 7.1 财务 → 人工上账 / 充值订单审核

**页面名称**：财务 → 人工上账 / 充值订单审核

**适用角色**：财务（finance）、管理员（admin / super_admin）；持 `finance.topup` 权限点

**功能定位**：管理员/财务为指定用户进行资金入账（线下/对公到账凭凭证入账、用户自助充值确认到账），全过程分级审批、双因素认证、二次确认、留痕可冲正。

**核心操作**：
1. 发起人工上账（用户 → 金额 → 凭证/单号 → 提交）
2. 待审核列表 → 按单据金额进入对应审批环节：≤¥10,000 单审；>¥10,000 双人复核；>¥100,000 追加 super_admin 终审（充值订单）
3. 审核通过 → 入账 → 用户收到到账通知；驳回 → 填写原因
4. 审核前必须通过操作级 2FA（输入 TOTP/备用码）并二次确认

**注意事项**：
- 审批人不能审批自己发起的单据（职责分离）；一级与二级审批不能为同一人
- 发起/审核均为资金写操作，后端强制 2FA + 二次确认
- 操作人 24h 累计入账超过 ¥50,000 后，后续入账升级为双人审批
- 单笔人工上账不超过 ¥50,000
- 错误入账通过红字冲销纠正，禁止直接修改/删除
- 所有入账写资金流水与审计日志，用户收到站内信（必发）

**常见问题**：
Q: 为什么审核按钮被禁用并提示"不能审批自己发起的单据"？
A: 平台强制职责分离：创建人/申请人不能审批自己发起的单据，请由其他持有财务权限的操作者审批。
Q: 提示"待双人复核"是什么意思？
A: 该单据金额超过 ¥10,000，一级审批已通过，需另一名审批人（不能是一级审批人本人）完成二级复核后才能入账。
Q: 提交时提示"将升级为双人审批"？
A: 您 24 小时内累计调增/上账已超过 ¥50,000 限额，本笔自动升级为双人审批以控制拆分风险。
Q: 输入验证码后提示"身份验证已过期"？
A: 操作级 2FA 验证结果 5 分钟内有效，超时需重新输入验证码。

### 7.2 财务 → 手动调账（发起 / 待我审批 / 调账台账）

**页面名称**：财务 → 手动调账

**适用角色**：管理员（admin / super_admin）；持 `finance.adjust` 权限点（finance 角色不可见）

**功能定位**：为指定用户调增/调减余额（平台赠送、补偿、纠错、扣减），按金额分级审批，防拆分，全程审计，错误调账可红冲。

**核心操作**：
1. 发起调账：选择用户 → 方向（调增/调减）→ 金额 → 会计科目 → 原因 → 提交
2. 金额 ≤¥10,000 单审；>¥10,000 双人复核；>¥100,000 追加 super_admin 终审
3. 待我审批：一级/二级/终审队列，排除自己申请的单据
4. 调账生效后错误可「红字冲销」生成反向记录

**注意事项**：
- 调增免审批已取消（除非开启白名单科目免审：仅赠送/补偿/纠错且 ≤¥1,000）
- 申请人 ≠ 审批人；一级 ≠ 二级；红冲需独立审批
- 操作人/被入账用户 24h 累计调增+上账超过 ¥50,000 → 后续笔升级双人审批
- 资金写操作需 2FA + 二次确认
- 错误调账不删除不编辑，通过红字冲销纠正

**常见问题**：
Q: 调增 ¥500 也要审批吗？
A: 默认是的（免审批已取消）；若运营开启白名单免审（赠送/补偿/纠错科目且 ≤¥1,000），符合条件的调增可提交即生效。
Q: 为什么"待我审批"看不到某些单据？
A: 该队列已排除您自己申请的单据（职责分离）。
Q: 调减如何审批？
A: 调减按金额分级：≤¥10,000 单审、>¥10,000 双人复核（恰为 ¥10,000 亦双人，保留更严语义），与调增同档统一。

### 7.3 设置 → 风控规则配置（大额规则 / 限额 / 2FA 策略）

**页面名称**：设置 → 风控规则配置

**适用角色**：super_admin（2FA 策略）；admin / super_admin（大额规则与限额，权限归属待裁决 B17）

**功能定位**：配置统一大额审批规则、24h 累计限额与操作级 2FA 策略，全局即时生效（新提交单据按新规则定级）。

**核心操作**：
1. 大额规则：单审上限（默认 ¥10,000）、双人触发线（>¥10,000）、super_admin 终审线（>¥100,000）、白名单免审开关
2. 限额：操作人 24h 累计、被入账用户 24h 累计（默认 ¥50,000）、超限行为（升级/拒绝）、豁免角色
3. 2FA 策略：操作级 2FA 开关（mandatory_admin / disabled）、令牌有效期、锁定阈值

**注意事项**：
- 配置变更即时生效；已提交单据的审批级别按提交时点固化，不受后续调整影响
- 保存配置为敏感写操作，需 2FA + 二次确认并写审计
- 不建议将超限行为设为"拒绝"以外长期策略误用（默认升级）

**常见问题**：
Q: 修改阈值后存量待审单据会怎样？
A: 存量单据沿用提交时确定的审批级别，不受新配置影响。
Q: 为什么 2FA 策略只有 super_admin 能改？
A: 2FA 策略属最高安全策略，仅超级管理员可调整，防止低权限者自降风控。
