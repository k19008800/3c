## 2. 分级缺陷清单

### 🔴 P0 阻断（0 个）

### 🟠 P1 严重（3 个）

#### P1-1 转账单号（transfer_no）全平台唯一性未实现 — R1 验收"重复创建同单号被拒"落空

- **位置**：`api/src/routes/admin-finance-missing.ts:331-366`（创建端点仅校验 `transfer_no` 长度 ≤ 100 并写入 `metadata.transfer_no`，无任何唯一性检查；全仓无对应唯一索引/表达式索引）
- **缺陷描述**：双签裁决 A6（ARCH §12.2）明确"`transfer_no` 填写则**全平台唯一**"（对应 PRD §3.1.3 C9 / 边界 B4 / 整改方案 R1 验收"重复创建同单号被拒"，是防重复入账的第一道闸）。当前实现下，同一银行流水号可在不同 Idempotency-Key 下重复创建多笔 pending 单，经两次审核即**重复入账**——幂等（Idempotency-Key）只防"同一请求重放"，不防"同单号不同请求"。
- **违反条款**：PRD §3.1.3 C9、§6 R1 验收；ARCH §12.2 裁决 A6；整改方案 R1 验收要点（任务分配单）；资金安全（防重复入账）。
- **修复建议**：创建端点校验 `SELECT 1 FROM recharge_orders WHERE metadata->>'transfer_no' = $1 LIMIT 1`（存在 → 409/400，文案"该转账单号已存在上账记录"）；并发场景追加表达式唯一索引 `CREATE UNIQUE INDEX uq_recharge_orders_transfer_no ON recharge_orders ((metadata->>'transfer_no')) WHERE metadata->>'transfer_no' IS NOT NULL`（随 0028 迁移）；补"同 transfer_no 二次创建被拒"测试用例。

#### P1-2 调账审批生效 / 红冲缺事务内原子状态守卫 — 并发重复审批可致资金重复变动

- **位置**：`api/src/routes/admin-adjust.ts:296-336`（approve/review 状态检查在**事务外**读 `rec.status`）、`applyApproval` `339-422`（事务内 `update ... set status='approved'` **无** `where status='pending'/'pending_level2'` 守卫，`379-387`）、`reverse` `445-533`（`519-521` 将原记录置 `reversed` 的 update 无 `where status='approved' AND reversed_by_id IS NULL` 守卫）
- **缺陷描述**：两个并发 approve/review 均先读到 `status='pending'` 通过预检，随后各自开事务执行 `creditBalance`（调增）或裸 UPDATE（调减）并置 `approved` —— 同一调账被**双重入账/双重扣减**；红冲同理可**双重复红冲**。对照：同批改造的 `manual-topup` review（`admin-finance-missing.ts:460-465`）与 `recharge.ts` audit（`381-387`）均在事务内用 `where status='pending'` 原子守卫 + `returning()` 判空，adjust 路径未对齐。ARCH §9.2 风险表明确声称"并发重复审核（双击）→ 现状 where status='pending' 原子守卫**保留**，R2 收口不改此语义"，本实现与之一致性不成立。
- **违反条款**：ARCH §9.2（原子守卫保留声明）；coding-standards-control-logic.md §二（状态机应用层+DB 双防线）；PRD B6/B18（重复审核余额不重复累加、通知不重复触发）。
- **修复建议**：`applyApproval` 事务内末尾 update 增加 `and(eq(id), eq(status, 'pending'))`（或 `pending_level2`）并检查 `rowCount`，0 行抛 `ORDER_ALREADY_PROCESSED`（409/422）；`reverse` 中"置原记录 reversed"的 update 增加 `and(eq(status,'approved'), isNull(reversed_by_id))` 守卫；补并发双 approve / 双 reverse 测试用例（对标 §8 用例 10 的并发风格）。

#### P1-3 GET /admin/recharge-orders 列表未纳入 finance.topup — 与 D2 财务导航冲突，A4 闭环断裂

- **位置**：`api/src/routes/recharge.ts:307`（列表仍 `adminAuth`，仅 admin/super_admin）；`web-console/src/layouts/ConsoleLayout.tsx:149`（FINANCE_NAV 为 finance 渲染"充值订单 finance.topup"菜单）
- **缺陷描述**：ARCH §12.4 D2 裁决为 finance 角色渲染含"充值订单"的最小财务导航（按 `finance.topup` 过滤），而 ARCH §5.4 替换清单只把 recharge 的 audit/reject 换为 `requirePerm('finance.topup')`，GET 列表未换。结果：finance 角色点入充值订单页 → `GET /admin/recharge-orders` 403 → **A4"finance 角色可审核充值订单"端到端不可达**（能审但看不到可审的单）。属 ARCH §5.2/§5.4 与 §12.4 D2 之间的契约冲突，backend 实现忠实于前者、违背了后者的用户体验意图。
- **违反条款**：ARCH §12.4 D2（finance 导航含充值订单）；ARCH §5.2 权限表 A4 裁决意图（audit/reject 放行 finance）；PRD §4 矩阵。
- **修复建议**：调度裁决二选一——（a）推荐：`GET /api/v1/admin/recharge-orders` 一并挂 `requirePerm('finance.topup')`（一行改动，与 D1 搜索端点同思路，不放开全量客户数据）；或（b）从 FINANCE_NAV 移除"充值订单"菜单。修复后补 finance 访问列表 200 的测试。

### 🟡 P2 一般（4 个）

#### P2-1 驳回（reject）未强制填写驳回原因

- **位置**：`api/src/routes/admin-finance-missing.ts:449`（`body.note?.trim() || null` 容忍空）
- **缺陷描述**：PRD §3.1.2 `review_note`"驳回时必填"、边界 B17"驳回时未填原因 → 拦截"，验收项"驳回 → failed 且记录驳回原因"。当前后端接受空原因（前端弹窗虽必填，后端无强制）。
- **违反条款**：PRD §3.1.2、B17、§6 R1 验收。
- **修复建议**：reject 分支加 `if (!String(body.note ?? '').trim()) throw new ValidationError('请填写驳回原因')`；补测试。

#### P2-2 通知策略事件名双命名不统一 — 后台策略无法控制充值邮件

- **位置**：`api/src/services/notify.ts:83,133`（按 `event_type === event` 匹配，event=`'recharge_success'`）；`api/src/routes/admin-permissions.ts:234`（策略界面事件字典为 `'recharge.success'`）
- **缺陷描述**：ARCH §12.2 Q4 已把 `notifications.type` 与 `email_templates.name` 统一为 `recharge_success`，但 `notification_policies_list` 的 event_type 命名仍停留在 `recharge.success`（admin-permissions.ts NOTIFY_EVENT_LABEL）。管理员在策略界面为"充值成功"建 `{channel:'email', event_type:'recharge.success', enabled:false}` 不会命中 notify.ts 的 `recharge_success` 匹配 → 关闭邮件策略**不生效**（默认发送）。
- **违反条款**：ARCH §6.1 策略语义（channel/event_type/enabled 生效）；PRD §3.4.2 邮件按偏好。
- **修复建议**：统一命名（策略事件字典补 `recharge_success`，或 notify.ts 兼容匹配 `recharge.success` 与 `recharge_success` 两种写法）；补"策略 enabled=false → email=skipped"测试。

#### P2-3 新端点未用 Zod schema 校验（规范 §1.3 偏差）

- **位置**：`api/src/routes/admin-finance-missing.ts:307-342`（手工 Number/String 校验）
- **缺陷描述**：编码规范 §1.3 要求"所有输入必须校验：body、query、params 全都要 Zod schema"。本期新增 POST 创建 / D1 搜索 / review 均手工校验（功能上覆盖完整，测试也覆盖），属规范偏差；与文件现状风格一致，非本次新引入的技术债模式。
- **违反条款**：coding-standards-api-db-test.md §1.3。
- **修复建议**：本期可用轻量 zod schema（`createManualTopupSchema` 等）收口，或列入二期债务清单统一治理。

#### P2-4 人工上账列表未回显 transfer_no / reviewer_id（硬编码 null）

- **位置**：`api/src/routes/admin-finance-missing.ts:243-244`
- **缺陷描述**：PRD §6 R1 验收"创建成功后新订单以 pending 状态出现在列表（含用户/金额/**类型/原因/凭证/单号**）"。当前列表 `transfer_no: null`、`reviewer_id: null` 为占位（ARCH §9.1 裁决"GET 列表契约不变，占位字段保持"）——数据实际已在 `metadata` 中，但列表不回显 → PRD 验收项与 ARCH 契约冲突。
- **违反条款**：PRD §6 R1 验收（列表含单号）；ARCH §9.1（保持占位）——契约冲突。
- **修复建议**：从 `metadata` 读出 `transfer_no`/`reviewer_id` 填充列表响应（低成本、不破坏兼容）；或由调度确认 PRD 验收口径后置 R9 凭证方案。

## 3. 门禁结论

### 首次评审（2026-08-18 初评）：❌ 不通过

**理由**：任务分配单 Gate 5 条件为"review-agent **无 P0/P1 缺陷**；规范抽查（JSDoc/错误类型）通过"。初评发现 **3 个 P1 缺陷**：

**说明**：P2/P3 不阻塞 Gate，可随二期或本批顺手修复；其中 P2-1（驳回原因必填）为一行修复，建议随 P1 一并处理。
