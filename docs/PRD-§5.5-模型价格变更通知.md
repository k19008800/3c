# 产品需求文档：§5.5 模型价格变更通知

> **所属章节**：§5 核心引擎（置于 §5.4 通知与告警之后）
> **优先级**：P1
> **核心价值**：当上游供应商调价或平台调整售价时，自动判断哪些用户需要知道、用最合适的方式通知，帮用户省钱/避坑

---

## 一、业务背景

3cloud 平台接入 130+ 模型、40+ 供应商，上游定价经常变动（降价竞争、成本波动、版本迭代等）。普通用户日常只高频使用 1-3 个模型，其他模型只是后备选项。

**问题**：
- 如果每次调价都通知所有用户 → 通知轰炸 → 用户屏蔽所有通知
- 如果不通知 → 用户突然发现费用暴增 → 投诉/流失
- 用户最需要知道的不是"什么变了"，而是"什么变了对**我**有影响"

**核心设计思想**：
> 平台替用户判断什么值得通知，而不是让用户自己设关注。

判断依据 = **变动幅度 × 消费占比 × 可替代性系数**

---

## 二、影响指数模型

### 2.1 影响指数公式

```
影响指数 = |变动幅度| × 用户月消费占比 × 可替代性系数

变动幅度：新旧价格的百分比差（如 +30%、-15%）
用户月消费占比：该模型在用户近 30 天总支出的占比
可替代性系数：0.3~2.0，该模型在同类型中是否容易被替代
```

### 2.2 可替代性系数

| 系数 | 含义 | 判断标准 |
|------|------|---------|
| 0.3 | 几乎不可替代 | 同类型活跃模型 ≤ 1 |
| 0.6 | 有替代品但差距大 | 同类型 2-3 个且用户仅用此模型 |
| 1.0 | 中等可替代 | 同类型 3-5 个活跃模型 |
| 1.5 | 高可替代性 | 同类型 ≥ 5 个且用户在该类中使用 ≥ 2 个模型 |
| 2.0 | 完全商品化 | 同类型 ≥ 8 个且存在多个更低价格的选择 |

自动计算方式：
```
基数：
- 同类型活跃模型 ≥ 8 个 → 1.5
- 同类型活跃模型 5-7 个 → 1.2
- 同类型活跃模型 2-4 个 → 1.0
- 同类型活跃模型 = 1 个  → 0.5

调整因子：
- 用户在该类型下使用了超过 2 个不同模型 → +0.3
- 存在同类低价模型（价差 > 30%）→ +0.3
- 该模型用户历史有切换记录 → +0.2
- 该模型用户从未切换过且用了超过 3 个月 → -0.2
```

### 2.3 影响指数示例

| 模型 | 变动 | 消费占比 | 可替代性 | 指数 | 分级 |
|------|------|---------|---------|------|------|
| deepseek-chat 涨价 30% | 30% | 60% | 1.8 | 32.4 | 🔴 A |
| GPT-4o 涨价 50%（独此一家）| 50% | 40% | 0.3 | 6 | 🟡 B |
| Claude 降价 20%（竞品多）| 20% | 25% | 1.5 | 7.5 | 🟡 B |
| qwen-max 涨价 15%（有替换）| 15% | 5% | 1.2 | 0.9 | ⚪ C |
| embedding 涨价 100%（只此一家）| 100% | 0.5% | 0.3 | 0.15 | ⚪ C |

## 三、三级通知策略

### 🔴 A 级 — 重要变动（立即通知）

**触发条件（满足任一）：**
- 影响指数 > 8
- 可替代性系数 ≥ 1.0 且涨价幅度 > 15%（用户该切了）
- 可替代性系数 ≥ 1.5 且降价幅度 > 15%（用户该切回来了）
- 任意模型从免费变收费 或 从收费变免费

**推送方式：**
- 站内信（单独一条）
- 如果用户有已验证邮箱 → 发邮件
- 不合并，不延迟

**通知内容构成：**
- 模型名 + 变动方向 + 幅度
- 旧价 → 新价
- 生效时间
- 影响的 API Key 列表
- 替代模型建议（涨价时必带，降价时可选）

### 🟡 B 级 — 参考变动（摘要通知）

**触发条件（满足任一）：**
- 影响指数 3-8
- 影响指数 < 3 但变动幅度 > 20% 且用户近 30 天有调用的模型

**推送方式：**
- 站内信（合并为「本周/本月模型价格调整汇总」）
- 不单独发邮件
- 频率上限：每周最多 1 条

**汇总通知内容：**
```
标题：【价格周报】您关注的 3 个模型价格有调整

本周调整概要：
- deepseek-chat 降价 30%（您现在 ¥0.35/M 即可使用）
- GPT-4o 涨价 20%（同类替代：deepseek-chat、qwen-plus）
- glm-5-pro 涨价 8%（小幅波动）

查看完整详情 → [链接]
```

### 🟢 C 级 — 噪声（不通知，只记录）

**触发条件（满足任一）：**
- 影响指数 < 3
- 用户近 90 天无调用
- 从未调用过的模型
- 变动幅度 < 5%

**处理方式：**
- 不推送任何通知
- 用户端「通知中心 → 价格变动」标签页可查
- 首页「近期价格变动」小角标提示数量

### 📋 通知分级总表

| 场景 | 变动方向 | 可替代性 | 通知级别 |
|------|---------|---------|---------|
| 竞品多 + 涨价 | 涨 | 高 | 🔴 即时通知 + 替代建议 |
| 竞品多 + 降价 | 降 | 高 | 🔴 即时通知（帮省钱）|
| 独此一家 + 涨价 | 涨 | 低 | 🟡 摘要通知（告知但用户没得选）|
| 独此一家 + 降价 | 降 | 低 | 🟢 不通知 |
| 消费占比低 + 波动小 | 任何 | 任何 | 🟢 不通知 |

## 四、用户端功能

### 4.1 通知灵敏度设置

用户不需要手动选择关注的模型，只需要选一个灵敏度档位：

```
通知中心 → 通知偏好 → 价格变动通知灵敏度

  ○ 精简 — 只通知替代性高的模型调价（推荐）
  ● 标准 — 默认，按影响指数自动分级
  ○ 全面 — 所有调用过的模型调价都通知（周汇总）
  ○ 关闭通知 — 不推送，登录后可查
```

用户不理解"可替代性"，他的实际感受：
- **精简**：「只告诉我真该知道的」
- **标准**：「合理」
- **全面**：「什么都知道比较好」

### 4.2 价格变动查看

**位置**：通知中心 → 新增「价格变动」标签页

**列表视图**：
```
┌────────────────────────────────────────┐
│  价格变动                   [灵敏度设置] │
├────────────────────────────────────────┤
│ ▸ deepseek-chat ─ 降价 30% ─ 07/28    │
│   ¥0.50 → ¥0.35，8月1日生效          │
│   影响您的 2 个 API Key ××  ... 查看   │
├────────────────────────────────────────┤
│ ▸ GPT-4o ─ 涨价 20% ─ 07/25          │
│   ¥3.00 → ¥3.60，已生效               │
│   替代方案：deepseek-chat（¥0.35）...   │
└────────────────────────────────────────┘
```

**单个模型历史**：点击进入模型详情页，可查看该模型最近 6 个月的调价时间线。

## 五、管理端功能

### 5.1 价格变更总览

**位置**：管理后台 → 系统管理 → 价格变更

**功能**：
| 功能 | 说明 |
|------|------|
| 全部变更列表 | 按时间倒序，含变更前/后价格、幅度、操作人 |
| 用户影响统计 | 每条变更覆盖了多少用户、触发了多少通知 |
| 通知状态 | 已推送/待推送/用户已读率 |
| 手动推送 | 管理员可重新触发某条变更的通知分发 |
| 数据导出 | CSV 导出变更记录和推送统计 |

### 5.2 可替代性配置

**位置**：管理后台 → 定价管理 → 可替代性系数

管理员可手动调整系统自动计算的系数（覆盖），应对冷启动或特殊情况。

| 字段 | 说明 |
|------|------|
| 模型 | 下拉选择 |
| 自动系数 | 系统当前计算的系数值 |
| 手动覆盖 | 可选（留空则使用自动计算） |
| 覆盖原因 | 必填（如："实际用户反馈该模型无替代品"）|

## 六、数据库设计

### 6.1 price_change_logs 价格变更日志表

```sql
CREATE TABLE price_change_logs (
  id              SERIAL PRIMARY KEY,
  model_id        INT NOT NULL REFERENCES models(id),
  vendor_id       INT NOT NULL REFERENCES vendors(id),
  old_cost_price  DECIMAL(12,6),
  new_cost_price  DECIMAL(12,6),
  old_sale_price  DECIMAL(12,6),
  new_sale_price  DECIMAL(12,6),
  change_rate     DECIMAL(5,2),      -- 变动幅度百分比
  effective_at    TIMESTAMPTZ NOT NULL,
  reason          VARCHAR(500),       -- 变动原因（上游调价/平台调整/活动结束等）
  operator_id     INT REFERENCES users(id), -- 管理员手动改价时记录
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_price_change_model_effective
  ON price_change_logs(model_id, effective_at DESC);
```

### 6.2 user_notifications 表新增枚举值

```typescript
// 新增 notificationTypeEnum 值
"price_increased_major",      // 🔴 重要涨价
"price_decreased_major",      // 🔴 重要降价

"price_decreased_minor",      // 🟡 一般降价
"price_weekly_summary",       // 🟡 每周价格汇总
"price_monthly_summary",      // 🟡 每月价格汇总
"price_alternative_suggest",  // 🔴 替代模型推荐
```

### 6.3 users 表新增字段

```sql

ALTER TABLE users ADD COLUMN price_notify_sensitivity VARCHAR(10)
  DEFAULT 'standard' CHECK (price_notify_sensitivity IN ('minimal', 'standard', 'full', 'none'));
```

## 七、服务拆分

新增服务 `services/price-alert-service/`，协调 4 个已有模块：

```
services/price-alert-service/
├── index.ts              ← 导出入口
├── types.ts              ← 类型定义
├── change-log.ts         ← 价格变更日志 CRUD
├── impact-calc.ts        ← 影响指数计算引擎
├── substitutability.ts   ← 可替代性系数计算（调用 stats-usage-service）
├── dispatch.ts           ← 通知分发决策（A/B/C 级判断）
└── summary.ts            ← 周/月汇总生成
```

**依赖的已有模块：**
- `services/pricing/` → 定价写入时自动记变更日志
- `services/stats-usage-service/` → 用户-模型消费分布
- `services/notification-service/` → 通知推送
- `routes/me/` → 用户端查询接口

## 九、定时任务

| 任务名 | 频率 | 执行逻辑 |
|--------|------|---------|
| dispatch-price-notifications | 每小时 | 扫描 effective_at 已到但未分发的 price_change_logs，计算影响指数，写入 A/B 级通知 |
| generate-weekly-summary | 每周一早 8 点 | 汇总上周所有 B 级变更，合并为「本周价格变动周报」推送给有相关变更的用户 |
