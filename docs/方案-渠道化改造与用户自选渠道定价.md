# 方案 — 渠道化改造与用户自选渠道定价

> **定位**：3cloud 平台「渠道/渠道」术语全局统一 + 用户自主选择渠道及渠道价目公布的实施方案
> **版本**：v1.0（评审稿）
> **日期**：2026-08
> **状态**：待评审 → 拆解为 PRD/Spec 并派发多 Agent
> **基础约束**：本改造遵循 AGENTS.md「产品设计基础要求」——每个功能页标题旁与每个操作按钮旁必须有 `[?]` 帮助说明。

---

## 一、背景与目标

### 1.1 背景
3cloud 平台当前把"上游提供 API Token/模型的渠道"称作 **渠道/渠道（Supplier / Vendor）**，把它的 Key、模型、定价分别建模为 `suppliers`、`supplier_keys`、`supplier_models`、`vendor_pricing`。业务上这套实体**本身就是一个会登录、会上传 Key、会被平台结算的完整业务角色**（有独立渠道门户 `VendorLogin/VendorDashboard/VendorSettlement` 与结算体系）。

参考 New API 项目，"**渠道（Channel）**"被定义为"平台上游提供 token 的渠道"——这正是 3cloud 平台 `suppliers` 的实际定义。因此需要把对外中文口径全局统一为"**渠道**"，消除"渠道/渠道/Supplier/Vendor/渠道"混用。

同时，当前同一模型可能由多个渠道提供，但**用户端只能看到一个统一模型+单一价格**（`/me/models` 返回硬编码 `DEFAULT_MODELS` 单价格），无法自选渠道、也无法按渠道比价。需支持用户自主选择渠道，并公布每个渠道对每个模型的售价。

### 1.2 决策基线（用户已拍板）
| # | 决策点 | 结论 |
|---|--------|------|
| D1 | 渠道与渠道的关系 | **渠道 = 渠道**（有结算体系的业务实体）；后台管理人员看到"渠道"即理解为上游渠道 |
| D2 | 文档术语表口径 | **只改中文文案 / UI / 文档**；**不改**数据库表名、字段名、代码标识符（`suppliers` 等保留） |
| D3 | 用户自选默认策略 | 用户未选择渠道 → 走**"自动智能路由"**（系统按健康度/价格/延迟选最优渠道）|
| D4 | 渠道与模型唯一标识 | **(模型 × 渠道)** 定义一个唯一可路由标识 → 采用 `model@channelCode` 语法（channelCode = `suppliers.code`）|

### 1.3 目标
1. **术语统一**：全平台中文稿（后台 UI、用户端、文档、运营手册）将"渠道/渠道"统一改为"渠道"。
2. **用户自选渠道**：允许用户在调用时从"同一模型的多个渠道"中自主选择；不选则自动路由。
3. **渠道价目公布**：平台公布每个渠道对每个模型的售价，同一模型不同渠道可有不同价格，用户可比价、自选。

## 二、术语统一方案（需求一）

### 2.1 统一术语对照表（对外文档与 UI 口径）
| 旧中文 | 新统一中文 | 英文/底层标识（**不改**） | 说明 |
|--------|-----------|--------------------------|------|
| 渠道 / 渠道 / Vendor | **渠道** | `suppliers`（表名保留） | 上游提供 token/模型的业务实体，含结算体系 |
| 渠道 Key | **渠道 Key / 渠道密钥** | `supplier_keys` | 渠道凭据，多 Key 轮换 |
| 渠道-模型映射 | **渠道-模型映射 / 渠道模型** | `supplier_models` | 某渠道提供的某模型 |
| 渠道-模型定价 | **渠道模型售价 / 渠道价目** | `vendor_pricing` | 渠道对模型的售价（区分为"售价"与内部"成本价"）|
| 渠道自助门户 | **渠道中心 / 渠道门户** | Vendor 系页面 | 渠道侧登录、Key 管理、结算 |

> 注：英文底层标识按 D2「不改」，因此**代码、接口路径、数据库列名维持 `supplier/vendor` 不变**，仅对外展示层与文档做中文化替换。可在代码注释/JSDoc 中同步增加"渠道"别名说明，便于后续维护者理解语义对齐 New API。

### 2.2 改造范围（仅文案/UI/文档层）
1. **后台管理端（web-console）**：所有 `渠道/渠道/Vendor` 中文标签、菜单、面包屑、空态文案、`[?]`帮助文案 → "渠道"。
2. **用户端（web-console 用户区 / model center）**：渠道筛选项、价格明细弹窗里的"渠道"文案 → "渠道"。
3. **渠道自助端（Vendor* 页面）**："渠道门户" → "渠道中心"；"渠道结算" → "渠道结算"（业务角色不变，仅称谓统一）。
4. **营销站（web-portal）**：`/models`、`/pricing` 页面中品牌/渠道描述统一术语。
5. **文档层**：`kb/3cloud/*`、`docs/*`、PRD/Spec/Ref 中涉及的中文称谓统一替换为"渠道"，并更新术语表。
6. **全局术语表维护**：在 `docs/` 维护一份"3cloud 术语对照表"，供所有 Agent 与后台人员查阅（含新旧对照、英文底层标识不变说明）。

> **明确不做（D2）**：不改表名 `suppliers`、字段名 `supplier_id`、接口路径 `/admin/suppliers`、前端组件名 `AdminSupplier*`、类型 `Supplier` 等代码标识符。

## 三、用户自选渠道 + 渠道价目公布方案（需求二）

### 3.1 现状核对（已确认）
- ❌ `model@vendor` 语法**尚未在后端实现**（api 无任何 `parseModelVendor` 解析）。
- ❌ `VendorSelectorPage.tsx` 使用**硬编码 mock 数据**（`MODEL_VENDORS` 静态表），后端 `/vendors/by-model` 端点缺失，页面**未挂到路由**。
- ❌ `/me/models` 返回硬编码 `DEFAULT_MODELS`（单一价格、单一 `provider` 品牌字段），**无按渠道展开的多价格**。
- ✅ 路由层 `selectChannel(model, {userId})` 已具备按渠道分组供给（`allowedGroups`）、多 Key 选择、熔断跳过等能力，**只差"按指定渠道锁定"的解析入口**。

### 3.2 (模型 × 渠道) 唯一标识设计（D4）
- **标识语法**：`model@channelCode`，其中 `model` = 模型名（如 `deepseek-chat`），`channelCode` = 渠道编码（`suppliers.code`，唯一，如 `vendor_a`）。
- **语义**：`model@channelCode` 全局唯一对应一条可路由的「渠道-模型」映射（即 `supplier_models` 上一条记录）。
- **解析规则**（新增，落入路由层）：
  ```
  请求体 model 字段 → parseModelVendor(model)
    ├─ 不含 '@'        → model 原样，走"自动智能路由"（D3）
    ├─ 含 '@' 拆出 code → 校验 channelCode 是否存在且 active
    │     ├─ 该渠道是否提供该模型（存在 supplier_models 匹配）
    │     ├─ 该渠道是否服务调用方分组（allowedGroups）
    │     └─ 通过 → 锁定该渠道 + 该模型映射；选 Key；返回可路由组合
    └─ '@' 后无内容 / 渠道不存在 / 渠道不提供该模型 / 渠道不可用
          → 返回 4xx + 错误码 + 可选渠道列表（含各自价格）供用户修正
  ```
- 未传渠道（自动路由）与显式 `model@channelCode` 的优先级：显式锁定优先；运维应急"路由覆盖"仍高于用户选择（沿用 `user-vendor-selection.md` 附录 C 规则）。

### 3.3 渠道价目公布（用户侧可见 "售价"，隐藏"成本价"）
- **数据**：`supplier_models`（channel+model+platformModel）已与 `vendor_pricing`（售价，含 input/output、缓存读/写）关联；内部成本价列（`cost_*`）**绝不对用户展示**。
- **用户可见价格口径**：价格取自 `vendor_pricing` 售价字段（输入/输出、缓存读/写），单位规范化展示（¥/1K 或 /1M tokens），同一模型各渠道允许不同售价。
- **公布载体**：
  - `GET /api/v1/me/models` → 升级为**按渠道展开**：返回该用户可见的所有 (模型×渠道) 组合及各渠道售价，前端模型中心据此渲染每个模型的渠道价格对比。
  - 新增 `GET /api/v1/models/:modelName/channels` → 返回指定模型下所有可用渠道及各自售价、健康度、延迟、状态（等价于现有设计的 `/vendors/by-model`，改用渠道口径）。
  - 模型中心 / 渠道选择器页面展示对比表（输入/输出价、缓存价、健康分、延迟、状态、推荐/维护标签）。

### 3.4 用户自选交互
- **默认**：模型选中后默认"自动智能路由"（不指定渠道），调用 `model` 不带 `@`。
- **手动**：用户点选某渠道 → 请求 `model@channelCode` 锁定该渠道。
- **渠道选择器**：在模型中心/调用入口提供渠道下拉或对比选择器；字段含渠道名、售价（输入/输出/缓存）、健康分、延迟、推荐/维护标记。
- **保存默认**（可选增强 P1）：允许用户为"模型"保存默认渠道偏好，落 `user_vendor_selections`（沿用既有设计表）。
- **价格公布矩阵**：平台提供任意模型下的"渠道×价格"矩阵展示，让用户有完整自主权比价选择。

### 3.5 关键体验（验证/验收重点）
| 场景 | 预期 |
|------|------|
| 用户不选渠道调用 `deepseek-chat` | 自动路由最优渠道，行为同现状，零迁移成本 |
| 用户选渠道调用 `deepseek-chat@channel_b` | 锁定 channel_b，走其 Key 池，按 channel_b 售价计费 |
| 用户选渠道下架/维护中 | 该渠道禁用；若已保存偏好则自动回退自动路由并通知 |
| 渠道不提供所选模型 | 返回错误+可选渠道列表（含价格）|
| `/me/models` 多渠道展示 | 同一模型展示多个渠道行，价格可不同 |

## 四、工作量边界与执行路径

> 本方案改动跨 3 层，按 AGENTS.md `spawn-protocol.md` 拆分派发。所有编码子代理先读 5 份编码规范，执行可由 dispatch-agent 并行派发产品/架构后再串行后端→前端→测试→运维→交付。

### 4.1 阶段划分
| 阶段 | 内容 | 涉及 Agent | 产出 |
|------|------|-----------|------|
| P0 数据支撑 | 确认 `supplier_models`/`vendor_pricing` 可支撑"同模型多渠道"，必要时补 `(supplier_id, model_name)` 唯一索引或查询口径 | arch + backend | 数据层齐备 |
| P1 后端能力 | ① `parseModelVendor` + 路由层"按渠道锁定"；② `/me/models` 升级为按渠道展开；③ 新增渠道价格公布端点；④ `/me/models` 价格统一来自 DB（替换/兼容 DEFAULT_MODELS）| backend | 接口文档 |
| P2 前端接入 | ① 模型中心显示渠道价格矩阵；② 渠道选择器接入真实 API 并挂路由；③ 后台/用户端术语改为"渠道"| front | 页面落地 |

| P4 验证 | 术语抽查 + 自选渠道端到端（不选自动路由/选渠道锁定/下架回退）+ `[?]`帮助齐全 | test | 测试报告 |

### 4.2 里程碑 Gate
| Gate | 条件 |
|------|------|
| G1 | 后端 `model@channel` 解析 + 渠道价格透出端点单测全绿；`tsc --noEmit` 0 错误 |
| G2 | 前端模型中心价格矩阵 + 渠道选择器可用；后台/用户端关键页术语切换完成 |
| G3 | 全库中文称谓改为"渠道"，术语对照表落地；`[?]`帮助抽查通过 |
| G4 | 端到端验收全部通过（含自动路由、锁定渠道、下架回退、多渠道比价）|

## 五、涉众与决策记录
- **渠道（渠道）**：首次体验为被称谓统一；新能力是"渠道价目公布 + 被用户自选"（不改变其结算/Key 管理业务）。
- **平台运营/管理员**：管理渠道、配置渠道价目、查看用户渠道选择分布。
- **终端用户**：自主比价、自选渠道、或依赖自动路由。

## 六、待确认/待设计细化项
1. `/me/models` 兼容策略：保留 `DEFAULT_MODELS` 回退还是完全切换到 DB 驱动（建议：DB 为主，DB 空时回退硬编码，避免回归）。
2. 渠道价格公布是否需区分"对 VIP/分组价"（`pricing_group` / `allowedGroups`）——用户侧价格应展示**该用户分组生效价**。
3. 渠道选择器是否需要"保存默认渠道偏好"（P1 增强）还是本期先做"每次选"。
