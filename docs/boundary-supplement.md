## ✅ [已合并到目标文档] 1. ref-5.1-routing.md — 智能路由系统 (P0)

### 模块概述

智能路由系统负责将用户的 API 请求（模型调用）按照策略分发给合适的供应商端点。核心功能包括路由策略配置、权重分配、熔断器、手动覆盖等。

### 边界条件清单

| # | 场景 | 触发条件 | 预期行为 | 影响范围 | 优先级 |
|---|------|---------|---------|---------|--------|
| ROUTE-001 | 全部供应商不可用 | 所有已配置供应商均返回错误或超时 | 系统进入熔断降级模式，向调用方返回 503 Service Unavailable，附带降级标识和预估恢复时间 | 全部 API 调用 | P0 |
| ROUTE-002 | 所有路由候选超时 | 所有候选路径均超过调用超时阈值 | 触发全局超时熔断，记录详细超时链路日志，唤醒管理员告警 | 该请求类型 | P0 |
| ROUTE-003 | 路由权重全为 0 | 某模型的所有供应商路由权重设置为 0 | 路由引擎跳过该模型的所有路由候选，标记为"手动关闭"，直接返回错误并提示管理员启用至少一个路由 | 该模型所有调用 | P0 |
| ROUTE-004 | 路由配置不存在 | 请求的模型没有对应的路由配置记录 | 使用默认兜底路由策略（若有配置），否则返回 404 并写入配置缺失告警 | 该模型调用 | P0 |
| ROUTE-005 | 熔断器恢复窗口过载 | 熔断器处于半开状态时大量并发请求涌入 | 仅允许一个探测请求通过（其余直接快速失败），探测成功则逐步恢复流量，失败则重新闭合 | 该熔断器作用域 | P1 |
| ROUTE-006 | 手动覆盖与自动路由冲突 | 管理员手动指定某供应商，但自动路由正在执行反向恢复 | 手动覆盖优先级最高，自动路由在该覆盖期间暂停对覆盖目标的调整，覆盖解除后恢复 | 该覆盖目标 | P0 |
| ROUTE-007 | 路由候选升降级竞态 | 两个并发请求同时触发候选升降级逻辑 | 使用乐观锁保证升降级原子性，后执行的升级/降级需基于最新状态重新判断，防止同一候选被重复升降级 | 路由候选状态 | P1 |
| ROUTE-008 | 路由配置热更新不一致 | 路由配置更新过程中服务实例间生效时间不一致 | 引入配置版本号，同一请求在单次链路上使用一致版本；跨版本请求允许短暂差异化，差异窗口不超过 30 秒 | 全部服务实例 | P1 |

### 详细边界说明

#### ROUTE-001: 全部供应商不可用

**处理流程**:
1. 路由引擎检测到所有候选供应商均不可用（连续 N 次失败）
2. 立即触发一级熔断，标记该路由策略为 `DEGRADED` 状态
3. 向调用方返回统一错误码 `ROUTING_ALL_DOWN`，附带 JSON 体：
   ```json
   { "error": "routing_all_down", "message": "所有供应商暂时不可用，请稍后重试", "estimated_retry_ms": 30000 }
   ```
4. 触发 P0 级管理员告警（短信 + 电话）
5. 进入自动健康探测循环（间隔 10s），任一供应商恢复后自动解除熔断

#### ROUTE-002: 全部候选超时

**处理流程**:
1. 单个请求尝试所有候选路径，每条路径均超过设定的超时时间（默认 30s）
2. 总耗时已超越全局超时上限（默认 120s），不再重试
3. 记录 `timeout_chain` 日志，包含每条候选的耗时、错误码、节点信息
4. 返回 `504 Gateway Timeout`，附带优化建议（如：降低模型参数、切换轻量模型）

#### ROUTE-006: 手动覆盖冲突

**规则**:
- 手动覆盖状态保存在 `route_overrides` 表中，附带过期时间（默认 4h）
- 覆盖期间，自动熔断器仍然可以触发（覆盖仅影响路由选择，不影响熔断保护）
- 覆盖到期后自动移除，若无其他覆盖则恢复自动路由
- 管理员可在覆盖到期前手动解除

### 异常流程汇总

| 场景 | 恢复策略 | 是否通知 |
|------|---------|---------|
| 全部供应商不可用 | 自动健康探测 + 自动恢复 | P0 告警（短信+电话） |
| 路由配置不存在 | 创建默认配置或返回 404 | P1 系统通知 |
| 手动覆盖期间自动熔断 | 熔断不受覆盖影响，自动恢复 | P1 操作日志 |
| 权重全 0 | 要求管理员手动启用 | P2 邮件通知 |

## ✅ [已合并到目标文档] 2. ref-5.3-rate-limiter.md — 限流引擎 (P0)

### 模块概述

限流引擎提供四级限流机制（API Key → 用户 → 模型 → 全局），支持令牌桶和滑动窗口两种算法，配套熔断降级策略。

### 边界条件清单

| # | 场景 | 触发条件 | 预期行为 | 影响范围 | 优先级 |
|---|------|---------|---------|---------|--------|
| RATE-001 | 四级限流全部触发 | 同一请求同时触及 API Key、用户、模型、全局四级限流阈值 | 返回最严格的限流结果（最小配额），四级限流信息均在返回头中标记（`X-RateLimit-*`） | 该请求 | P0 |
| RATE-002 | 限流配置错误（负数阈值） | 限流规则中阈值为负数或 0 | 系统自动拒绝该配置，返回配置校验错误；若配置已生效，则以系统默认值（如 100 req/min）兜底 | 该限流规则的生效范围 | P0 |
| RATE-003 | 限流计数器溢出 | 高并发下计数器达到整型上限 | Redis 计数器使用带 TTL 的自增结构（EXPIRE + INCR），单个 Key 上限 2^31-1，达到上限后重置该窗口计数器 | 单个限流窗口 | P1 |
| RATE-004 | 分布式限流时钟偏差 | 多实例间系统时钟偏差超过 100ms | 令牌桶模式：基于 Redis 集中存储，不受本地时钟影响；滑动窗口模式：使用 Redis sorted set，偏差影响 < 允许误差 | 分布式实例 | P1 |
| RATE-005 | 限流熔断后恢复 | 触发限流后熔断器闭合，但调用方仍持续发送请求 | 熔断器采用"快速失败 + 渐进恢复"策略：半开窗口内仅放行 10% 请求，成功率达到阈值后逐步放开 | 该 API Key/用户 | P0 |
| RATE-006 | 白名单绕过限流 | 内部服务或白名单 IP 调用时绕过限流检查 | 白名单请求跳过限流计数，但在返回头中标记 `X-RateLimit-Bypass: whitelist` 以供审计 | 白名单请求 | P0 |
| RATE-007 | 限流规则热更新竞态 | 限流规则更新过程中部分实例使用旧规则、部分使用新规则 | 引入规则版本号，请求在单次链路中使用一致的版本；规则变更生效间隔不超过 5 秒 | 全部实例 | P1 |
| RATE-008 | Token 桶突发耗尽 | 令牌桶的突发容量（burst）被瞬时耗尽 | 后续请求回退到稳定速率模式，不再提供突发能力，直到桶内令牌自然补充到 burst 水平 | 该限流维度 | P1 |

### 详细边界说明

#### RATE-001: 四级限流全部触发

**处理逻辑**:
```
请求到来 → 检查 API Key 限流（已触发，剩余 0）
           → 检查用户限流（已触发，剩余 2）
           → 检查模型限流（已触发，剩余 0）
           → 检查全局限流（已触发，剩余 5）
           → 取最小值 = 0 → 返回 429 Too Many Requests
```
返回头中包含四级指标的各自剩余值，便于调用方针对性优化。

#### RATE-005: 限流熔断恢复

**恢复流程**:
1. 熔断闭合 → 进入半开状态（持续 60 秒）
2. 半开窗口内放行 10% 请求
3. 每 10 秒评估一次：若通过率 > 80%，扩大放行比例至 25% → 50% → 100%
4. 若半开窗口内失败率 > 20%，立即回到闭合状态
5. 恢复成功后发送恢复通知

#### RATE-006: 白名单绕过

**白名单类型**:
- 内部服务 IP（CIDR 匹配）：跳过所有限流
- 运营调试账户：跳过用户级和 API Key 级限流，但仍受全局限流保护
- 健康检查探针：完全跳过

### 异常流程汇总

| 场景 | 恢复策略 | 是否通知 |
|------|---------|---------|
| 负数阈值配置 | 拒绝配置，使用系统默认值 | P1 配置告警 |
| 计数器溢出 | 自动重置窗口 | 仅日志记录 |
| 分布式时钟偏差 | 集中存储不依赖本地时钟 | 无 |
| 白名单滥用 | 审计日志监控异常流量模式 | P2 安全告警 |

## ✅ [已合并到目标文档] 3. ref-5.4-alert-rules.md — 告警规则 (P0)

### 模块概述

告警规则系统负责定义和管理告警触发条件、通知渠道、静默期、升级策略等，是平台可观测性的核心组成部分。

### 边界条件清单

| # | 场景 | 触发条件 | 预期行为 | 影响范围 | 优先级 |
|---|------|---------|---------|---------|--------|
| ALERT-001 | 告警风暴抑制 | 同一规则在短时间内（如 5 分钟内）触发超过 100 次 | 自动进入告警静默模式：相同规则只发送聚合摘要（每 5 分钟一条），风暴平息后恢复逐条发送 | 该告警规则 | P0 |
| ALERT-002 | 告警规则配置冲突 | 两条或多条告警规则的条件完全或部分重叠 | 规则引擎按优先级（P0 > P1 > P2 > P3）执行，同优先级按最后修改时间排序，较新的规则覆盖较旧的 | 重叠规则 | P0 |
| ALERT-003 | 所有通知渠道不可用 | 邮件、短信、Webhook、站内信四个通知渠道全部投递失败 | 告警事件写入"待发送"队列，启动备用通知通道（如有）；持久化未投递记录，管理员登录后显示待处理告警横幅 | 全部告警 | P0 |
| ALERT-004 | 告警静默期重叠 | 多个静默期规则重叠在同一时间段 | 静默期合并：取覆盖时间范围的最宽交集（取其并集），静默原因取优先级最高的规则 | 重叠区间 | P1 |
| ALERT-005 | 告警恢复事件丢失 | 告警触发后，对应的恢复事件因系统故障未被生成或传输 | 引入"告警超时自动恢复"机制：告警超过"最长持续期"（可配置，默认 24h）后自动标记为恢复；运维人员可手动确认恢复 | 该告警事件 | P0 |
| ALERT-006 | 告警规则表达式解析失败 | 用户自定义的告警条件（PromQL 类表达式）语法错误 | 保存时实时校验并拒绝；若已生效的规则因数据字段变更导致解析失败，标记为 `INVALID` 状态并停止评估，通知管理员 | 该规则 | P1 |
| ALERT-007 | 告警升级链断裂 | 告警未在升级时间窗口内被确认，但升级链中的下一级负责人不存在 | 跳过断裂层级，沿升级链寻找下一有效负责人；若链上全部失效，升级至系统超级管理员 | 该告警 | P1 |
| ALERT-008 | 告警通知频率超限 | 单个用户/渠道在短时间内收到过多告警通知 | 对同一用户开启通知节流：同一规则每 5 分钟最多发送 1 条；跨规则合并为告警摘要（每 15 分钟发送一次） | 该用户/渠道 | P1 |

### 详细边界说明

#### ALERT-001: 告警风暴抑制

**处理逻辑**:
```
触发器：同一告警规则 ID 在 5 分钟内触发次数 >= 100
动作：
  1. 停止逐条发送通知
  2. 启动聚合摘要模式，每 5 分钟发送一条聚合消息
  3. 聚合摘要格式："告警 [规则名] 在 [时间窗口] 内触发了 N 次，当前状态：[FIRING/RESOLVED]，影响范围：..."
  4. 统计风暴期间的最高频事件、平均持续时间
退出条件：连续 2 个聚合周期内触发次数 < 10 次/分钟
```

#### ALERT-003: 所有通知渠道不可用

**处理流程**:
1. 告警事件写入 `alert_pending` 表，状态为 `DELIVERY_FAILED`
2. 按指数退避重试通知（10s → 30s → 60s → 300s → 600s）
3. 若 30 分钟内仍未投递成功，升级至备用通知渠道（如有）
4. 管理员登录后，后台首页显示"未送达告警"计数器
5. 通知恢复后，按时间顺序补发未送达告警（每日凌晨压缩一次）

### 异常流程汇总

| 场景 | 恢复策略 | 是否通知 |
|------|---------|---------|
| 告警风暴 | 自动静默 + 聚合摘要 | 只发摘要 |
| 通知渠道全部不可用 | 指数退避重试 + 持久化 | 无（渠道不可用） |
| 恢复事件丢失 | 超时自动恢复 + 人工确认 | P2 运维通知 |
| 规则表达式解析失败 | 标记无效 + 停止评估 | P1 通知管理员 |
| 升级链断裂 | 跳级至有效负责人 | P1 通知当前告警责任人 |

## 4. SPEC-§4-管理后台.md — 管理后台 (P0)

### 模块概述

管理后台是平台运营管理的核心界面，涵盖总览看板、用户管理、供应商管理、财务管理、营销运营、安全、监控日志、系统配置、批量运营工具、异常交易工作台、数据生命周期管理等 24 个子模块。

### 边界条件清单

| # | 场景 | 触发条件 | 预期行为 | 影响范围 | 优先级 |
|---|------|---------|---------|---------|--------|
| ADMIN-001 | 批量操作部分失败 | 批量操作（如批量充值、批量修改用户状态）中部分项目成功、部分失败 | 采用"全部成功则提交，否则全部回滚"的事务模式；若不支持事务（如跨服务），逐条执行并记录成功/失败明细，返回操作报告 | 该批量操作 | P0 |
| ADMIN-002 | 角色权限变更对活跃会话的影响 | 管理员在后台修改了当前在线用户的角色或权限 | 活跃会话的权限在本次登录期间不变，权限变更在下次登录时生效（或强制重新登录后生效） | 该用户 | P0 |
| ADMIN-003 | 仪表盘数据加载失败 | 仪表盘的一个或多个数据源（如 Redis 缓存、数据库）不可用 | 降级显示：已缓存的数据优先展示并标记"缓存时间"；不可用数据源显示"--"或"加载失败"标记，不阻塞其他模块加载 | 仪表盘 | P0 |

### 详细边界说明

#### CORE-001: 并发扣款

**关键技术设计**:
```python
# 伪代码 — 扣款原子性保证
def deduct_balance(user_id, amount):
    lock_key = f"balance:lock:{user_id}"
    lock = redis.lock(lock_key, timeout=1000, retry_delay=50, retry_count=5)
    if not lock.acquire():
        return {"error": "concurrent_deduction", "retry_after_ms": 200}
    try:
        user = db.users.find_by_id(user_id, version=true)
        if user.balance < amount:
            return {"error": "insufficient_balance"}
        db.users.update_balance(user_id, -amount, version=user.version + 1)
        db.transactions.insert(user_id, -amount, type="api_call")
        return {"success": True}
    finally:
        lock.release()
```

#### CORE-004: 计费精度边界

**处理规则**:
- 最小计费单位：0.0001 元（1/10000 分）
- 小于最小单位：四舍五入到 0.0001
- 累计截断误差：每季度核对一次，差值 ≤ 0.01 元时在季度结算中补齐
- 货币使用 DECIMAL(16,4) 存储，禁止使用 float/double

#### CORE-005: 组件自愈

**自愈流程**:
1. 监控探针每 10s 检测各引擎组件健康状态
2. 检测到故障后触发自动重启，记录重启原因
3. 重启期间：
   - 路由引擎：使用最近一次成功路由结果 + 轮询策略
   - 计费引擎：请求排队等待（最多 30s）
   - 限流引擎：跳过限流检查（熔断模式）
4. 重启成功后自动恢复满负载
5. 重启失败 3 次则停止自动重启，触发 P0 告警

| COMP-004 | 活动 ROI 计算异常 | 运营活动 ROI 计算时，某个数据源（如投放成本、转化收入）不可用 | 使用已有数据计算部分 ROI，不可用的数据标记为"待补充"；ROI 报告显示"数据完整度"百分比；数据完整度 < 60% 时 ROI 报告标注为"低置信度" | ROI 分析 | P1 |
| COMP-005 | 隐私政策版本回滚 | 隐私政策发版后需紧急回滚到上一版本 | 版本管理支持一键回滚，回滚后当前版本标记为 `REVOKED`；用户重新看到回滚后的版本，系统引导用户重新确认 | 隐私政策 | P0 |
| COMP-006 | 服务条款批量确认超时 | 服务条款更新后，大量用户同时确认新协议导致系统压力 | 确认操作为异步低负载写入；系统设置用户"最后操作期限"，期限内未确认的逐步限制功能（先限制新 API 创建，再限制 API 调用） | 服务条款 | P1 |
| COMP-007 | 供应商成本多维度聚合异常 | 供应商成本按多维度（模型、时间、区域）聚合时出现数据不一致 | 使用 OLAP 预聚合（物化视图）保证各维度聚合结果一致性；发现不一致时刷新物化视图；告警记录不一致的范围和差值 | 成本分析 | P2 |
| COMP-008 | 合规数据归档冲突 | 合规数据在归档过程中被新的操作访问 | 归档前检查是否有未完成的事务；归档中的数据标记为 `ARCHIVING` 状态，新操作自动跳过；归档完成后更新访问权限 | 数据归档 | P2 |

### 详细边界说明

#### COMP-003: GDPR 数据删除请求过期

**处理流程**:
1. 用户提交 GDPR 数据删除请求 → 状态 `PENDING`，设置最终期限（30 天）
2. 到期前 7 天（D+23）：发送提醒通知给法务团队
3. 到期前 3 天（D+27）：升级通知到法务负责人
4. 到期日（D+30）：标记 `OVERDUE`，升级到法务总监和 CISO
5. 过期后仍须尽快处理，处理完成后更新状态为 `COMPLETED_OVERDUE`
6. 监管报告需说明所有过期请求的原因

#### COMP-001: 大文件导出

**技术实现**:
- 导出任务创建后立即返回 `task_id`
- 后台异步执行数据收集、格式转换、压缩打包
- 文件大小 > 100MB 自动分片（每片 50MB）
- 下载链接使用预签名 URL（临时 Token，有效期 7 天）
- 支持断点续传（HTTP Range 头）

### 异常流程汇总

| 场景 | 恢复策略 | 是否通知 |
|------|---------|---------|
| 大文件导出 | 异步分片 + 预签名 | 任务完成通知 |
| 成本分析数据延迟 | 部分数据标记 + 自动刷新 | P2 运维通知 |
| GDPR 请求过期 | 升级通知 + 延期处理 | P0 法务通知 |

| 隐私政策回滚 | 版本回滚 + 重新确认 | 用户重新确认 |
| 条款确认超时 | 逐步限制功能 | 用户通知 |
