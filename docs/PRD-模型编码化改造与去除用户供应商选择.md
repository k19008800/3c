> **文档编号**：PRD-MODEL-CODE

> **日期**：2026-09
> **状态**：**待评审**

## 0. 概述

### 0.1 背景

3Cloud 平台当前把"模型"与"供应商"作为**两个独立维度**：用户请求传 `model`（模型名），系统在提供该模型的多个供应商间自动选择（`selectChannel(model)` 按 priority/健康/熔断加权）；部分能力（`user-vendor-selection.md`、`方案-渠道化改造…`）规划了"用户自选渠道 + `model@vendor` 语法"。

但用户侧真正关心的只有"模型"。同一个逻辑模型（例如 `deepseek-v4-flash`）若由两个供应商提供服务，用户天然希望**看到两个 `deepseek-v4-flash` 可选项**，选中即确定供应商，而不需要额外的"供应商/渠道"选择菜单。背后的诉求是：**每个（模型 × 供应商）在系统内就是一条唯一的"模型编码"，供应商被隐式地固化进编码里。**

### 0.2 核心场景

```
用户进入模型中心，看到模型 "deepseek-v4-flash" 有两个可选项：
  └─ deepseek-v4-flash（供应商A，¥0.80/¥2.40）   ← 模型编码 ds-v4f-vendorA
  └─ deepseek-v4-flash（供应商B，¥0.90/¥2.60）   ← 模型编码 ds-v4f-vendorB
用户选中供应商B那一条
  → Playground / API 请求 model = "ds-v4f-vendorB"
  → 后端按编码精确命中供应商B + 其 platform_model + 定价
  → 计费/日志/对账全部锚定该编码
```

### 0.3 设计目标

| 目标 | 说明 |
|------|------|
| 用户无感 | 用户只选"模型"，不再出现"供应商/渠道"选择菜单 |
| 指哪打哪 | 模型编码全局唯一，一对一路由到供应商，无歧义 |
| 多供应商可见 | 同一逻辑模型的多个供应商在模型中心并排展示，各自价格/健康/状态 |
| 兼容演进 | 可选保留"智能/自动"兜底项；旧调用（裸模型名 / `model@vendor`）兼容窗口 |
| 术语统一 | "供应商选择"从用户侧移除，但管理后台的"供应商管理"保留为内部设施 |

### 0.4 与既有方案的差别（重要）

| 方案 | 用户侧形态 | API 语义 |
|------|-----------|---------|
| 现状 | 一个模型名 + 系统自动选供应商；`/me/models` 硬编码单价格 | `model = 模型名`，`selectChannel` 自动选 |
| 旧规划（`model@vendor`） | 模型 + 独立"渠道选择器" | `model = "模型@vendor"`，`@` 后为渠道编码（供应商仍是独立维度） |
| **本方案（模型编码化）** | **模型列表直接展开为"模型编码"条目，无供应商维度** | **`model = 模型编码`，编码即固化供应商** |

> 本方案**取代** `user-vendor-selection.md` / `方案-渠道化改造与用户自选渠道定价.md` 中"用户自选渠道"的二维设计。后台"供应商管理"设施保留，但不再向用户暴露"供应商选择"。

## 1. 决策基线（评审确认项）

| 编号 | 决策点 | 建议结论 | 待评审 |
|------|--------|---------|--------|
| M-C-01 | 模型编码命名规则 | `{modelName}@{supplier.code}`（如 `deepseek-v4-flash@vendorB`）或平台短 code（`dsv4f-vb`） | ✔ 需拍板 |
| M-C-02 | 目录/权威模型 | 在 `supplier_models` 层引入**可路由的 `model_code` 列**（唯一索引），作为 API `model` 权威值 | ✔ 需拍板 |
| M-C-03 | 是否保留"智能/自动"兜底 | **建议保留**：`model="deepseek-v4-flash"`（无编码）→ 走现有智能路由；`model` 含编码 → 精确路由 | ✔ 需拍板 |
| M-C-04 | 旧调用兼容 | 建议 1 个版本兼容窗口：裸模型名→自动；`model@brandCode`→若匹配编码则精确，否则视为自动 | ✔ 需拍板 |
| M-C-05 | 编码显示名去重 | 同一逻辑模型多个编码时，模型中心用"模型名（供应商名）"作展示名，编码作值 | ✔ 需拍板 |

## 3. API 变更需求

| 方法/路径 | 现状 | 目标 |
|-----------|------|------|
| `GET /api/v1/me/models` | 硬编码 `DEFAULT_MODELS`（单供应商单价格） | 按 (模型×供应商) 展开为**编码列表**；每编码含唯一供应商/价格/状态；DB 空时回退兼容 `DEFAULT_MODELS` |
| `GET /api/v1/models/:modelName/channels` | 渠道价目（若已实现） | 改为"该逻辑模型下的**编码清单**"（语义同，字段口径换成编码） |
| `POST /api/v1/(chat/completions|playground/...)` | model 为模型名，`selectChannel` 自动选 | 解析 `model`：编码→精确锁定供应商；`auto`/裸名→自动路由 |
| 路由层 `selectChannel` | 按模型名自动选第一个可用 | 增加"按编码精确锁定"入参；命中唯一 `supplier_models` |

## 4. 数据模型变更需求

| 变更 | 说明 |
|------|------|
| `supplier_models` 增加 `model_code` | 全局唯一、可路由、一对一映射供应商+模型；做唯一索引 |
| 编码生成 | 后台/同步引擎生成；选定规则后稳定不可复用 |
| 索引与唯一性 | `model_code` 唯一索引，防复用 |
| 兼容 | `model_name` 保留；`platform_model` 保留；新增 `model_code` 作为用户可调用的权威标识 |
| `consumption_records` / `call_logs` | 增加/确认 `model_code` 字段作为锚点，支撑日志与财务对账回追溯 |

---

## 5. 运营与客服策略

| 场景 | 策略 |
|------|------|
| 某供应商某编码下线/维护中 | 该编码置灰/不展示；若用户已调用过，下次调用返回该编码不可用错误码 + 可选编码清单 |
| 多供应商编码并存 | 运营可比价定价；允许"某编码专属价格/分组价"（沿用 L4 分组价逻辑，落到编码维度） |
| 客服 FAQ | "为什么同一个模型有两个条目？"——来自不同供应商，价格/稳定性不同，可在模型中心逐条对比 |
| 供应商结算 | 对账以 `model_code`（→ supplier）为聚合锚点 |

## 6. 非功能需求

| 指标 | 要求 |
|------|------|
| 编码解析 | P99 < 1ms（纯字符串/索引查询） |
| `/me/models` 响应 | P99 < 200ms（字典缓存，TTL 60s） |
| 编码稳定性 | 唯一索引兜底，禁止复用/改码；改码需走迁移流程并更新历史锚点策略 |
| OpenAI SDK 兼容 | `model` 字段直接传编码即可，SDK 无感知 |

---

## 7. 运量/验收关注点（对接 test-agent）

1. 同逻辑模型多供应商：各编码独立路由、独立计费、日志正确记录 `model_code`。
2. 编码 404（`MODEL_CODE_NOT_FOUND`）/ 该用户无权限 403。
3. `auto`/裸模型名 → 自动路由行为与现状一致（若开启兜底）。
4. 某编码下线/维护中 → 错误码 + 可选编码清单；历史偏好自动回退（若启用偏好）。
5. `/me/models` DB 空 → 回退 `DEFAULT_MODELS`。
6. 每个新增/改动页面与按钮的 `[?]` 帮助齐全（见下方附录）。
