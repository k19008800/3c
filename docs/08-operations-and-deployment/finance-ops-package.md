## 2. 通用发布顺序

1. 变更单、版本号、影响主题和回滚方案获批准；确认窗口、主/备执行者及财务业务窗口。
2. 在目标环境只读检查环境变量、数据库连通性、Redis、磁盘、进程和当前版本；禁止使用开发 `.env`。
3. 构建发布包，生成并记录 SHA-256；执行者、包名、版本、checksum 写入证据清单。
4. 验证最近成功备份（≤24 小时、文件存在、大小合理、SHA-256 匹配）及最近恢复演练状态。
5. 获取发布锁和数据库迁移单执行者锁；锁不可用不得绕过。
6. 先执行迁移，严格按 [`migration-runbook.md`](migration-runbook.md) 顺序；失败即停，不启动 PM2。
7. 结构/约束/枚举/迁移记录校验通过后，再部署构建产物并启动或 reload API、Portal；Console 使用已校验构建产物。
8. 执行健康检查、路由检查、只读 smoke、五主题关键路径和告警试报；写入 request_id/版本/时间。
9. 发布后观察窗口内无 P1/P2 告警、错误率和延迟达标，财务窗口确认账务只读核验；否则按回滚章节处理。

发布结束必须归档：变更单、执行者、开始/结束时间、包 checksum、迁移日志、结构校验输出、健康检查、监控快照、告警试报、验收结论和异常工单。

## 3. 迁移执行控制

### 3.1 顺序、checksum 与单执行者锁

- 唯一入口：从 `3cloud/api` 执行已核验的 `pnpm run db:migrate:manual`；不得临时拼接 SQL 或使用未批准 runner。
- 顺序固定：Drizzle `0000–0016`，再按编号执行手写 `0017–0032`；每一步记录文件名、SHA-256、开始/结束时间、执行结果和数据库迁移记录。
- 发布包和每个迁移文件在执行前计算 SHA-256；执行中 checksum 与批准清单不一致，立即停止并升级。
- 单执行者锁必须覆盖“预检→备份确认→迁移→结构校验→释放锁”全流程。建议锁键：`3cloud:ops:migration:<environment>`，包含 release-id、holder、TTL、获得/续租/释放时间；锁过期、丢失或无法续租即停止。
- 仅锁持有者可执行；备份、迁移、发布的审批人与执行人按 SoD 分离。禁止第二人并发补跑。

### 3.2 失败即停与判断点

| 失败点 | 立即动作 | 禁止动作 |
|---|---|---|
| 环境/连接性/权限 | 停止并记录 | 不改生产配置绕过 |
| 备份缺失/恢复不可验证 | 停止发布 | 不以口头确认替代 |
| checksum 不一致 | 隔离包并升级 | 不执行该文件 |
| 任一迁移失败 | 保留现场、导出日志、通知值班 | 不跳过、不手工“修到能跑”、不启动 PM2 |
| 结构校验失败 | 停止并评估回滚 | 不接受部分成功 |
| 健康/业务 smoke 失败 | 冻结流量或按批准方案回滚 | 不继续放量 |

## 4. 五主题运行操作基线

| 主题 | 发布后只读核验 | 关键监控/告警 | 失败处置与回滚边界 |
|---|---|---|---|
| 充值 | 订单状态、渠道回调、余额流水一一对应；同 Key 重放不重复入账 | 回调验签失败、回调积压、入账延迟、重复入账、支付失败率 | 先停止回调消费/放量；不得直接改余额；按原订单状态和备份恢复方案处置 |
| 人工上账 | 待审/已拒/已付状态、审批阶段、SoD、转账单号唯一性、流水与余额一致 | 待审超时、审核失败、2FA 失败激增、通知 outbox 失败 | 停止人工上账写入口；已入账错误只能走独立调账/红冲，禁止改删原单 |
| 调账 | 审批链、限额事件、余额与流水、终态不可二次操作、负余额为零 | 限额拒绝/升级、审批积压、并发冲突、余额不足、负余额检测 | 停止调账/红冲写入口；不得逆向修改原记录；仅按批准的反向记录或备份恢复 |
| 退款/红冲 | 余额退款只增加一次；原路退款不回滚平台余额；红冲成功后原单才 reversed | 通道失败重试、退款积压、负余额拦截、重复执行、outbox 失败 | 停止执行/重试队列；通道退款失败保持 failed；不得手工补余额冒充原路退款 |
| 结算/对账 | 报告范围、匹配/差异总量、结算周期、关账状态、差异处理审计 | 对账锁冲突、任务超时、差异突增、关账失败、报表生成失败 | 停止关账/差异资金写入；保留报告与批次现场，不绕过锁或强行标平 |

各主题业务规则以对应 SPEC 为准：[`recharge.md`](../03-functional-spec/03-billing-and-finance/recharge.md)、[`manual-topup.md`](../03-functional-spec/03-billing-and-finance/manual-topup.md)、[`balance-adjustment.md`](../03-functional-spec/03-billing-and-finance/balance-adjustment.md)、[`refund-and-reversal.md`](../03-functional-spec/03-billing-and-finance/refund-and-reversal.md)、[`settlement-and-reconciliation.md`](../03-functional-spec/03-billing-and-finance/settlement-and-reconciliation.md)。

## 5. 备份、恢复与回滚

规范基线见 [`backup-and-restore.md`](backup-and-restore.md)：系统级 cron/宝塔任务每日 04:00（Asia/Shanghai），本机 7 天、异地独立存储 30 天，成功后复制并 SHA-256 校验；每月在独立环境恢复演练，绝不覆盖生产库。PostgreSQL custom archive 只能用 `pg_restore`。

### 恢复前后控制

- 恢复前冻结相关资金写操作，确认事件窗口、目标库、版本兼容性、备份对象和 checksum；两人复核，记录审批。
- 恢复后执行 schema/约束/枚举/迁移记录校验、余额与流水抽样、五主题只读核验、应用版本兼容性和健康检查。
- 恢复演练证据必须包含：演练日期、环境、备份文件名/大小/SHA-256、恢复命令输出、耗时、校验 SQL/输出、缺陷与复盘；当前证据位置仅预留为 `evidence/finance/<release-id>/restore/`。

### 回滚决策

1. 迁移前：优先使用已验证的逆向迁移（若有批准脚本）；无逆向脚本只能走已验证备份恢复。
2. 迁移失败：保留失败日志和锁信息，不自行猜测性回滚；由架构/运维 owner 决定修复或恢复。
3. 应用 smoke 失败：停止放量/写入口，按批准版本切换或恢复；资金数据不通过应用回滚“改回去”。
4. 退款/红冲、人工上账、调账已生效记录不可删除或改金额；必须产生独立反向记录并保留审计。

## 6. 监控、告警和值班

最低监控维度：API 5xx/4xx、P95/P99 延迟、数据库连接/锁等待/磁盘、Redis 可用性、迁移锁、队列积压、outbox、每主题状态停滞、余额-流水差异、对账差异量、退款/支付通道失败率。阈值、通知渠道和 pager 接收人必须在目标环境配置单中固化并试报；未配置不准宣称通过。

建议告警分级：P1（数据一致性、重复入账、负余额、生产不可用）立即电话/值班升级并暂停写操作；P2（持续错误率/延迟、迁移锁异常、队列积压、通道失败）15 分钟内响应；P3（单主题非关键延迟、报表失败）工作时段处理。告警记录保存于 `evidence/finance/<release-id>/monitoring/`。

责任矩阵：

- 运维执行者：预检、锁、发布/迁移、日志和证据完整性；
- 运维备值班：主值班失联接管，不能绕过锁和审批；
- 后端/架构 owner：迁移、结构、回滚技术判断；
- 财务业务窗口：五主题只读核验、金额/状态/对账口径确认；
- 安全/权限 owner：2FA、SoD、凭证和审计核验；
- 变更审批人：批准窗口、风险与回滚决策；
- 事件指挥人：P1 统一调度、暂停/恢复写操作和复盘。

实际姓名、联系方式、轮班时间和告警渠道必须填入变更单/值班表；本文不虚构配置。
