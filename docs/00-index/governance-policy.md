## 1. 唯一入口与权威层级

> 本文档是治理元文档，不是业务功能页面；不适用页面/按钮级 `[?]` 控件门禁。

1. `docs/00-index/README.md` 是全库唯一文档准入入口。
2. `document-inventory.md` 是全量登记事实表；`document-map.md` 是五大资金主题的交付追踪视图。两者必须保持一致。
3. `docs/README.md` 与 `docs/PRD-README.md` 是来源/导航入口，不得声明自己是唯一权威，也不得以自身链接范围排除已登记文档。
4. 权威层级为：`accepted` ADR → `approved` PRD → `approved` SPEC → `approved` ARCH/状态机/数据/权限 → `approved` API → `approved` TEST → `approved` OPS → archive。层级只表示依赖优先级，不允许下游文档反向覆盖上游裁决。
5. `draft`、`review`、`来源资料`、`迭代管理`、`临时恢复草稿`均不得单独作为开发或验收依据。
6. 每份文档必须在文件头提供：document ID、version、status、owner、source_of_truth，并在 `document-inventory.md` 登记。

## 2. 状态机

```text
draft → review → approved
  │       │         │
  └───────┴→ superseded ← approved（新版本替代）
                    │
                    └→ archived（仅追溯）
```

- `draft`：工作稿或来源资料，不能准入。
- `review`：已形成可审阅版本，仍不能准入；必须有评审记录、冲突处理和链接检查结果。
- `approved`：正式文档，可在其上游依赖均满足时作为开发/验收依据。
- `accepted`：仅用于 ADR，表示裁决生效。
- `superseded`：被明确的新文档/版本替代；保留链接和替代关系。
- `archived`：不再现役，仅供历史追溯。
- `rejected`：评审否决的工作稿；不得作为来源依据，保留原因。

状态变更必须在清单、地图（如适用）和文档头部同步；禁止只改表格不改正文，或只改正文不改登记。

## 3. 元数据与命名

- ID 在全库唯一，建议按域分配：`GOV-*`（治理）、`INDEX-*`（索引）、`PRD-*`、`SPEC-*`、`API-*`、`ARCH-*`、`TEST-*`、`OPS-*`、`ADR-*`。
- `version` 使用语义版本（如 `v1.0.0`）；重大契约/行为变化升主版本，兼容扩展升次版本，文字修订升补丁版本。
- `owner` 是对内容负责的角色或团队，不以文件路径代替 owner。
- `source_of_truth` 必须指向唯一事实来源；若为派生视图，写明其上游文档，不得写“代码现状”替代业务裁决。
- 文件名应稳定、可检索；改名必须保留替代链接并同步清单。

## 4. 升格、废止与冲突

### 升格为 approved/accepted 的最低条件

1. 元数据完整、ID 唯一、已登记。
2. 上游依赖已达到要求，或明确列出不阻断的缺口。
3. 需求、接口、状态机、权限/数据、测试、运维之间可追溯；关键决策关联 accepted ADR。
4. 业务冲突均已由 owner/产品/架构裁决；未裁决项标记 `CONFLICT`，不得包装为 approved。
5. 相对链接检查通过；UI 功能必须包含页面标题 `[?]` 帮助和按钮/操作入口 `[?]` 帮助对照表。
6. 有评审记录和验证证据；不得以“已实现代码”作为缺失文档的替代证据。

### superseded/archived

- 新文档必须明确 `supersedes`/`superseded_by` 和原因；旧文档不可静默删除。
- 仅当替代文档已登记并可访问时，原文档才可标为 `superseded`。
- `_recovered/` 永远是临时工作区；恢复内容须人工裁决后移入正式目录或归档，不能因登记而自动 canonical。
- `supplement/` 是来源资料；通过联合评审后升格为正式 SPEC 章节，或标记 `superseded`，不能直接跳过评审成为开发依据。

## 5. 变更控制

1. 变更提交必须说明变更原因、影响范围、上游依据、受影响 ID/链接、迁移/回滚方式（如适用）。
2. 业务规则、金额、权限、状态转移、API schema、错误码、幂等或验收基线的变更，必须先新增/更新 ADR 或取得对应裁决，再修改正文。
3. 只读导航变更可由治理 owner 合并，但仍须更新清单并跑链接检查。
4. 版本发布前，至少检查：元数据、重复 ID、登记一致性、相对链接、`CONFLICT`/待办状态、下游追踪。
5. 禁止把历史来源中的“待裁决”文字直接复制进 approved 文档；已 accepted ADR 与旧来源冲突时，以 ADR 为准并登记正文修订任务。

## 6. 开发与验收准入规则

一个主题只有在以下条件全部满足时，才可进入开发准入：

- PRD、SPEC、API、状态机、权限/数据文档均已登记且为 `approved`（ADR 为 `accepted`）；
- TEST 文档已建立并覆盖主流程、异常、幂等、权限/SoD、金额精度和终态不可逆等要求；
- OPS 文档已建立并覆盖发布、迁移、监控、回滚、备份/恢复责任；
- 所有主题级 `CONFLICT` 已关闭，或明确由治理负责人确认“不阻断”且不涉及业务裁决；
- 页面/操作的 `[?]` 帮助要求已在 SPEC、实现和测试中可追踪；
- 完整性检查、链接检查和对应评审证据通过。

本次矩阵只登记现状和缺口；“已具备 PRD/SPEC/API/状态机”不等于 TEST/OPS 完整，也不等于业务主题 approved。任何缺口均须在矩阵关闭后重新评审。

## 7. 责任与证据

- 治理 owner：维护入口、状态机、ID、清单和变更记录。
- 产品 owner：业务规则、范围、验收口径及冲突裁决。
- 架构 owner：状态机、权限、数据、一致性和 API 约束。
- 测试 owner：TEST 覆盖与真实执行证据。
- 运维 owner：OPS、迁移、发布、监控和恢复证据。

任何状态结论都必须能从文档链接、评审记录或真实命令输出复核；没有证据的项目标为“待补证据”，不得声称完成。
